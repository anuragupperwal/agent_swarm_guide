Reasoning and planning patterns

Every pattern in this chapter answers the same three questions. How many model calls does a task get? What does each call see? And what decides the next call: the model, your code, or the environment? Once you can answer those for a pattern, you can predict its cost, its latency, and how it fails.

The big idea

Chapter 01 showed that one model call turns a context into tokens, and Chapter 03 wrapped that call in a loop. Reasoning and planning patterns are different ways of arranging calls. Some spend more tokens inside a single call. Some split the work into a planning call and cheaper execution. Some run the same work several times and compare. Some search a tree of possibilities.

Key idea

Reasoning patterns trade model calls and tokens for reliability. More calls buy more chances to catch an error, or more ways to bring outside facts in. They cost money and time. The engineering skill is buying only as much reliability as the task needs, and knowing which kind of mistake each pattern actually catches.

Two questions sort every pattern on the map:

  • Where does the plan live? Inside the model's head (CoT, ReAct, native thinking), or as an explicit artifact your code holds (plan-and-execute, ReWOO, LLMCompiler)? A plan your code holds can be validated, budgeted, parallelized and shown to a human before anything runs.
  • Where does feedback come from? Nowhere (CoT), from the model itself (Self-Refine), from the environment (ReAct observations, Reflexion's tests), or from a search over many attempts (ToT, LATS). Feedback from outside the model is the kind that catches the errors the model can't see.

Chain-of-thought and self-consistency

Chain-of-thought (CoT) means the model writes out intermediate steps before the answer. Wei et al. (2022) showed it by putting worked examples with reasoning into the prompt (few-shot CoT). Kojima et al. (2022) found that appending “Let's think step by step” gets much of the same effect with no examples (zero-shot CoT).

Why it works: tokens are computation

A transformer spends roughly a fixed amount of computation per token it produces. If the answer is the very next token, the model gets one forward pass to compute it. If it first writes “23 − 20 = 3”, two things change:

  • More passes. Each intermediate token is another forward pass that can do part of the work.
  • Intermediate results become context. “3” is now in the context window, so every later token can attend to it. The written reasoning acts as working memory the model can read back. It doesn't have to hold the whole calculation in one pass.

This also explains the limit. CoT gives the model more computation over what it already knows. It can't add facts. If the model doesn't know who owns the billing service, more thinking produces a more elaborate guess.

Pitfall · the reasoning isn't a proof

The written chain isn't guaranteed to be what produced the answer. Turpin et al. (2023) biased models toward a particular answer, for example by always making option (A) correct in the examples. The models followed the bias, and their written explanations never mentioned it. Treat CoT text as a useful trace for debugging. Don't build a safety check that assumes the stated reasoning is the real reason.

Self-consistency: sample several chains, then vote

Wang et al. (2022) noticed that a hard problem usually has several valid reasoning paths that reach the same answer, while mistakes tend to scatter. So: sample N independent CoT answers to the same question and return the most common final answer. The individual chains are thrown away. Only the answers are compared.

Self-consistency in plain Python

from collections import Counter

def self_consistent(question, n=5):
    answers = []
    for _ in range(n):                     # independent calls: run them concurrently
        out = llm.complete(messages=[{"role": "user",
                                      "content": question + COT_SUFFIX}])
        answers.append(extract_final_answer(out.text))   # e.g. parse "Answer: 9"
    best, votes = Counter(answers).most_common(1)[0]
    return best, votes / n                 # agreement is a free confidence signal

Three properties to remember:

  • N times the tokens, about one call of latency. The samples are independent, so they can run in parallel (Chapter 10).
  • It needs answers you can compare. A number, a label, a multiple-choice letter, a yes/no. For an essay or a plan, “most common” is undefined. You'd need a judge model or a similarity measure, which is a different pattern.
  • It needs diversity. If every sample takes the same path, voting adds nothing. Some current APIs, including Anthropic's, don't accept a temperature setting, so diversity comes from the default sampling or from varying the prompt. And if the model is systematically wrong (it confidently believes a false fact), all five samples agree on the wrong answer. Voting removes noise, not bias.

ReAct: reasoning interleaved with acting

ReAct (Yao et al., 2022) interleaves three things: a thought (reasoning about what to do next), an action (a tool call), and an observation (the tool's result, written into the context). Thoughts decide actions. Observations ground the next thought in facts the model didn't have. That second half is what CoT can't do.

You've already built ReAct. The agent loop from Chapter 03, using the tool protocol from Chapter 04, is ReAct with a structured wire format: the thought is the text (or thinking) before a tool_use block, the action is the tool_use block, and the observation is the tool_result your code sends back.

ReAct is the Chapter 03 loop

def react(task, tools, max_steps=10):
    messages = [{"role": "user", "content": task}]
    for step in range(max_steps):
        resp = llm.complete(system=SYSTEM, tools=tools, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})  # thought + action
        if resp.stop_reason != "tool_use":
            return resp.text
        results = [run_tool(call) for call in resp.tool_calls]      # your code acts
        messages.append({"role": "user", "content": results})        # observation
    raise StepLimitReached(max_steps)

Why ReAct is the default

  • Adaptive: every step uses the newest information.
  • Handles surprises (errors, empty results) naturally, because they arrive as observations.
  • Simple: one loop, one prompt, no plan format to parse.

Where ReAct hurts

  • Greedy: it decides one step at a time and can wander, repeat a call, or loop.
  • Every step re-sends the whole history: the n² growth from Chapter 01.
  • The plan is implicit. Your code can't validate, budget or show it before it runs.

Plan-and-execute

Plan-and-execute splits ReAct's single role in two. A planner call writes the whole plan before anything runs. An executor carries out one step at a time. Usually a replanner (often the same planner prompt, called again) looks at what has happened and decides whether to keep the plan, revise it, or finish.

The single-call ancestor is Plan-and-Solve prompting (Wang et al., 2023): “first understand the problem and devise a plan, then carry out the plan step by step”. It targeted a specific failure of zero-shot CoT, where the model skips a step. The multi-call agent version, with separate planner and executor, became a common open-source agent pattern around the same time.

Plan-and-execute, with the limits your harness owns

def plan_and_execute(task, max_steps=8, max_replans=3):
    plan = validate(planner.make_plan(task))      # LLM call → list of steps; check it before running
    done = []                                     # (step, result) pairs
    replans = 0
    while plan:
        if len(done) >= max_steps:
            raise StepLimitReached(max_steps)
        step = plan.pop(0)
        result = executor.run(step, context=done)   # a tool call, or a small ReAct loop
        done.append((step, result))
        decision = planner.replan(task, done, plan)  # LLM call: keep / revise / finish
        if decision.kind == "finish":
            return decision.answer
        if decision.kind == "revise":
            replans += 1
            if replans > max_replans: raise ReplanLimitReached()
            plan = validate(decision.plan)
    return planner.summarize(task, done)

Read the code for what it gives you and what it costs:

  • The executor sees less. Each step gets the step and the results it needs, not the whole transcript. Smaller contexts per call are cheaper and easier for the model to use well (Chapter 06).
  • The planner works with the least information. It commits to steps before any tool has run. Plans go stale the moment reality disagrees. Replanning fixes that but adds a model call each time it runs.
  • Every limit is in your code. max_steps, max_replans and validate don't depend on the model behaving. A planner that keeps revising forever is a known failure. Without max_replans, nothing stops it.

ReWOO and LLMCompiler: plans with placeholders

Look at where ReAct spends tokens. After every tool result it calls the model again, and every call re-sends the instructions, the tool definitions, and every earlier observation. Most of those tokens are repeats. ReWOO (“Reasoning WithOut Observation”, Xu et al., 2023) removes the repeats by planning the whole tool chain at once, before any result exists. The planner writes evidence variables (#E1, #E2, …) as placeholders for results it hasn't seen.

Planner
One LLM call. Writes the plan: each step names a tool, its input, and the variable that will hold its result. Later steps can refer to earlier variables.
Worker
Plain code, no reasoning between steps. Runs each tool in order, substituting earlier results into later inputs.
Solver
One LLM call. Reads the task, the plan and all the evidence, and writes the answer.

The numbers in Figure 5.4 are made up but the shape isn't. On HotpotQA, the ReWOO authors report roughly five times fewer tokens than a ReAct-style baseline, with a small accuracy gain. Where the saving comes from:

  • The prefix is sent twice, not once per step. Instructions, examples and tool definitions are often the biggest part of a ReAct call.
  • Each observation is sent once, to the solver, instead of being re-sent on every later step. This removes the n² term from Chapter 01.
  • Only two calls produce output tokens, and there are no “thought” turns between tools.

The cost is adaptivity. The plan is fixed before any evidence exists. If Metrics[billing] times out, the worker can't ask the model what to do. The solver receives #E2 = error: timeout and must answer with a gap. Adding a “replan on failure” step fixes this, and moves you back toward plan-and-execute.

ReWOO: two model calls, plain code in between

def rewoo(task):
    plan = llm.complete(system=PLANNER_PROMPT, tools=TOOL_DOCS,       # call 1
                        messages=[user(task)])
    steps = parse_plan(plan.text)          # [("E1", "Metrics", "auth"), ...] → validate it
    evidence = {}
    for var, tool, arg in steps:           # the worker: no LLM in this loop
        arg = substitute(arg, evidence)     # "#E2" → the earlier result
        evidence[var] = run_tool_safely(tool, arg)   # errors become evidence, not crashes
    return llm.complete(system=SOLVER_PROMPT,                      # call 2
                        messages=[user(task, plan.text, evidence)]).text

LLMCompiler: the plan as a dependency graph

ReWOO's worker runs steps one after another. LLMCompiler (Kim et al., 2023) borrows an idea from compilers: if two instructions don't depend on each other, run them at the same time. Its planner emits tasks with explicit dependencies, which form a DAG (directed acyclic graph). A task-fetching unit dispatches every task whose inputs are ready, in parallel. A joiner (an LLM call) then decides whether to answer or to replan.

# planner output: each task lists the tasks it depends on
1. error_count("auth")                       # deps: none   ┐
2. error_count("billing")                    # deps: none   ├ wave 1, in parallel
3. error_count("search")                     # deps: none   ┘
4. pick_max($1, $2, $3)                      # deps: 1,2,3  · wave 2
5. owner_of($4)                              # deps: 4      · wave 3

Five steps, three waves. Wall-clock time drops from the sum of all the tool latencies to the sum of the slowest tool in each wave. The paper reports large latency and cost reductions against ReAct on tasks with independent sub-steps. On tasks where every step depends on the previous one, a DAG has nothing to parallelize.

Key idea

ReWOO and LLMCompiler move the plan out of the model's context and into a data structure. Once the plan is data, ordinary engineering applies: validation, dependency analysis, parallel scheduling, retries per step. This is exactly the move your swarm harness makes when a planner returns child tasks for your code to schedule.

Think, check, retry: Self-Refine and Reflexion

The patterns so far make one attempt. The next family makes an attempt, gets feedback on it, and tries again. They differ in where the feedback comes from, and that turns out to be the whole story.

Self-Refine

Self-Refine (Madaan et al., 2023) uses one model in three roles: write a draft, critique it, rewrite it using the critique. Repeat until the critique finds nothing or an iteration limit hits. There is no training and no tool. It works best when the model can recognize a problem it didn't avoid the first time: missing constraints (“include all five keywords”), tone, readability, an obviously incomplete answer.

Reflexion

Reflexion (Shinn et al., 2023) works across whole attempts. An actor (often a ReAct agent) tries the task. An evaluator produces a signal: unit tests passing or failing, an environment's success flag, or a grader's score. On failure, a self-reflection call turns the trajectory and the signal into a short lesson in plain language, such as “I assumed the input was sorted. Check first.” The lesson goes into a memory buffer that the actor reads on the next attempt. The authors call this “verbal reinforcement learning”: the agent improves through its context, not its weights.

Reflexion: the evaluator is the part that matters

def reflexion(task, max_attempts=3):
    lessons = []                                    # episodic memory for this task
    for attempt in range(max_attempts):
        result = actor.run(task, lessons=lessons)    # e.g. a ReAct loop
        verdict = evaluate(task, result)             # tests, schema check, a grader
        if verdict.passed:
            return result
        lesson = llm.complete(messages=[user(
            reflect_prompt(task, result.trajectory, verdict.feedback))]).text
        lessons.append(lesson)
    raise AttemptsExhausted(lessons)              # the lessons are useful in the error report
Pitfall · a critic with no new information

Huang et al. (2023) tested models correcting their own reasoning with no external feedback. Accuracy often didn't improve and sometimes dropped: the model “corrected” right answers into wrong ones. The pattern works when the feedback carries information the first attempt lacked. Strong signals: a failing test, a compiler error, a schema validator, a tool result, a different model, a person. Weak signal: “Are you sure? Check your answer.” A reflection loop is only as good as its evaluator.

Search: Tree of Thoughts and LATS

CoT follows one line of reasoning. If an early step is wrong, everything after it is wasted. Tree of Thoughts (ToT, Yao et al., 2023) treats reasoning as a search problem. A thought is one coherent intermediate step. The harness asks the model to propose several next thoughts from a state, asks the model to judge how promising each resulting state is, keeps the best, and backtracks when a branch dies.

ToT has four parts you choose: how to split the problem into thought steps, how to propose candidates, how to evaluate states (a value label like sure/likely/impossible, or a vote between states), and the search algorithm (breadth-first keeping the best b per level, or depth-first with backtracking). On the Game of 24, the paper reports GPT-4 with CoT solving 4% of problems and ToT solving 74%.

ToT as beam search: count the calls

def tot_beam(problem, depth=3, k=5, beam=2):
    frontier = [State(problem)]
    for level in range(depth):
        candidates = [s.extend(t) for s in frontier
                                  for t in propose(s, k)]   # 1 call per state, k thoughts back
        scored = [(value(c), c) for c in candidates]           # 1 judge call per candidate
        scored = [(v, c) for v, c in scored if v > IMPOSSIBLE]
        frontier = [c for v, c in sorted(scored, key=by_value, reverse=True)[:beam]]
        for s in frontier:
            if s.is_solution():
                return s
    return None

Count it: level 1 costs 1 proposal and 5 judgments; levels 2 and 3 cost 2 proposals and 10 judgments each. That's about 30 model calls where CoT makes one. ToT is for problems where intermediate states can be judged and a wrong early step is expensive: puzzles, constrained planning, some code search. It's almost never worth it for a chat reply.

LATS: search over real actions

Language Agent Tree Search (Zhou et al., 2023) combines ReAct, Reflexion and ToT using Monte Carlo tree search (MCTS). Nodes are agent states. Expanding a node means actually taking an action in the environment and observing the result. Each new state gets a value, from an LLM's score and from environment feedback such as whether tests pass. Values are backed up the tree, so promising branches get explored more. Failed trajectories produce reflections that guide later expansions.

That design has a hard requirement: the environment must be reversible. To try a sibling branch, the harness has to return to an earlier state. Re-running a search query or resetting a sandbox works. Sending an email, charging a card or deleting a file can't be undone. LATS fits simulated web environments, code with tests, and question answering. It doesn't fit side effects in the real world.

What native thinking models change

Since 2024, frontier models have been trained, largely with reinforcement learning, to produce a long reasoning trace before they answer. OpenAI's o1 (2024) was the first widely known example. DeepSeek-R1 (2025) published a training recipe. Anthropic's models expose the same idea as extended or adaptive thinking. In practice, chain-of-thought has moved inside the call, into a dedicated content block.

What changes

  • You script the steps less. Provider guidance for reasoning models generally favors describing the problem, the constraints and what a good answer looks like, rather than prescribing “first do X, then Y”. Detailed step scripts can make the result worse.
  • ReAct's “thought” becomes a thinking block. With interleaved thinking, the model can think again after each tool result, before its next action. The Chapter 03 loop doesn't change. The quality of each step does.
  • Some checking moves inside the call. These models are trained to check their own work while thinking, so wrapping them in external self-consistency or self-critique can pay off less than it did with older models. Measure before you assume either way.
  • Thinking costs output tokens. Thinking is billed as output, and output is the expensive side. With adaptive thinking the model decides how much to think, and an effort setting moves the dial. On some current models thinking is always on and effort is the main control, so check your model's documentation. Your budget meter must count these tokens.
  • The protocol has a new rule. Thinking blocks come back with a signature. In a tool loop, send the assistant turn back exactly as you received it, thinking blocks included and unmodified. On newer models the signature is tied to the conversation that came before it, so rewriting earlier history (trimming old turns, changing the system prompt) can invalidate the reasoning. That's one more reason to keep history append-only, which Chapter 06 takes up. Depending on the model and settings, the thinking text itself may be summarized or omitted. Never build logic that parses it.

Key idea

Native thinking moves chain-of-thought inside the call. It doesn't move the plan into your harness, or the environment's feedback into the model. Agent patterns that put structure outside the model (explicit plans, external evaluators, parallel workers) still earn their place. Patterns that only add more reasoning inside one context (“think step by step”, some self-critique loops) pay off less.

Choosing a pattern: cost, latency, reliability

“Latency” here means wall-clock time for one task. “Reliability gain” is relative to a single plain call, and it depends heavily on the task. Treat this as a starting point for your own measurements, not a ranking.

A ladder that works for most agent designs: start with a capable model and a ReAct loop. Add an explicit plan when your code needs to validate, approve, budget or parallelize the work. Add an evaluator loop when you have a check that doesn't come from the model itself. Use search only for problems where states can be judged, and only in environments you can reset. Use self-consistency for short, comparable answers where mistakes look random.

Misconceptions to drop
  • “More reasoning is always better.” Past a point it costs tokens and time, and self-critique with no new information can make answers worse.
  • “The plan the model wrote is the plan that runs.” Only if your code validates it and executes it.
  • “Self-consistency fixes hallucination.” It removes noise. A model that confidently believes a false fact votes for it five times.
  • “ReWOO is just a faster ReAct.” It buys its savings by giving up the ability to react to results.
  • “Reasoning models make agent patterns obsolete.” They absorb reasoning inside one call. Facts, plans as data, outside evaluators, parallelism and budgets still live in your harness.

Each generated token is another forward pass of computation, and intermediate results written into the context can be attended to by later tokens, so the reasoning acts as visible working memory. It can't add facts the model doesn't have, and the written chain isn't guaranteed to be the real cause of the answer (Turpin et al.).

Apply A task needs four independent lookups, then a summary. Count the model calls for ReAct with one tool call per turn, ReAct with parallel tool calls, ReWOO, and LLMCompiler.

ReAct, one tool per turn: 5 (four lookup turns, then the answer), each re-sending a growing history. ReAct with parallel calls: 2 (one turn requests all four, one answers), but only if the model chooses to batch. ReWOO: 2 (plan, solve); its worker runs the four tools one after another. LLMCompiler: 2 (plan, joiner), and its scheduler runs all four in one parallel wave because the plan declares no dependencies. The real differences are history size and who decides about parallelism.

Apply You run self-consistency (n = 5, no tools) on “Which team owns the billing service?”. All five samples say “platform team”, which is wrong. Why didn't voting help, and what would?

Voting removes random errors. This error is systematic: the model doesn't know the fact, so every sample shares the same wrong belief, and 5 out of 5 agreement even looks like high confidence. The fix is grounding: give the model a tool that looks the owner up (ReAct), or retrieve the fact into the context (Chapter 07).

Design Your coding agent reviews its own patch using the same model and the same context, and the review almost always says “looks good”. Why, and how would you redesign it?

The critic has the same knowledge, the same blind spots and the same context as the author, so it has no new information. Self-correction without external feedback often doesn't help (Huang et al.). Redesign: make the evaluator external, by running the tests, the type checker and the linter and feeding concrete failures back (Reflexion). If you still want a model reviewer, give it a fresh context, a rubric and ideally a different model, and treat its output as one signal among several.

Design Someone proposes LATS for an agent that changes cloud infrastructure. What property of the environment does LATS need, and what would you propose instead?

LATS expands nodes by taking real actions and then returns to earlier states to try siblings, so the environment must be resettable or reversible. Real infrastructure changes have costs and side effects that can't be undone. Options: search against a simulation or a dry-run (“plan”) mode and execute only the chosen plan; limit search to read-only actions; or use plan-and-execute with a validated plan and human approval before any write.

Interview “Reasoning models think on their own now. Do we still need patterns like plan-and-execute or Reflexion?”

Thinking moves chain-of-thought inside one call, so prompts that script reasoning steps and some self-critique loops pay off less. It doesn't replace structure outside the model: tools for facts, a plan held as data that code can validate, approve, budget and schedule in parallel, external evaluators such as tests, budgets the model doesn't know about, and separate contexts for sub-agents. Thinking also has its own costs: output tokens, latency, and protocol rules such as returning thinking blocks unmodified. The honest answer is “fewer in-context tricks, the same need for harness structure, and measure the rest”.

Recall card

Five lines to rehearse. If you can expand each into a minute of explanation, you know this chapter.

  1. Every pattern trades calls and tokens for reliability. Ask: how many calls, what each one sees, and who decides the next one.
  2. CoT adds computation and visible working memory, but no facts. Self-consistency removes noise, not shared bias.
  3. ReAct is the Chapter 03 loop: adaptive but greedy, with growing history. Plan-and-execute, ReWOO and LLMCompiler move the plan into data your code can validate and schedule.
  4. A reflection loop is only as good as its evaluator. Outside signals (tests, validators) beat self-critique.
  5. Thinking models move CoT inside the call. Plans as data, outside feedback, parallelism and budgets stay in the harness.
