Concurrency for agents

An agent spends most of its life waiting for a model to reply. Concurrency is how one program keeps doing useful work during those waits. This chapter builds asyncio from the bottom up: the event loop, tasks, groups of tasks, cancellation and limits. It also covers the bugs that show up the moment two children run at once.

The big idea

Look at what one agent step actually does. Your code builds a request, which takes microseconds. It sends the request and waits for the reply, which takes seconds. Then it parses the reply and updates some state, which is microseconds again. Almost all of the step is waiting, and during that wait your process has nothing to compute.

Two words get mixed up here, and the rest of the chapter depends on keeping them apart:

Concurrency
Several tasks are in progress at the same time, so their lifetimes overlap. That says nothing about whether two instructions ever execute at the same instant.
Parallelism
Two instructions execute at the same instant, on different CPU cores.

A single cook with three pots on the stove is concurrent. Three cooks are parallel. If the pots mostly need waiting rather than stirring, one cook does fine.

Key idea

For agents, concurrency means overlapping waits, not using more cores. One thread can keep many model calls in flight at once, because while a call is in flight nothing in your process is computing. Every tool in this chapter is there to make that overlap happen, to bound it, or to stop it from corrupting shared state.

The chapter goes from the bottom up. First, what kind of work agents do. Then the four ways a child could run. Then how asyncio's event loop switches between tasks. Then the tools (create_task, gather, TaskGroup, cancellation, timeouts, semaphores, locks), each with the bug it prevents or causes. Chapter 09 made a run's state explicit. This chapter is about what happens when several pieces of code change that state at once.

I/O-bound vs CPU-bound work

Every piece of work is limited by something. Name the limit and you know which kind of concurrency can help.

CPU-bound
The work finishes as fast as the processor can compute it. Examples: tokenizing a large corpus locally, computing embeddings on the CPU, parsing a 200 MB file, running a small model on your laptop. The thread is busy the whole time.
I/O-bound
The work finishes when something outside the processor answers: the network, the disk, a subprocess, a human. Examples: a model API call, a web search tool, reading a file, waiting for an approval. The thread is idle for most of it.

An agent harness is overwhelmingly I/O-bound. A model call usually takes seconds, and longer outputs take longer (Chapter 01). Building the request and parsing a typical JSON reply usually take well under a millisecond. Here is what that means for five agents.

sequential ≈ sum of the waits  = 3 + 2 + 4 + 2.5 + 3.5 = 15 s
concurrent ≈ longest wait + total CPU work ≈ 4 s + (a few ms)

Same five jobs, but each is 3 s of computing instead of waiting:
one thread, any style  ≈ 5 × 3 = 15 s  ← nothing to overlap; you'd need more cores

The last line is the point. Concurrency on one thread helps only because the thread is idle during the waits. Give it five CPU-bound jobs and there is no idle time to fill, so the total stays at 15 seconds whichever way you schedule them. CPU-bound work gets faster only with parallelism, meaning more cores. In standard CPython that means more processes, for reasons the next section explains.

Pitfall

Concurrency reduces wall-clock time, not cost. Five concurrent calls are billed exactly the same tokens as five sequential ones. It also doesn't lift the provider's rate limits. Fifty children launched at once will hit them, which is why this chapter ends with semaphores.

Process, thread, coroutine or function call

Any of the four can run a child agent. They differ in four ways: where the child's code executes, who decides when it pauses, what it shares with the parent, and what the parent can do to it while it runs. Start with what each one is.

Function call
The child's code runs on the parent's own call stack. The parent's next line runs only after the child returns, and nothing else happens in between.
Coroutine
A function defined with async def. It can pause at an await and be resumed later. Wrapped in an asyncio task, it is scheduled on an event loop next to the parent and its siblings, all on one thread. It switches only where it awaits.
Thread
A line of execution scheduled by the operating system inside the same process. It shares all memory with the parent. In CPython, only one thread runs Python code at a time, because of the global interpreter lock (GIL). By default, the running thread is asked to give up the GIL after about 5 ms if another thread is waiting (sys.getswitchinterval()). Blocking I/O releases the GIL while it waits.
Process
A separate running program with its own interpreter and its own memory. Nothing is shared unless you send it. Arguments and results travel between processes as serialized (usually pickled) messages.

Also, “races between almost any two steps” is not an exaggeration. Even counter += 1 is several bytecode steps, and the OS can switch threads between them.

How the event loop works

The rest of the chapter uses asyncio, so it's worth knowing exactly what it does. There are four pieces, and each builds on the one before.

Coroutine
What calling an async def function gives you. The body has not started; you have a paused computation sitting at its first line.
Future
A placeholder for a result that doesn't exist yet: “the reply on this socket”, “the timer due in 2 seconds”. It is either pending or done. Every chain of awaits eventually ends at one.
Task
The thing that drives one coroutine. It runs the coroutine one step at a time. A step lasts until the coroutine awaits a future that isn't done yet. Then the task arranges to be woken when that future completes, and hands the thread back to the loop.
Event loop
One loop, on one thread, that runs task steps and other callbacks. It keeps a ready queue (a first-in, first-out list of steps that can run now), a set of timers sorted by due time, and the sockets it is watching for the operating system.

Each turn of the loop does three things. It asks the operating system which watched sockets are ready, waiting at most until the next timer is due (and not at all if the ready queue already has work). It moves those wake-ups, and any timers that are due, onto the ready queue. Then it runs what's in the queue, one step at a time.

Here's one coroutine, annotated with where it can and can't be paused:

One agent step, from the loop's point of view

async def agent_step(name):
    prompt = build_prompt(name)            # runs alone: no other task can run here
    reply = await call_model(prompt)       # suspends: the loop runs other tasks for seconds
    plan = parse(reply)                    # resumes on exactly this line, then runs alone again
    await trace.write("planned", name)     # may suspend: another chance for a switch
    return plan                            # the task is done

Two consequences matter for everything that follows.

  1. Between two awaits, your code runs alone. No other task can read or change shared state in that stretch. That's the most useful fact about asyncio, and the race section is built on it.
  2. An await is a place where a switch may happen. Only an await that actually has to wait gives up the thread. Awaiting a coroutine that never waits runs straight through, like a function call. Don't rely on that. A helper that doesn't wait today may start waiting after a small refactor, such as adding a trace write. Treat every await as a switch point.
Key idea

asyncio is cooperative. A task gives up the thread only at an await. That makes it easy to reason about, because no switch can happen between two awaits. It also makes it easy to break, because a task that never awaits stops everyone else. Threads are the opposite: the OS can switch them almost anywhere, so you can't point at the lines where a switch happens.

create_task vs await: creating work vs running it

Three lines of code look almost the same and do very different things. This is the asyncio version of the “create vs run” distinction in your Q2.

child(x)
Builds a coroutine object and nothing else. No line of child runs. If the object is thrown away without ever being awaited, Python warns “coroutine 'child' was never awaited”.
await child(x)
Runs the child now, inside the current task. The parent stops at this line until the child finishes. No new task is made, so this alone adds no concurrency. It behaves like a function call, except that other tasks may run while the child waits.
create_task(child(x))
Wraps the coroutine in a new task, puts its first step on the ready queue, and returns a Task handle at once. The parent keeps running. The child starts the next time the parent gives up the thread.
await task
Waits for a task that already exists to finish, then returns its result or raises its exception.

Row b in code: create first, then wait

async def parent():
    tasks = [asyncio.create_task(child(x)) for x in ("a", "b", "c")]
    log("created 3")                  # still the parent's turn: no child has run a line
    results = []
    for t in tasks:
        results.append(await t)          # first real wait: now the children start
    return results

If you print from inside each child, “created 3” comes out first, before any child's first line. Three facts follow from that, and each one matters in a harness:

  • Creating is instant and cheap. Running is slow and costs tokens. The gap between the two is where a harness can validate and register a child before any of its code runs. Chapter 16 builds the whole spawn lifecycle on this gap.
  • Keep a reference to every task you create. The asyncio documentation warns that the event loop keeps only weak references to tasks. A task that nothing else refers to can be garbage-collected before it finishes.
  • Every task needs an owner who awaits it. If a task that nobody awaits raises an exception, the error isn't raised anywhere. At best, asyncio logs “Task exception was never retrieved” when the task object is cleaned up. In a swarm, a child with no owner is an orphan: it keeps spending, and no one hears about it when it fails.

gather, TaskGroup and structured concurrency

Creating tasks one by one and awaiting each in a loop works, but you'll usually want one call that starts a group of children and waits for all of them. asyncio has two, and the difference between them is mostly about what happens when one child fails.

asyncio.gather

gather: start all, wait for all

results = await asyncio.gather(child("A"), child("B"), child("C"))
# results is in argument order: [A's result, B's result, C's result],
# whichever child finished first

results = await asyncio.gather(child("A"), child("B"), child("C"),
                               return_exceptions=True)
# a child that raised gives its exception object in its slot

gather wraps each coroutine in a task and runs them concurrently. Results always come back in the order you passed the children in, not the order they finished. Its failure behavior, from the documentation:

  • Default: the first exception is passed straight to the code awaiting gather. The other children are not cancelled. They keep running, but nobody is waiting for their results anymore.
  • return_exceptions=True: exceptions are treated like results. gather waits for every child and puts each exception object in that child's slot.
  • If gather itself is cancelled, it cancels every child that hasn't finished yet.

asyncio.TaskGroup

TaskGroup (Python 3.11+): the block owns its tasks

try:
    async with asyncio.TaskGroup() as tg:
        ta = tg.create_task(child("A"))
        tb = tg.create_task(child("B"))
        tc = tg.create_task(child("C"))
    # reaching this line means every task in the group finished without error
    results = [ta.result(), tb.result(), tc.result()]
except* ValueError as eg:                 # except* matches inside an ExceptionGroup
    for err in eg.exceptions:
        log("child failed", err)

A TaskGroup has one rule: the async with block can't exit until every task created in it has finished. When a task in the group fails with any exception other than CancelledError, the group cancels all the others and waits for them to finish. Then it raises an ExceptionGroup holding every real error, even if there's only one. You catch it with except* (PEP 654).

Pitfall

return_exceptions=True makes failure easy to forget. You get back a list and loop over it as if every item were a result. An exception object in that list looks like any other value until you check its type. A child that was cancelled shows up there too, as a CancelledError instance.

Structured concurrency

Nathaniel J. Smith's 2018 essay “Notes on structured concurrency, or: Go statement considered harmful” explains why the TaskGroup rule matters. A bare “start this in the background” call, like Go's go statement or a create_task nobody awaits, lets a function start work that outlives it. That breaks three things you normally rely on:

  1. You can't tell from a call whether it left something running. A function that returned may still have live tasks behind it.
  2. Errors have nowhere to go. The code that started the work has moved on, so there's no caller left to raise into.
  3. Cancellation can't find the work. Cancelling the caller doesn't reach a task it never linked to.

Structured concurrency's fix is one rule: concurrent tasks live inside a block, and the block doesn't exit until all of them have finished. The essay's library, Trio, calls that block a nursery. asyncio's TaskGroup applies the same rule. With it, every task's lifetime is visible in the indentation of your code, errors flow to the parent, and cancelling the parent reaches every child.

Key idea

An agent tree is a structured-concurrency tree. Every child should finish inside its parent's lifetime, the same way every task finishes inside its TaskGroup block. The spawn tree in your trace and the task tree in memory should be the same tree. A child still running after its parent returned is the orphan your Stage 3 acceptance criteria forbid.

Structure and failure policy are separate questions, though. TaskGroup's “one failure cancels the rest” is right for tightly coupled work, and usually wrong for independent children (Chapter 11, errors as values).

Cancellation: a request, delivered at an await

task.cancel() doesn't stop anything on the spot. It records a request. The next time the task is resumed, asyncio raises CancelledError inside the coroutine, at the await where it was suspended. From there it's an ordinary exception climbing the child's stack. Five consequences follow:

  1. Cancellation arrives only at an await. A task stuck in a CPU loop or a blocking call can't be cancelled until it next awaits.
  2. Cleanup runs. As the exception unwinds the stack, every finally block and every async with exit runs. That's where cleanup belongs: give back a semaphore slot, close a streaming response, write the “cancelled” trace event.
  3. A task cancelled before it starts never runs at all. Not its first line, and not its finally either. If your “agent started” and “agent ended” events are written inside the coroutine, a child cancelled while still in the ready queue leaves no trace events at all.
  4. Cancellation flows down linked awaits. Cancelling a task that is awaiting another task, a gather or a TaskGroup also cancels what it's awaiting. A task that nobody awaits isn't linked to anything, so it keeps running when its creator is cancelled. That's how orphans get made.
  5. It isn't caught by except Exception. Since Python 3.8, CancelledError inherits from BaseException. That's deliberate. But a bare except: or except BaseException: does catch it.

Why you must not swallow it

If a coroutine catches CancelledError and doesn't re-raise it, the request is lost and the task carries on as if nothing had happened. The documentation warns that TaskGroup and asyncio.timeout() are built on cancellation internally, and can misbehave if a coroutine swallows it. You can see this directly: a coroutine that swallows the error inside a 0.7-second timeout runs to completion at 1.2 seconds, and no TimeoutError is raised.

Wrong: cancellation becomes an ordinary value

async def child(job):
    try:
        return await do_work(job)
    except BaseException as e:  # catches CancelledError
        return {"ok": False, "err": repr(e)}

Right: record, clean up, let it travel

async def child(job):
    try:
        return await do_work(job)
    except asyncio.CancelledError:
        note("cancelled", job)     # quick and local
        raise                       # required
    except Exception as e:
        return {"ok": False, "err": repr(e)}
    finally:
        release(job)                # runs on every exit

Cleanup in a finally may itself await, for example to write a trace line. Keep it short, though. If someone cancels the task again while that await is in progress, for instance an outer timeout firing, the cleanup is interrupted too. Suppressing cancellation on purpose is almost never right in a harness. If you ever must, the documentation says to call Task.uncancel() as well.

Pitfall · the catch-all boundary

The “wrong” version above is exactly what a well-meaning error boundary looks like: “catch everything and return a failed Result, so one child can't crash the parent.” It also makes the child impossible to stop. Your Stage 3 break-it list includes “a child ignores cancellation”. This is how that child gets written by accident. Chapter 11's boundary rule, “let cancellation pass through”, exists because of this.

Timeouts and semaphores

A timeout is a scheduled cancellation

Python 3.11+: bound a block of awaits

try:
    async with asyncio.timeout(30):          # or asyncio.timeout_at(deadline)
        reply = await call_model(prompt)
except TimeoutError:
    ...                                        # the call took longer than 30 s

Here's what happens inside. On entry, the context manager sets a timer on the event loop. If the block is still running when the timer fires, the timer cancels the current task. CancelledError is raised at whatever await the block is suspended on, the finally blocks below it run, and when the exception reaches the end of the async with, it is turned into a TimeoutError. In Python 3.11 and later, asyncio.TimeoutError is the same class as the built-in TimeoutError. Before 3.11, the tool was asyncio.wait_for(aw, timeout), which still exists.

So a timeout is only as good as the cancellation underneath it. Everything in the previous section applies: it fires only at an await, it runs your cleanup, and a coroutine that swallows cancellation defeats it. asyncio.timeout_at() takes an absolute deadline on the loop's clock instead of a duration. That's the form you need for Chapter 11's rule, “pass deadlines, not durations”. How deadlines nest down a tree, and what values to pick, are policy, and Chapter 11 covers them (timeouts at every level).

A semaphore bounds how many run at once

A semaphore is a counter of free slots. async with sem: takes a slot, or waits until one is free, and gives it back on exit, even when the block raises or is cancelled. With a semaphore of 4 around the model call, at most 4 calls are in flight no matter how many agents exist.

At most 4 model calls in flight, however many agents exist

llm_slots = asyncio.Semaphore(4)

async def call_model(request):
    async with llm_slots:                 # waits here while 4 calls are in flight
        return await client.send(request)   # the slot is released on any exit

Three things a semaphore is not:

  • Not a rate limiter. Providers usually limit requests and tokens per minute. A semaphore limits how many calls are in flight at the same moment. Four slots with fast calls can still exceed a per-minute limit. Handling 429 responses is Chapter 11's job.
  • Not a fairness guarantee you should rely on. Don't build logic that depends on which waiting task gets the next slot. Stage 0A exercise 6 asks you to observe the order. Note what you see, and don't design around it.
  • Not free of deadlock. Where you put it matters. A slot held by a task that is waiting for something that also needs a slot can never be given back.

Races across an await

A race condition is a bug where the result depends on the order in which concurrent tasks happen to interleave. With threads, an interleaving can happen almost anywhere. With asyncio, it can happen only at an await that suspends. That's a huge help, because you can point at every spot where it can go wrong. It doesn't make races go away, though.

The classic shape is check-then-act: read some shared state, decide based on it, then change it. If an await sits between the check and the act, another task can run in the gap, check the same, still-unchanged state, and make the same decision. Here's the version every swarm harness writes at least once:

The bug: the check and the deduction are separated by an await

budget = {"left": 8000}

async def child(name, cost=5000):
    if budget["left"] >= cost:          # check
        reply = await call_model()       # suspends: the other child runs here
        budget["left"] -= cost            # act, on a stale decision

await asyncio.gather(child("A"), child("B"))   # left ends at -2000

Two fixes, and what each one costs:

Reserve before the await

Do the check and the deduction in one stretch of code with no await inside it. On one event loop, nothing else can run in that stretch, so it's atomic without a lock. Settle up afterwards, when the real usage is known.

if budget["left"] < cost:            # check ...
    return refuse()
budget["left"] -= cost                # ... and act: no await between
reply = await call_model()

Costs: you need a worst-case estimate up front, and something has to refund the difference afterwards.

A lock around check-and-act

An asyncio.Lock lets only one task at a time into a block, even one that awaits. You need it when the critical section must await, for example when the budget lives in a database or a file you have to read and write.

async with budget_lock:
    left = await ledger.read()
    if left >= cost:
        await ledger.write(left - cost)

Costs: every task queues at the lock. Hold it across the model call and you've made your swarm sequential again.

Notice that the lock version still reserves before the model call. The lock protects the read-check-write, never the slow work. Two more limits on these fixes: an asyncio.Lock coordinates tasks on one event loop and doesn't protect state shared with threads (that needs a threading.Lock). And neither fix helps across processes, where the state isn't shared to begin with.

Key idea

Every await between reading shared state and writing it is a door. To review concurrent code, find each piece of shared state (budget, agent counter, registry, a claimed-task set) and look at the lines between where it's read and where it's written. If there's an await in that stretch, either move the write above it or put a lock around it. This is the race behind Stage 3's “spawning at the exact moment the maximum agent count is reached”. It's the same shape with a counter instead of a budget.

Blocking calls and asyncio.to_thread

A blocking call holds the thread until it returns, without ever awaiting. Common ones: time.sleep, requests.get, a synchronous SDK client, subprocess.run, reading a large file with open().read(), and any heavy computation. Inside a coroutine, a blocking call doesn't just make that task slow. It freezes the whole event loop: every other task, every timer and every timeout waits until it returns (Figure 10.3: nothing can interrupt a running step).

One blocking call stalls everyone

async def heartbeat():                    # prints every 0.25 s, when it can
    for _ in range(6):
        print(f"beat {elapsed():.1f}")
        await asyncio.sleep(0.25)

async def bad_tool():
    await asyncio.sleep(0.3)
    time.sleep(1.0)                        # blocking: holds the thread for 1 s

await asyncio.gather(heartbeat(), bad_tool())
# beat 0.0   beat 0.3   beat 1.3   beat 1.6 ...   <- a one-second hole

In a swarm, that hole is every agent at once. Five agents whose replies arrived during the second have their data sitting unread in socket buffers, and their timeouts can't fire either. There are three ways out, in order of preference:

  1. Use an async library. An async HTTP client, or the async client that many provider SDKs offer. Its waits are real awaits, so the loop keeps running.
  2. Move blocking I/O to a thread with await asyncio.to_thread(func, *args) (Python 3.9+). The function runs in a worker thread, and your coroutine awaits the result. The loop stays free.
  3. Move heavy CPU work to a process, for example with loop.run_in_executor and a ProcessPoolExecutor. Only a separate process gets past the GIL in standard CPython.

to_thread has three catches worth knowing before you rely on it:

  • It doesn't speed up CPU-bound Python. The documentation says that because of the GIL, to_thread can typically only make I/O-bound functions non-blocking.
  • You can't cancel the thread. Cancelling the awaiting task stops the waiting. The function keeps running in its thread until it finishes, along with any side effects it has. A timeout around it gives you your control back, not the resources it's using.
  • Shared state becomes thread-shared. Whatever the function touches can now be changed at any moment by another thread, and an asyncio.Lock doesn't protect it.
Finding blocking calls

Run with asyncio.run(main(), debug=True), or set PYTHONASYNCIODEBUG=1. In debug mode, asyncio logs every step that holds the loop longer than 100 ms (loop.slow_callback_duration). That's often the fastest way to find the one synchronous call hiding in a tool.

Misconceptions to drop
  • “await runs things concurrently.” It runs one thing and waits. Concurrency comes from creating tasks.
  • “asyncio has no race conditions because it's single-threaded.” It has fewer places for them: every await between a read and a write of shared state.
  • “cancel() stops the task.” It requests a stop, delivered at the task's next await, and the task can ignore it.
  • “A timeout guarantees the block ends on time.” Only if the code inside awaits, and doesn't swallow cancellation.
  • “Threads would be faster for model calls.” For waiting, one thread already overlaps the waits. Threads add OS switching and races almost anywhere.
  • “to_thread makes anything non-blocking.” It frees the loop. It doesn't make CPU-bound Python faster, and the thread can't be cancelled.

Check yourself

Answer each one out loud or on paper before you open it.

Recall What's the difference between concurrency and parallelism, and which one does an agent harness mostly need?

Concurrency means several tasks are in progress with overlapping lifetimes. Parallelism means instructions execute at the same instant on different cores. A harness mostly needs concurrency, because its work is waiting on model and tool calls. One thread can overlap those waits. Parallelism matters only for CPU-heavy work, which in standard CPython means separate processes.

Recall What does asyncio.create_task(child()) do that await child() doesn't, and the other way round?

create_task wraps the coroutine in a new task, schedules it on the loop and returns immediately. The parent keeps running, and the child starts at the parent's next real await. await child() runs the child inside the current task and doesn't return until it's finished. It creates no new task, so it adds no concurrency. You also have to keep a reference to a created task and await it eventually, or its result and any error are lost.

Apply Eight agents each wait about 3 s for one model call. Estimate the wall-clock time run sequentially, with unlimited concurrency, and with a semaphore of 4 around the call.

Sequential: 8 × 3 = 24 s. Unlimited: about 3 s, the longest single wait. With 4 slots: two waves of four, so about 6 s. The token bill is the same in all three cases. If the provider rate-limits you, the unlimited version may also be slower in practice, because of 429 responses and retries.

Apply A child wraps each of its steps in try: ... except BaseException: continue. The parent runs it under async with asyncio.timeout(10), and the work takes 60 s. What happens at 10 s, and at the end?

At 10 s, the timer cancels the task, and CancelledError is raised at the child's current await. The child's except BaseException catches it, and the loop carries on. The block runs until the work finishes at about 60 s. No TimeoutError is raised, because no cancellation reached the end of the async with. The timeout was silently defeated. The fix is to catch Exception, or to re-raise CancelledError after any quick bookkeeping.

Apply A tool inside an async agent calls requests.get, and the server takes 20 s to answer. Five other agents are mid-call. What happens to them, and what are the fixes?

The whole event loop is frozen for 20 s. The other agents' replies wait unread, and their timers and timeouts can't fire. When the call returns, everything that came due runs late, all at once. Fixes: use an async HTTP client, or run the call with await asyncio.to_thread(...). Remember that cancelling a to_thread await doesn't stop the thread, so give the blocking call its own timeout as well.

Design Max agents is 10 and 9 exist. Two parents each run if registry.count() < MAX: await trace.write("spawning"); registry.add(child). What can go wrong? Give two fixes and what each costs.

Both parents check, both see 9, both write to the trace (an await), and both add a child, so 11 agents exist. It's check-then-act across an await. Fix 1: register or reserve the slot before any await, as one synchronous step (check and add together), and write the trace afterwards. It costs you having to undo the reservation if the spawn then fails. Fix 2: hold an asyncio.Lock across the check, the trace write and the add. It's correct even with the await inside, but every spawn queues behind the lock, so the lock must never cover slow work.

Design A parent has five independent children. It wants every child's outcome, including failures, and it must leave nothing running if it is itself cancelled. Which shapes meet both requirements, and which don't?

Default gather fails the first requirement: the first error reaches the parent while the other children run on, unobserved. gather(..., return_exceptions=True) meets both: every outcome comes back in its slot, and cancelling the gather cancels the unfinished children. A TaskGroup meets both only if each child converts its own failures into values at its boundary (while letting cancellation through). Otherwise its fail-fast rule cancels the siblings. Choosing between the two working shapes is your Stage 3 decision. Weigh the lifetime guarantee of the block against the extra boundary code.

Interview “Why would you build a multi-agent system on asyncio rather than threads?”

A strong answer starts from the workload: agents are I/O-bound, so the goal is overlapping waits, and in standard CPython neither threads nor asyncio give Python code parallel CPU time. asyncio tasks are cheap, switches happen only at await, so races can only occur at visible points. Tasks can be cancelled, and TaskGroup gives structured lifetimes, so no orphans. Threads can't be cancelled from outside and can be switched almost anywhere. Then give the costs honestly: one blocking call freezes everything, you need async libraries or to_thread, CPU-heavy or untrusted work belongs in processes, and races across awaits are still real.

Recall card

Five lines to rehearse. If you can expand each into a minute of explanation, you know this chapter.

  1. Agents are I/O-bound. Sequential time is the sum of the waits; concurrent time is the longest wait. Tokens don't change.
  2. One event loop, one thread, one running task. A task gives up the thread only at an await that has to wait.
  3. create_task creates work, await waits for it. Every task needs an owner; a TaskGroup makes the owner the enclosing block.
  4. Cancellation is a request delivered at the next await. finally runs. Never swallow CancelledError, because timeouts and TaskGroups depend on it.
  5. Every await between reading and writing shared state is a door for a race. Reserve before the await, or lock the read-check-write.
