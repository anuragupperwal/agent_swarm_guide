Why multiple agents (and why not)

A second agent is not free intelligence. It is a second context window, a second clock and a second chance to be wrong. This chapter asks what you buy when you split one agent into many, what you pay for it, and how to tell in advance which side wins.

The big idea

Everything in Parts 1–3 was about one loop: one model, one context window, one trajectory. A multi-agent system runs several of those loops and connects them. Each loop is an ordinary agent. What is new is the wiring between them, and the wiring has a price.

There are only three honest reasons to pay that price:

Context isolation
Each agent gets a fresh, focused window. It reads a lot, then returns a little. The agent that coordinates never sees the noise.
Parallelism
Independent parts run at the same time, so wall-clock time is set by the slowest part rather than the sum of the parts.
Specialization
Each agent gets a narrower prompt and a smaller tool set, so it chooses tools more reliably and follows its instructions more closely.

And four costs that come with every split: more tokens, coordination latency, compounding errors and information lost at every handoff.

Key idea

Multi-agent is a trade, not an upgrade. It pays when the task is wide (many parts that need little shared context) and valuable enough to cover the token bill. It loses when the task is deep (each step depends on decisions made in earlier steps). Your default should be one agent; you should have to argue your way to more.

Reason 1: context isolation

Chapter 06 showed that a context window is not a bucket that works equally well until it is full. Quality falls as it fills: old tool results distract, the middle gets less attention, and irrelevant detail competes with what matters. A long research task fills the window with search results from every subtopic at once.

A subagent is a way of throwing context away on purpose. The child reads forty pages about subtopic A in its own window, distils them into one page and returns that page. Its window, with all forty pages, is then discarded. The coordinator only ever holds the plan and the summaries.

Notice what isolation does not do. It does not reduce total work. It spends more tokens overall to keep each window small. It is the multi-agent version of a technique from chapter 06: compaction, applied before the context is written rather than after.

Pitfall

Isolation works only if the summary is good. A child that returns forty pages of raw text has defeated the point; a child that returns one vague line has thrown away the evidence. The return contract (chapter 16) is where you decide what “distilled” means.

Reason 2: parallelism

When the parts of a task do not depend on each other, nothing forces you to do them one after another. Because model calls are I/O-bound (you wait on the network, not the CPU), you can run them concurrently from a single process. Chapter 10 covers the mechanics with asyncio.

Tsequential = tplan + Σ ti + tsynth   vs   Tparallel = tplan + max(ti) + tsynth

Two consequences fall out of the max:

  • Stragglers set the pace. One child stuck in a retry loop holds up every result. Per-child timeouts are not optional in a parallel system (chapter 11).
  • The fixed steps don't shrink. Planning and synthesis are sequential by nature. If they dominate, parallelism barely helps. This is Amdahl's law in miniature: the speed-up is capped by the part you cannot parallelize.

Reason 3: specialization

A specialist agent has a prompt written for one job and only the tools that job needs. Fewer tools means fewer wrong tool choices; a shorter prompt means fewer competing instructions. It also limits damage: a critic with no write tools cannot break anything.

Be sceptical of this reason on its own. A single agent can also switch prompts, and a router (chapter 02) can pick a specialist prompt without a second loop. Specialization justifies a separate agent mainly when the specialist also needs its own context (reason 1) or its own permissions (chapter 12). Splitting work into “roles” because a human team would do it that way is a common design smell.

The evidence: Anthropic's research system

The most detailed public account of a production multi-agent system is Anthropic's write-up of the Research feature in Claude (2025). A lead agent plans, spawns subagents that search in parallel, and synthesizes their findings. Four numbers from it are worth memorising, along with the limits on each.

Finding (as reported)What it meansCaveat
A lead on Claude Opus 4 with Claude Sonnet 4 subagents scored about 90% higher than a single-agent Claude Opus 4.On breadth-first research, splitting helped a lot.Their own internal research eval, not a public benchmark.
On BrowseComp, token usage alone explained about 80% of the variance in performance; tool-call count and model choice explained most of the rest.Much of the gain comes from simply spending more tokens, spread across windows.“More tokens” is the mechanism, so cost scales with quality.
Agents used about 4× the tokens of a chat; the multi-agent system about 15×.The bill is large and predictable.Only worth it when the task's value is high.
Parallel subagents (and parallel tool calls inside them) cut research time by up to 90% on complex queries.Parallelism (reason 2) is real.“Up to”: the best case, on the widest tasks.

The same write-up is just as useful for what went wrong. Early versions spawned around fifty subagents for simple queries, searched endlessly for sources that did not exist, and distracted each other with too many updates. The fix was not clever code; it was explicit effort rules in the lead's prompt (roughly: one agent for a simple fact, a few for a comparison, many only for genuinely complex research) plus hard limits in the harness. The authors also say plainly that tasks needing all agents to share the same context, or with many dependencies between agents, are a poor fit, and they name most coding tasks as an example.

The four costs

Every split adds the same four costs. None of them is a bug you can fix once; each is a quantity you manage.

CostWhere it comes fromWhat it looks like in a traceMain lever
TokensEvery child re-reads its own system prompt, tools and brief; the lead re-reads every summary.Total tokens far above the single-agent run for the same question.Spawn limits; cheaper models for children; skip spawning for easy tasks.
Coordination latencyPlanning, waiting for the slowest child, then synthesis. In a synchronous design the lead is idle while children run.Long gaps in the lead's span; one child's span much longer than its siblings'.Timeouts; optional children; streaming partial results.

Information lossA summary is a lossy compression. Decisions made inside a child are invisible to its siblings.Children's outputs that contradict each other or don't fit together.Better briefs; richer return contracts; fewer, larger splits.

Error compounding, drawn to scale

If each step in a chain has probability p of being right, and the steps fail independently, the whole chain is right with probability pn. Small per-step error rates become large end-to-end ones.

The model cuts both ways, which is worth seeing clearly:

In series, more agents hurt. A plan → research → summary → synthesis chain multiplies the chance of a wrong link. Deep delegation trees are chains: a grandchild's error passes through its parent and then the root.

In parallel, more agents can help. If k independent attempts each succeed with probability p, and you can check which one succeeded, at least one succeeds with probability 1 − (1 − p)k. Voting and best-of-k rely on this, but only when you have a reliable checker.

Information loss: the counter-argument

In 2025 Walden Yan of Cognition (the company behind the Devin coding agent) published Don't Build Multi-Agents, a deliberate counterweight to the enthusiasm. Its argument rests on two principles:

  1. Share context, and share full agent traces, not just individual messages. A one-line brief cannot carry what the parent knows.
  2. Actions carry implicit decisions, and conflicting decisions carry bad results. Every choice a child makes (a style, a naming scheme, an assumption) is a decision its siblings never saw.

Its example: split “build a Flappy Bird clone” into two subtasks and run them in parallel.

The essay's recommendation is a single-threaded agent, with a separate model compressing old history when the context gets long. It notes that Claude Code's subagents are used to answer questions and investigate, not to write code in parallel with the main agent.

Key idea

The two essays do not contradict each other. Anthropic's system does breadth-first reading: children gather facts, and facts from different sources combine cleanly. Cognition's example is coupled writing: children make choices, and choices from different authors clash. The question to ask about any split is “do the parts need to agree on decisions that aren't in the brief?”

Wide tasks and deep tasks

That question sorts tasks into two shapes. Wide (breadth-first) tasks have many parts that each need little of the others' context. Deep (depth-first) tasks are a sequence in which each step depends on what earlier steps decided.

TaskShapeShared context the parts needMulti-agent fit
List the board members of every IT company in the S&P 500 (Anthropic's example)WideAlmost none: each company is independentGood
Check 40 contracts for an indemnity clauseWideThe clause definition onlyGood, though a fixed parallel workflow (ch02) may be enough
Explore a large codebase, then one agent makes the changeWide reading, deep writingChildren only read and reportGood if the children never write
Build a small game whose parts must fit togetherDeepStyle, interfaces and assumptionsPoor
Debug an intermittent race conditionDeepThe whole investigation so farPoor: one agent, careful context management

A decision checklist

Work through the questions in order. Any “no” sends you to a cheaper option. Notice that the last question is about measurement, not architecture.

Pitfall

“It's a learning project, so the checklist doesn't apply.” It applies more. If you never run the single-agent baseline, you will not learn whether your harness's recursion actually earned its cost, which is the most interesting result your project can produce.

In your swarm harness
  • Stage 5, Experiment 001. Your question is “Explain the architecture of a modern RAG system”. Before you run it: which of the three reasons applies to this question, and how strongly? Is it wide or deep? Write your prediction down.
  • Stage 5, baseline. Run the same question through a single agent with the same tools and the same total token budget. Record tokens, wall-clock time and a quality score for both. What score difference would convince you the recursion was worth it? Decide the threshold before you look.
  • Stage 6. Which of the four costs can you already see in your traces? Which one would you not notice without a dedicated metric?
  • Design question. Your children return summaries. What would the Flappy Bird failure look like in a research task: which implicit decisions could two sibling researchers make differently?

Check yourself

Answer each one out loud or on paper before you open it.

Recall Name the three reasons to use multiple agents and the four costs.

Reasons: context isolation, parallelism, specialization. Costs: tokens, coordination latency, error compounding, information loss.

Recall Does context isolation reduce the total number of tokens used?

No. It increases the total (several windows, each with its own system prompt and brief) to keep each individual window small and focused. It trades money for quality per window.

Apply Plan 5 s, parts of 30, 22 and 28 s, synthesis 10 s. Sequential and parallel wall-clock?

Sequential: 5 + 30 + 22 + 28 + 10 = 95 s. Parallel: 5 + max(30, 22, 28) + 10 = 45 s. The token cost is the same in both.

Apply Eight handoffs, each 95% reliable and independent. End-to-end reliability?

0.958 ≈ 0.66. Roughly one run in three has a wrong link somewhere. At 0.99 per step it would be about 0.92.

Apply Three independent attempts, each right 60% of the time, with a perfect checker. Chance at least one is right?

1 − 0.43 = 1 − 0.064 ≈ 0.94. Without a checker you can't tell which one is right, so the gain depends on how good the checker or vote is.

Design Why did Anthropic's research system work while Cognition argues against multi-agent coding?

Research is wide reading: facts from independent sources combine cleanly, and children make few decisions that siblings depend on. Coding is coupled writing: each child makes implicit decisions (style, interfaces, assumptions) that the others must agree with but never see.

Design Your lead spawns 12 children for “What year was the transformer paper published?” What went wrong, and where should the fix live?

Effort was not scaled to the task. Fix it in two places: guidance in the lead's prompt about how many children each kind of task deserves, and a hard limit enforced by the harness, so a bad plan cannot spend the budget even if the prompt is ignored.

Interview “Should we make our support bot multi-agent?” How do you answer?

Start with the checklist. Does a single agent with good tools fail measurably? Is the task wide? Support conversations are usually deep (each turn depends on earlier ones), latency-sensitive and high-volume, which makes a 15× token multiple hard to justify. Propose a measured single-agent baseline first, then test a split (for example, read-only retrieval helpers) against it on the same eval.
