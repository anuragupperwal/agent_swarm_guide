What a harness is

An agent is a model plus a program. This chapter takes the program apart. You'll see its nine components, follow one request through all of them, and walk through a real harness, Claude Code. It ends with the rule your swarm harness is built on: the model proposes, the harness disposes.

The big idea

Chapter 01 ended with a table. Every limitation of the model (it's stateless, it can't act, it can't stop itself, it costs money) mapped to a job that code around it must do. That code has a name: the harness.

The word has two useful meanings, and both apply. A horse's harness doesn't make the power; it channels it into a cart and gives the driver the reins. A test harness is the code that drives a component, feeds it inputs and records what it does. An agent harness does both. It turns the model's text into actions in the world, and it keeps the operator in control while that happens.

Key idea

Agent = model + harness. The harness is everything except the weights: the loop, the tools, what goes into the context, what is allowed, what it costs, what gets recorded, and when a human is asked. Two agents built on the same model can behave very differently, because the harness differs.

This is not a small point. Public coding benchmarks routinely show the same model scoring very differently under different scaffolds. The SWE-agent paper made this its central claim: changing the interface the model uses to see and edit files changed results substantially, with the model held fixed. When an agent is bad, the cause is often the harness, and the harness is the part you can change today.

Harness, framework, scaffold, SDK

These four words get used loosely, and sometimes interchangeably. Pin them down now, because Chapter 21 (the framework landscape) depends on it. Think of them as layers, not rival products.

A useful test: can it run an agent end to end with no extra code from you? An SDK can't. A framework can't until you assemble it. A harness can. A scaffold can, but usually only for the task it was built for.

Pitfall · names lie

Product names don't follow these definitions. Anthropic describes its Claude Agent SDK as giving developers the same agent harness that powers Claude Code, so it's a harness packaged as a library, despite the “SDK” in its name. Some “frameworks” ship a default loop that is close to a harness. Classify by what the thing does, using the test above, not by what it's called.

Your project builds a harness without a framework, and Stage 9 compares it with frameworks afterwards. That order is deliberate: once you've built each component yourself, you can see which ones a framework hides from you.

The nine components

Here is a single-agent harness taken apart. Not every harness draws these boundaries in the same place, and small harnesses merge several into one function. But every working harness does all nine jobs somewhere. If you can't point to where your harness does one of them, it isn't being done.

Each component has one job. The useful question for each is: what goes wrong if it's missing?

ComponentIts one jobWithout it
Loop driverRun call → act → repeat, and decide when to stopNo agent: one model call, then nothing
Model clientTurn a request into an API call; retry transient errors; parse the reply into your own typesProvider details leak into every file; a 429 crashes the run
Context managerDecide what goes into each request: system prompt, history, tool results, notesContext grows until it overflows or rots (Chapter 06)
State storeHold the run's facts: messages, status, partial results, step countNothing to resume from; no way to ask “where is this run?”
Tool registryMap each tool name to its schema and handlerThe model can name a tool that doesn't exist and your code calls something
Tool executorRun the handler with a timeout; turn exceptions into error resultsOne hung or crashing tool takes the whole agent down
Permissions + sandboxAllow, ask or deny each call; confine what an allowed call can reachThe model's text has root access to your machine
Budget meterCount tokens, steps, time; refuse work past the limitA loop that never ends, or a bill that never ends
TracerRecord every decision and action as structured eventsWhen it goes wrong, you can't say why (Chapter 13)
Human-in-the-loopTake the task, ask for approval, ask clarifying questions, accept a stopThe only control a person has is to kill the process

That's ten rows. The loop driver is the hub the other nine attach to, which is why the scope calls them nine components plus the loop. Count however you like, but don't drop one.

Here is where each one sits in code. This is a teaching sketch of a single agent, in plain Python with a generic client. It is not your swarm harness: your Stage 1 runner has different jobs, and you design it.

The loop driver, with every component it calls

def run(task, h):                                  # h holds the components
    state = h.state.new_run(task)                    # state store
    h.tracer.emit("run_started", run_id=state.run_id)
    while True:
        if not h.budget.allows_another_call(state):     # budget meter, BEFORE spending
            return h.finish(state, "budget_exceeded")
        request = h.context.build(state)              # context manager
        reply = h.llm.complete(**request)             # model client
        h.budget.charge(state, reply.usage)
        h.tracer.emit("model_call", usage=reply.usage, stop=reply.stop_reason)
        state.append(reply.message)

        if reply.stop_reason == "end_turn":
            return h.finish(state, "succeeded", answer=reply.text)
        if reply.stop_reason != "tool_use":            # max_tokens, refusal, ...
            return h.finish(state, "failed", reason=reply.stop_reason)

        results = [h.dispose(call, state) for call in reply.tool_calls]
        state.append(h.context.tool_results_message(results))   # all results, one message

Notice what the loop doesn't do. It never runs a tool itself. Every tool call goes through dispose, which you'll meet in the section on proposals. That single choke point is what makes the harness safe to reason about.

One request through every component

A component diagram shows what exists. A sequence diagram shows what happens, in order. Below is one small task, “fix the failing test”, as it moves through the harness. Read it top to bottom. Each horizontal arrow is one function call or message. The vertical dashed lines are the components, called lifelines.

Read the diagram as six phases. Each phase belongs to particular components.

  1. Intake. The human-in-the-loop component receives the task. The loop driver creates the run in the state store and the tracer records run_started.
  2. Think. The budget meter says yes or no to one more call. The context manager builds the request. The model client sends it and parses the reply.
  3. Charge. The budget meter adds the reported usage. Note that this is after the fact: you only learn the real cost of a call once it returns. Chapter 10 shows why that gap matters when calls run concurrently.
  4. Act. For each tool_use, the registry, permissions and executor dispose of it, in that order.
  5. Observe. The results go back into the state as one tool_result message, and the loop goes round again.
  6. Finish. end_turn, or a limit, ends the loop. The tracer records the outcome and totals, and the answer goes back to the caller.

The lines marked harness never reach the model. The model sees the task, its own outputs and the tool results. The harness sees all of that plus every decision it made. That asymmetry is the whole job: the model needs a clean, focused context, and you need a complete record. Your JSONL trace from Stage 1 is the “harness” lines, written down.

The model proposes, the harness disposes

An old proverb says “man proposes, God disposes”: you make plans, but something else decides what actually happens. In an agent, the harness plays the second part. A tool_use block is a proposal. It has no authority of its own. It's text the model wrote, and it becomes an action only if harness code agrees.

Key idea

Authority lives in harness code, never in model output. The model can ask for anything. What it gets is decided by the registry, the validator, the permission policy and the budget, all of which you wrote, tested and can read. This is your spec's principle 2.2, “LLM proposes, framework validates and executes”, seen from the inside.

Here is the choke point from the loop above, written out. Every branch returns a tool_result paired to the call's id, because the API requires an answer for every tool_use (Chapter 04).

dispose: one tool call, four checks, one result

def dispose(call, state):
    tool = registry.get(call.name)
    if tool is None:
        return error(call, f"unknown tool: {call.name}")
    problems = tool.validate(call.input)                  # schema first, then semantics
    if problems:
        return error(call, "; ".join(problems))
    decision = permissions.decide(tool, call.input, state)   # "allow" | "ask" | "deny"
    if decision == "ask":
        decision = human.approve(call)                    # blocks until a person answers
    if decision == "deny":
        return error(call, "denied by policy")
    if not budget.allows_tool(state, tool):
        return error(call, "budget exhausted")
    try:
        output = executor.run(tool, call.input, timeout=tool.timeout_s)
    except TimeoutError:
        return error(call, f"timed out after {tool.timeout_s}s")
    except Exception as exc:                          # the tool failed, not the harness
        return error(call, f"{type(exc).__name__}: {exc}")
    return ok(call, output)

def error(call, reason):
    tracer.emit("tool_rejected", tool=call.name, reason=reason)
    return {"type": "tool_result", "tool_use_id": call.id,
            "content": reason, "is_error": True}

Three things in this sketch are choices, and you should be able to defend each one:

  • Order. Cheap, certain checks go first. There's no point asking a person to approve a call whose input fails the schema. Now a harder one for you: should the budget check come before the human is asked? If the run can't afford the call, why interrupt anyone?
  • What the model is told. “denied by policy” tells the model to try another way. A detailed reason helps it recover, but it also teaches a misbehaving model exactly where the fence is. Chapter 12 returns to this trade-off.
  • What counts as the tool's fault. A tool that raises is an observation the model can react to. A bug in dispose itself is not; it should crash loudly in tests. Keep those two kinds of failure apart.
Pitfall · checks in the prompt

“Never delete files” in the system prompt is a request to the model, not a control. It lowers the odds, and that's all. If an action must never happen, the check has to be in dispose, where a test can prove it. Use the prompt to guide behavior, and use code to enforce rules.

The shape of a tool decides what the harness can check

The harness can only reason about what a tool call makes visible. That makes tool design a control question as well as a usability question. Compare the two extremes.

A single bash(command) tool gives the model enormous breadth. Anything the shell can do, it can do. But every action now has the same shape, an opaque string. To tell ls from rm -rf, the harness has to parse shell syntax, which is easy to get wrong. A dedicated tool like edit_file(path, old, new) can do far less, but it hands the harness typed fields to act on.

The harness wants to…With bash(command)With a dedicated tool
Gate one kind of actionParse a shell string and hopeMatch the tool name and typed arguments
Check stalenessNot possible in generalReject an edit if the file changed since the model last read it
Render for a humanShow a raw commandShow a diff, or a question with options
AuditLog a stringLog structured fields: which path, which action
Run in parallelMust assume it writes, so run calls one at a timeRead-only tools can safely run at the same time
Cover new tasksAnything the shell can doOnly what you built

A practical rule of thumb: start with broad tools, and promote an action to its own tool when you need to gate, render, audit or parallelize it. Which actions need gating? Reversibility is a good boundary. Reading a file can be undone by doing nothing. Sending an email, deleting data, paying, or writing to an external system can't, so those deserve their own tools with their own permission rules.

Even asking the user a question can be a tool. Claude Code exposes question-asking as a tool. When the model calls it, the harness renders the question with its options and the loop waits until the person answers. A tool is the model's only way to ask the harness for anything, and that includes a human.

Worked example: Claude Code

Claude Code is Anthropic's coding agent. It runs in a terminal, and also in IDEs, a desktop app and the web. The model behind it is the same Claude you can call through the API. Everything that makes it a coding agent is harness. So it's a good specimen: a production harness you can use every day and inspect from the outside.

A caution before the details. Products change quickly. What follows describes the general design as documented at the time of writing. Treat specific names and modes as examples, and check the current Claude Code documentation before relying on them.

ComponentHow Claude Code does it
Loop driverThe model works through tool calls until it ends its turn. You can interrupt at any point and redirect it.
Tool registryBuilt-in tools to read, search, edit and write files, run shell commands, fetch web pages, keep a to-do list and delegate to subagents. Tools from MCP servers are added to the same registry.
Permissions + sandboxPermission modes, plus allow, ask and deny rules in settings files. Rules match tool names and, for some tools, patterns such as a command prefix or a file path.
Context managerLoads project instructions from CLAUDE.md files at the start of a session. Reads files on demand rather than preloading the repository. Compacts the conversation when it nears the context limit.
State storeSaves session transcripts locally, so a session can be resumed later.
Budget meterShows context and token usage. Programmatic use through the Agent SDK can cap the number of turns.
TracerThe transcript itself, plus hooks that can log every tool call, plus optional telemetry export.
Human-in-the-loopApproval prompts, interruption, a question tool that blocks the loop until you answer, and a plan mode for review before any change.

Permission modes

A permission mode is a standing answer to “should I ask before doing this?”. Described generally, Claude Code offers a spectrum:

  • Default: reading is allowed. It asks before actions that change things, such as editing files or running shell commands, and you can approve one action or a kind of action for the session.
  • Accept edits: file edits go ahead without asking. Other risky actions still ask.
  • Plan: the agent may read and explore but not change anything. It ends by presenting a plan for you to approve.
  • Bypass: skips the prompts entirely. It's intended for isolated environments such as a throwaway container, where the sandbox is the safety boundary instead of a person.

Rules in settings files refine any mode. A deny rule beats an allow rule, so you can allow a broad class of commands and still forbid one dangerous member of it. This is permissions.decide from the sketch above, made configurable by the user.

Hooks

Hooks are commands you configure, which the harness runs at fixed points in its lifecycle. The harness passes the event's details (for a tool call, the tool name and its input) to your command, and your command's result can change what happens next. A hook that runs before a tool call can block it, and its message goes back to the model. A hook that runs after an edit can run a formatter or the tests.

Hooks matter for this chapter because they show where the line is. The model decides what to try. Hooks are deterministic code that runs every time, no matter what the model said, which makes them the right place for rules that must always hold. “Always run the linter after an edit” written in CLAUDE.md is a request. The same rule as a post-tool hook is a guarantee. One more consequence: hooks run with your own permissions on your machine, so a hook is code you must trust as much as any script you run.

Subagents

The main agent can hand a task to a subagent through a tool. Each subagent runs in its own fresh context window, with its own instructions and optionally a narrower tool set. When it finishes, only its final report comes back to the main agent. All the files it read and the dead ends it explored stay in its own context and are thrown away.

That's context isolation (Chapter 06), and it's the simplest form of spawning (Chapter 16). Note one design choice: as documented at the time of writing, Claude Code's subagents can't spawn subagents of their own, so the tree is one level deep. That's a deliberate limit, and a cheap way to make runaway recursion impossible. Your harness makes the opposite choice in Stage 2, which is exactly why you need depth, count and fan-out limits.

Compaction

A long session eventually nears the context limit. Claude Code then compacts: it has the model summarize the conversation so far, and continues with the summary in place of the full history. You can also trigger it yourself. Compaction trades detail for room, so anything the summary drops is gone from the model's view, though it can still be in the transcript. Chapter 06 covers how to choose what survives.

A swarm harness is a harness of harnesses

Now scale up. In a swarm, every agent still needs all nine jobs done. It has its own loop, its own context, its own tools and its own state. So each agent runs inside its own harness. What's new is a layer above them: the services that must be shared, because they describe the run as a whole rather than any one agent.

The table below sorts what stays per-agent from what the swarm layer must add. The right-hand column is a list of design problems, not answers. Most of Part 4 is about them.

ConcernSingle-agent harnessWhat the swarm layer adds
LoopOne loopOne loop per agent, plus a scheduler that runs many at once (Chapter 10)
BudgetOne meterOne ledger across the tree. How it is split between parent and children is a decision for you to make (Chapter 16).
TracingOne runOne run_id, an agent_id per agent and a parent_id link, so the trace forms a tree
PermissionsPer tool callA spawn policy too: who may create agents, how deep, how many
LifecycleStart, finishEvery agent has its own lifecycle. Parents wait on children, and cancelling one agent must reach its whole subtree (Chapters 09 and 10).
FailureThe run failsA child's failure becomes a Result its parent reads (your spec's principle 2.8)
HumanOne person, one agentWhich agents are allowed to ask the human anything?
Key idea

Spawning is a tool call, so it goes through disposal. spawn_agent sits in the parent's tool registry. When the parent proposes it, the request passes the same four checks as any other call: known, valid, allowed (the spawn policy), affordable (the ledger). Only then does the swarm layer create, register and schedule a new agent harness. The recursion is in the structure: the code that builds the child's harness is the same code that built the parent's.

Misconceptions to drop
  • “The agent ran the tool.” It proposed a call. The harness decided, then ran it.
  • “A framework is a harness.” A framework is a box of parts. A harness is the assembled, running thing.
  • “Safety rules belong in the prompt.” The prompt guides. Only code enforces.
  • “One bash tool is enough.” It's enough for breadth. It costs you the ability to gate, render, audit and parallelize.
  • “A multi-agent system is several agents.” It's several agents plus the shared services that make them one system.

Check yourself

Answer each one out loud or on paper before you open it.

Recall Distinguish SDK, framework and harness in one sentence each, and give the test that separates them.

An SDK is a typed client for one API. A framework is a set of reusable parts for building agents. A harness is the complete program that drives a model end to end. The test: can it run an agent end to end with no extra code from you? The SDK can't, the framework can't until assembled, and the harness can.

Recall Name the components around the loop driver, with one job each.

Model client: send, retry, parse. Context manager: decide what the model sees. State store: hold the run's facts. Tool registry: map names to schemas and handlers. Tool executor: run with a timeout and catch failures. Permissions and sandbox: allow, ask or deny, and confine. Budget meter: count and refuse. Tracer: record every decision. Human-in-the-loop: task, approvals, answers, stop.

Apply The model proposes send_email with the required to field missing. Walk it through Figure 8.3. What does the model see next?

Known: yes. Valid: no, because the schema check fails. The pipeline stops there. Nobody is asked for approval, no budget is checked, and nothing is sent. The harness returns a tool_result with the same tool_use_id, is_error: true and a reason such as “missing required field 'to'”. On its next call the model reads that and can retry with the field filled in.

Apply Your agent has only bash(command). Security asks you to block all network access except one internal host. Do you parse commands, or do something else?

Parsing is fragile. There are endless ways to reach the network from a shell (curl, wget, a one-line Python script, and so on), and you'll miss one. Enforce egress at a layer the command can't talk its way around: a sandbox or network policy that applies whatever the command is. Use parsing or dedicated tools for convenience and auditing, not as the security boundary.

Design Where should “never exceed the run budget” be enforced: the prompt, the loop driver, dispose, or the model client?

Not the prompt; that's a request. Check before every model call, so in the loop driver or a wrapper around the model client. Also check in dispose before any tool that spends, and spawning is one of them. Then notice the gap: usage is only known after a call returns, so a check-then-charge design can overshoot. Reserving budget before the call is one fix. Chapters 10 and 16 develop it.

Design Claude Code's subagents can't spawn subagents. Give one benefit and one cost of that rule, and say what your harness must add because it allows recursion.

Benefit: a runaway tree is impossible, and accounting and cancellation stay simple. Cost: deep tasks can't be split recursively, so the main agent has to do all the decomposition itself. Allowing recursion means you must add depth, count and fan-out limits, a ledger shared across the tree, cancellation of a whole subtree, and tracing that links each agent to its parent.

Interview “What's the difference between an agent and a harness, and why does it matter?”

Agent = model + harness. The harness is everything except the weights: the loop, tools, context, permissions, budgets, tracing and the human interface. It matters because reliability, safety, cost and observability all come from it. The same model can perform very differently in different harnesses, as SWE-agent showed with coding tasks. And the harness is the part you can change today.

Interview “An agent dropped a production table. Where was the bug?”

Not “in the model”. The model proposed an action, and the harness let it through. Look for: a tool that was too broad (raw SQL instead of typed operations); no deny or ask rule for irreversible actions; no human approval on destructive operations; credentials with more privilege than the task needed. The fixes are all code: narrower tools, permission rules keyed on reversibility, least-privilege credentials, and a trace that shows exactly which proposal was allowed and why.
