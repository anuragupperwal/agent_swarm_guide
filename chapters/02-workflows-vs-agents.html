Workflows vs agents

Most "agentic" systems that work in production aren't agents. They're workflows: LLM calls wired together by code that decides what happens next. This chapter gives you one question that separates the two, five workflow patterns to reach for first, and a spectrum for placing any system, including your own.

The big idea: who owns the control flow

Every LLM system is a program that calls a model one or more times. The question that sorts these programs is not “how many calls?” or “does it use tools?” It's this: when one step finishes, who decides what happens next?

  • If your code decides, with the order of steps written down before the run starts, it's a workflow. The model fills in each step, but it can't add a step, skip one, or go back.
  • If the model decides, choosing its next action after seeing the result of the last one, again and again until it judges the task done, it's an agent.
Key idea

Workflows are “systems where LLMs and tools are orchestrated through predefined code paths.” Agents are systems where “LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.” (Schluntz and Zhang, 2024.) The test is simple: could you draw the control-flow graph before the run starts? If yes, it's a workflow, however clever each step is.

Neither is “better”. A workflow trades flexibility for predictability: you know its cost, latency and failure points in advance, and you can test each step alone. An agent trades predictability for flexibility: it can handle tasks whose steps you couldn't list ahead of time, but every run can take a different path, at a different cost. Choosing between them is an engineering decision, and you should be able to defend it.

The building block: the augmented LLM

Both workflows and agents are built from the same unit. Schluntz and Zhang call it the augmented LLM: one model call that can use three extensions. Chapter 01's bare model becomes useful once it has these:

retrieval
The model, or your code, asks for relevant text and gets it placed in the context. Retrieval-augmented generation (RAG) is the name for this pattern.
tools
The model writes a structured request (“call search with these arguments”) and your code runs it. Chapter 04 covers the protocol.
memory
Anything that survives past one call: a saved summary, a notes file, a vector store. Chapter 07 covers it.

One augmented LLM call, used once, is already a complete system for many tasks. Everything after this point is about how you combine calls: with fixed code (workflows) or by letting the model pick the next call (agents).

Five workflow patterns

These five come from Schluntz and Zhang (2024). They're worth knowing by name because almost every production LLM system, including many sold as “agents”, is one of them or a mix. For each one, notice what the code fixes and what the model is allowed to decide.

1 · Prompt chaining

Break the task into a fixed sequence of steps. Each LLM call takes the previous call's output as input. Between steps you can put a gate: a programmatic check that the work so far is on track.

Use it when the task splits cleanly into fixed subtasks. You give up some latency for accuracy, because each call has a smaller, easier job. Examples: write marketing copy, then translate it; write an outline, check it, then write the document. It breaks when the right next step depends on what the previous step found. A fixed chain can't change course.

2 · Routing

One LLM call classifies the input. Code then sends it down one of several specialized paths. Each path has its own prompt, tools or even a different model.

Use it when inputs fall into distinct categories that are better handled separately, and the classification is reliable. Optimizing one prompt for every kind of input tends to make it worse at some of them. Examples: customer-service tickets sorted into general questions, refunds and technical support; easy questions sent to a smaller, cheaper model and hard ones to a larger one. It breaks when inputs belong to several categories at once, or the categories blur.

3 · Parallelization

Run several LLM calls at the same time and combine their outputs in code. There are two versions, and they solve different problems.

Use it when subtasks are independent (sectioning, for speed and focus) or when one answer isn't trustworthy enough and several attempts help (voting). Examples: one call answers the user while another screens the request for policy problems; several prompts each review code for a different class of vulnerability; three judges vote on whether content is inappropriate, with a threshold you choose. It breaks when the subtasks depend on each other, or when every vote shares the same blind spot. Three runs of the same prompt are not three independent opinions.

4 · Orchestrator-workers

A central LLM looks at the task, decides at run time what the subtasks are, hands each to a worker LLM call, and then a final step combines the results.

Use it when you can't predict the subtasks in advance. Examples: a coding change whose set of files depends on the request; a research question that needs a different set of searches each time. It breaks when the plan is wrong and nothing notices, because nothing loops back to re-plan; when workers duplicate each other; or when the synthesizer can't reconcile results. Look closely at this pattern. It's your Stage 4.

5 · Evaluator-optimizer

One LLM call generates a response. Another evaluates it against clear criteria and gives feedback. The generator revises using the feedback, and this repeats until the evaluator accepts or a round limit is hit.

Use it when you have clear evaluation criteria and revision measurably helps, as when a human editor's feedback would improve the draft. Examples: literary translation where the evaluator catches lost nuance; a search task that needs several rounds of searching until the evaluator judges the coverage complete. It breaks when the evaluator can't tell good from bad (vague criteria, or the same model grading its own blind spots), and when the round limit is missing, so the loop runs until the budget dies.

Agents: the model owns the loop

Schluntz and Zhang describe agents in one plain line: they “are typically just LLMs using tools based on environmental feedback in a loop.” Each part of that sentence carries weight:

using tools
The model picks an action from an open menu, with arguments it writes itself. It isn't just picking a label for your code to act on.
environmental feedback
The action's result comes back to the model as an observation: a search result, a test failure, a file's contents. This is the agent's “ground truth” for judging its own progress.
in a loop
The model sees the observation and chooses again. It keeps choosing until it decides the task is done, or until a limit your code set stops it.

Put side by side in code, the difference is visible in a handful of lines. This sketch leaves out everything Chapter 03 adds (limits, errors, state), so look only at the shape:

routing workflow (example b)

label = llm.complete(prompt=CLASSIFY, input=ticket).text   # model decides once
return HANDLERS[label](ticket)                            # code decides what follows; run ends

agent (shape only)

messages = [user(task)]
while True:                                        # real code bounds this: Chapter 03
    reply = llm.complete(messages=messages, tools=TOOLS)
    if reply.stop_reason == "end_turn":
        return reply.text                              # model decided it's done
    results = [run(call) for call in reply.tool_calls]  # model picked the action
    messages += [reply, user(results)]               # model sees the result next time

The three highlighted comments are the three things the workflow version doesn't have. In the workflow, the model's output is used once and the program moves on. In the agent, the model's output determines what the program does and what the model sees next, so each decision feeds the next one.

When an agent is the right tool

  • The path can't be written down in advance. You can't predict how many steps it takes, or which, because that depends on what the earlier steps find. Fixing a bug in an unfamiliar codebase is the classic case.
  • The environment gives honest feedback. Tests pass or fail, code compiles or doesn't, a search returns something or nothing. Without a signal like this the agent can't tell whether it's making progress, and it will report success anyway.
  • You trust the model's decisions in this domain, and the cost of a wrong action is bounded: a sandbox, reversible actions, or a human approval on the risky ones.

The autonomy spectrum

“Workflow or agent” is a useful binary, but real systems sit along a line. A better question than “is it an agent?” is “how much of the control flow does the model own?” Andrew Ng has argued for treating “agentic” as an adjective with degrees rather than a yes-or-no label, and Kapoor et al. (2024) describe agentic-ness as a spectrum for the same reason.

Read the third column carefully. It never becomes empty. Even at the far right, your code decides what the model is allowed to do and when it's forced to stop. That's principle 2.2 in your spec, “LLM proposes, framework decides”, written as a table. Moving right doesn't remove the harness. It moves the harness's job from choosing the steps to constraining the chooser.

Your two examples, placed on the spectrum

Back to the two cases from your Round 1 feedback. Check your checkpoint answer against each step.

(a) Send text to an LLM, return the summary

This is a single call, the leftmost point on Figure 2.8. The model decides the words of the summary and nothing else. Nothing it writes changes what the program does next, because there is no next. It's a function that happens to contain an LLM call: summarize(text) → str. Not an agent under any definition.

(b) Classify the request, route to one of three hardcoded handlers

This one is more interesting, because the LLM's output does change what the program does. Your A1 said that if “whatever is obtained from the LLM” can't be “used to act upon”, it's a function. In (b) it is used to act upon: the label picks the handler. So a definition built on “uses the LLM's result to act” puts (b) on the agent side, and that's the problem with it. It lets in every router, and routers are workflows.

(b) is a routing workflow (Figure 2.4). Compared with the agent sketch above, it's missing all three highlighted lines:

  1. No feedback. The model never sees what the handler did. If the refund handler fails, the model doesn't know.
  2. No second decision. The model chooses once, and then the run ends. There's no loop in which its next choice depends on an observation.
  3. No say over stopping. The code ends the run after one handler. The model can't decide “that didn't work, try the other path” or “done”.

A fourth difference is smaller but real: the model chooses from three labels that code interprets, instead of choosing actions with arguments. That's what separates routing from tool use.

A sharper definition

An agent is a program in which a model repeatedly chooses the next action, observes its result, and decides when the task is done, inside limits that code enforces.

Compare it with your A1 word by word. “Deterministic software” describes the harness around the agent, not the agent. “Specialised task” is optional: a general coding agent is still an agent. Your “decision-making loop” was the right instinct. What it needed was feedback (the model sees what happened) and stopping (the model says when it's done). Chapter 03 turns this sentence into a list of minimum parts.

When not to build an agent

The single most repeated piece of advice in Schluntz and Zhang is to start with the simplest thing: “finding the simplest solution possible, and only increasing complexity when needed.” For many applications that's one well-prompted call with retrieval and good examples. Move right on the spectrum only when you can show that the simpler version fails, and say how it fails.

Two more pieces of advice from practice:

  • Measure against a simple baseline. Kapoor et al. (2024) found that on a well-known coding benchmark, simple baselines (such as retrying the same model, or escalating to a stronger one) matched complex agent designs at a fraction of the cost. Their point: report cost alongside accuracy, or the comparison is meaningless.
  • Be careful with frameworks early. They make it quick to start but can hide the actual prompts and responses behind abstractions, which makes failures harder to debug. Schluntz and Zhang suggest starting with direct API calls, because most patterns are a few dozen lines of code. That's also the premise of your project.
Mistakes to avoid
  • “It has a loop, so it's an agent.” An evaluator-optimizer loop is a workflow. What matters is who picks the kind of next step.
  • “It uses tools, so it's an agent.” A chain whose step 2 always calls search is a workflow with a tool in it.
  • Building an agent where a router would do. You pay for flexibility you never use, and you gain new failure modes.
  • Trusting an orchestrator's plan without checking it. The plan is model output. Validate it (Chapter 01, Figure 1.4) before you spend money on workers.
  • Treating votes as independent. The same prompt to the same model fails in correlated ways. Voting reduces random errors, not systematic ones.
  • Leaving out the round or step limit because “the model will stop when it's done.” Sometimes it won't.

Recall In one sentence, what separates a workflow from an agent?

Who decides the next step. In a workflow, code fixes the steps and their order before the run. In an agent, the model chooses each next action after seeing the result of the last one, and decides when it's done, within limits that code enforces.

Recall Sectioning and orchestrator-workers both fan out to parallel LLM calls. What's the difference?

In sectioning, the list of subtasks is written in code (“check facts, check tone, check policy”). In orchestrator-workers, an LLM writes the list at run time, so the number and content of subtasks change per input. Both are still workflows: plan once, run, merge.

Apply Place each on the spectrum: (1) extract fields from an invoice into JSON; (2) generate SQL, run it, and on an error send the error back to the model to fix, up to 3 times; (3) a model with a shell that fixes a failing test in a repo it's never seen.

(1) Single call, maybe with a validation gate. (2) An evaluator-optimizer loop with the database as the evaluator. It's a workflow: the only choice the model gets is how to fix the query, never what kind of step to take next. (3) An agent. The steps depend on what it finds, the tests give honest feedback, and it decides when it's done.

Apply What's the smallest change that turns example (b) into an agent?

Expose the handlers as tools. Send each handler's result back to the model, and let the model choose another action or finish. Add a step limit in code. Those changes add feedback, repeated decisions and model-decided stopping. Without the step limit, it's an agent with no brakes.

Design A support bot handles FAQs (80% of traffic) and refunds (20%, which need order lookup and a policy check). Sketch the design.

A router first. FAQs go to a single call with retrieval on a small model. Refunds go down a workflow: look up the order, then a policy check in code, then a draft reply. Agent behaviour is justified only if refunds really need open-ended investigation, and even then the action that moves money should need approval. The design follows the traffic: the cheap path serves the most requests.

Interview “When would you not use an agent?”

When the steps are known in advance; when there's no honest feedback signal; when errors are costly or irreversible; when cost or latency must be predictable per request; when a simple baseline already works. Then say what you'd do instead (the matching workflow pattern) and how you'd find out you need more: measure the simpler version's failures first.

Interview “Is orchestrator-workers an agent?”

As usually described, no. The orchestrator plans once, the pipeline (plan, then workers, then merge) is fixed, and nothing loops back. It becomes agentic when the orchestrator sees the workers' results and decides what to do next: re-plan, spawn more work, or finish, in a loop. That's the step from your Stage 4 to Stage 5, and it's worth saying so explicitly.
