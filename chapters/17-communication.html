Communication and coordination

So far, information in your tree has moved in only two directions: a task goes down to a child, and a result comes back up. This chapter is about everything else: agents talking sideways, waiting on each other, sharing a workspace, and agreeing. Every channel you add is a new way for the system to work, and a new way for it to fail.

First question: do you need agents to talk at all?

In a pure orchestrator-worker tree (Chapter 16), children never talk to each other. The parent writes a task, the child runs in isolation, and the child returns one result. That design is simple for a reason: an isolated child can't be confused, delayed or poisoned by a sibling. Its trace reads top to bottom. Its failure stays inside its own branch.

Messaging between agents breaks that isolation on purpose. It is worth it only when one of these is true:

  • Information is needed during a sibling's run, not after it. Waiting for the parent to collect results and re-plan would be too slow or too late.
  • Work would be duplicated because siblings can't see what the others have already claimed or found.
  • Work has to be negotiated: who is free, who is best suited, who takes which piece.
  • An agent lives longer than one task: a service agent (a reviewer, a librarian) that many others query.

Most of the time, there is a cheaper option than messaging:

Re-plan between waves

Children run, return, and the parent reads all results and spawns the next wave with better tasks. The information still flows, just once per wave.

A shared artifact store

Children write findings to named files or keys. Later children read them. There's no conversation, only a written record.

Better decomposition

If two siblings keep needing each other, the split was wrong. Give the overlap to one child, or make the subtasks disjoint.

Stage 7 gate

Before you write any messaging code, write one sentence in your notes: “My demo task needs agents to exchange information during their runs because …”. Name the concrete task. If the sentence ends with “it would be cool” or “real swarms do it”, build one of the three cards above instead and come back when a trace shows you need more.

Two ways to share information

There are only two basic ways for concurrent workers to share information. Every pattern in this chapter is one of them, or a mix.

Shared state
Everyone reads and writes one place: a dict, a file, a database table. Nobody sends anything to anybody. Coordination is implicit: you see what others did by looking at the shared place.
Message passing
Each agent owns its state privately. The only way to influence another agent is to send it a message, which lands in its inbox. All sharing is explicit, and every interaction is visible as an event.
Shared stateMessage passing
CouplingAgents depend on the store's layout, not on each otherAgents depend on each other's addresses and message types
Typical bugLost update, stale read, check-then-act raceDeadlock, lost or duplicated message, unbounded inbox
VisibilityYou see the latest state, not who changed it (unless you log writes)Every interaction is an event with a sender and a time
Context costAn agent reads only what it asks forEvery delivered message lands in the receiver's context
Good forAccumulating facts, claiming work, final artifactsQuestions, negotiation, handing off control

The Go community has a proverb for this: “Don't communicate by sharing memory; share memory by communicating.” The idea is much older. Carl Hewitt's actor model (1973) describes a system made of actors that share nothing. An actor can do only three things when a message arrives: send messages to actors it knows, create new actors, and decide how to handle its next message. An LLM agent with an inbox is very close to an actor. The main difference is that each “handle a message” step costs a model call.

Key idea

In a single asyncio process, “shared state” and “message passing” are both just Python objects in one memory space. The difference is a discipline you impose: who is allowed to touch what, and whether every interaction leaves an event in the trace. Pick the discipline first, then the data structure.

Mailboxes and queues

A mailbox (inbox) is a queue owned by one agent. Others put messages in; only the owner takes them out. In asyncio this is asyncio.Queue, and its behavior is worth knowing exactly:

await q.put(m)
Adds a message. If the queue was created with maxsize and is full, the sender waits until there is room. That waiting is backpressure: a slow receiver slows its senders down instead of growing without limit.
q.put_nowait(m)
Adds without waiting. Raises asyncio.QueueFull if the queue is full, so the sender must decide what to do: drop it, retry later, or report an error.
await q.get()
Takes the oldest message, waiting if the queue is empty. An agent awaiting get() uses no CPU and no tokens.
q.get_nowait()
Takes a message or raises asyncio.QueueEmpty. Useful for “drain whatever is there, then continue”.
q.task_done() / await q.join()
A counter of finished items. join() returns when every item put has been marked done. Handy for “wait until all work is processed”.

Now the question that matters for an LLM agent: when does the agent read its inbox? A model call can't be interrupted halfway to insert a message. So the inbox is read at step boundaries, between one model call and the next:

An agent loop with an inbox (pseudocode)

async def run(self):
    while not self.done():
        response = await llm.complete(self.context, tools=self.tools)
        self.context.append(response)
        for call in response.tool_calls:
            result = await self.execute(call)        # may include send_message(...)
            self.context.append(result)
        for msg in self.inbox.drain(limit=5):       # bounded: messages cost tokens
            self.context.append(as_user_block(msg))

Three consequences follow from that one highlighted line:

  • Latency. A message sent now is seen only after the receiver's current model call (and tool runs) finish. That can be tens of seconds. Messaging between LLM agents is slow by design.
  • Token cost. Every delivered message becomes part of the receiver's context and is re-sent on every later call (the n² growth from Chapter 01). Ten chatty siblings can fill each other's windows with noise.
  • Trust. A message from another agent is text the receiver will read as instructions. It can carry a prompt injection that one agent picked up from a web page (Chapter 12). Mark messages clearly as coming from a peer, and never give peer messages the authority of the system prompt.
Pitfall

An unbounded asyncio.Queue() (the default, maxsize=0) never applies backpressure. If one agent produces messages faster than another reads them, memory and the receiver's future context both grow without limit, and nothing complains. Set a maxsize, and decide in advance what happens on QueueFull.

Request/reply vs fire-and-forget

Once agents can send messages, every send is one of two kinds. Either the sender needs an answer before it can continue (request/reply), or it doesn't (fire-and-forget, also called a notification).

Request/reply over a queue needs one piece of machinery: a way to match each reply to the request that caused it. A sender may have several requests in flight, and replies can arrive in any order. The standard answer is a correlation id plus a table of pending futures:

Request/reply on top of a message bus (pseudocode)

pending: dict[str, asyncio.Future] = {}

async def request(to, content, timeout=30):
    msg = Message(type="request", to=to, content=content, msg_id=new_id())
    fut = asyncio.get_running_loop().create_future()
    pending[msg.msg_id] = fut
    await bus.send(msg)
    try:
        return await asyncio.wait_for(fut, timeout)       # a hang becomes TimeoutError
    finally:
        pending.pop(msg.msg_id, None)                 # no leak, even on timeout

def on_reply(msg):                                   # called by the bus for type="reply"
    fut = pending.get(msg.correlation_id)
    if fut and not fut.done():                      # late replies are dropped
        fut.set_result(msg.content)

Read it line by line. The future is a placeholder for “the answer, later”. wait_for is the single parameter from your Predict question 2: without a timeout, a reply that never comes means this coroutine waits forever, silently. With a timeout, the wait becomes a TimeoutError your harness can log and handle. The finally clause removes the pending entry whether the reply came, the timeout fired, or the task was cancelled.

Delivery guarantees

Inside one Python process, a put that succeeds really does deliver. Across processes or machines it doesn't, and distributed-systems vocabulary becomes useful:

GuaranteeMeaningWhat the receiver must do
At-most-onceSend once, never retry. A message can be lost, never duplicated.Nothing, but accept losses.
At-least-onceRetry until acknowledged. Nothing is lost, but duplicates happen.Be idempotent: skip a msg_id it has already processed.
“Exactly-once”Not achievable as pure delivery over an unreliable network.Build it as at-least-once delivery plus idempotent processing.

Duplicates hurt LLM agents more than ordinary services. A duplicated “please research X” message costs a full sub-run of tokens, and it may produce a second, slightly different answer that someone then has to reconcile.

Addressing, discovery and the message schema

To send a message, the sender must name a receiver. There are three ways to do that, from simple to flexible:

Direct address
The sender knows the receiver's id (agent-7). Simple and traceable. It only works when the sender already knows who exists, which in a tree usually means a parent addressing its own children.
Registry lookup
A registry maps ids to live agents, along with their role and status. A sender asks “who is reviewer?” and gets an id. Your Stage 3–5 agent registry is already most of this.
Capability lookup
The sender asks “who can do SQL review?” and the registry matches a description of the need against descriptions of what each agent offers. Flexible, and also where things go wrong, because matching text to text is fuzzy. A2A's agent cards (later in this chapter) are a standard version of this.

Whatever the addressing, define the message as a data structure, never as free text. Here is one possible shape. Treat it as a menu of fields to consider, not a standard:

One message on the wire (JSON)

{
  "msg_id": "m-0193",
  "run_id": "run-2026-11-16-a",
  "from": "agent-4",
  "to": "agent-7",
  "type": "request",
  "performative": "query",
  "correlation_id": null,
  "reply_to": "agent-4",
  "topic": null,
  "content": { "question": "Which retry policy did you find for 429s?" },
  "sent_at": "2026-11-16T10:42:07Z",
  "ttl_s": 60,
  "hop_count": 1
}
msg_id
Unique per message. Used for deduplication and as the target of a reply's correlation_id.
run_id
Which run this belongs to, so a stray message from a previous run can be rejected.
from / to
Sender and receiver. The harness sets from, never the model, so an agent can't impersonate another.
type
The harness's routing category: request, reply, notify, handoff. Code branches on this.
performative
What the sender intends: asking, telling, proposing, refusing. Covered under speech acts below.
correlation_id / reply_to
On a reply, the msg_id it answers. On a request, where the reply should go.
topic
For publish/subscribe: the channel name instead of a receiver.
content
The payload. Give it a schema per message kind and validate it like any model output.
ttl_s / hop_count
Safety fields. A message older than its TTL is dropped. A message that has been forwarded too many times is dropped. These two fields stop stale messages and endless forwarding loops.
Key idea

The model decides what to say. The harness decides everything else: the id, the sender, the timestamp, whether the receiver exists, whether the sender is allowed to reach it, and whether the content passes validation. A message is one more model proposal, and it gets checked like a tool call.

Four channel patterns

Chapter 15 covered topologies: the shape of who talks to whom. Underneath every topology sits one or more of these four channel patterns.

Publish/subscribe

A publisher posts to a named topic. Anyone subscribed to the topic receives a copy. The publisher doesn't know, or care, who is listening. That decoupling is the point: you can add a new listener (a logger, a monitor, a summarizer) without changing any sender. Broadcast is the extreme case: one topic that every agent hears. Broadcast is the easiest way to multiply token cost, because one message lands in n contexts.

The blackboard

The blackboard architecture comes from the Hearsay-II speech-understanding system (Erman et al., 1980). Independent specialists, called knowledge sources, watch a shared, structured workspace. Each one adds a contribution when it can, building on what others posted. A control component decides which knowledge source gets to act next. For LLM agents, the blackboard is the natural home for three kinds of entries:

  • Facts: findings with their source and the agent that found them.
  • Claims: “agent-5 is working on subtopic X”, with an expiry time, so others skip X. A claim that expires is called a lease: if agent-5 crashes, the claim lapses and someone else can take X.
  • Open questions: things one agent needs and hopes another can answer.

A blackboard is shared state, so it inherits shared state's bugs. The classic is check-then-act: agent A checks that X is unclaimed, awaits something, then claims X. Meanwhile B did the same check. Both claim X. In a single asyncio event loop the fix is simple: make the check and the write a single function with no await between them, so no other coroutine can run in the gap (Chapter 10).

Handoffs vs delegation

These two are easy to blur, and the difference decides who owns the result:

Delegation (your Stage 5–6 tree)

The parent spawns a child, waits, and gets a result back. The parent stays in charge and keeps its own context. Control returns to the caller, as with a function call.

Handoff

The current agent transfers the conversation to another agent and stops. The new agent talks to the user from then on. Nothing comes back. Control moves sideways, as with a goto. This is the core move in OpenAI's Swarm (Chapter 18).

Same shape, different cause

This is the same n(n−1)/2 that appears in Chapter 01's token growth and in Brooks's law about adding people to a late software project. Pairwise communication grows quadratically whenever any member may talk to any other.

Coordination failures: deadlock, livelock, ordering, duplicates

Once agents can wait on each other, they can wait on each other in a circle. This section covers the four classic coordination failures, each with the signal it leaves in a trace.

Deadlock

A deadlock is a set of agents in which each one is waiting for another one in the set. Nobody can move, so nobody ever will. Coffman, Elphick and Shoshani (1971) showed that a deadlock needs four conditions to hold at the same time. Break any one and deadlock becomes impossible.

Agent harnesses rarely deadlock through messages alone. The more common version comes from a concurrency limit. Here is a bug that is easy to write in a recursive harness:

A deadlock with no messages at all (pseudocode)

sem = asyncio.Semaphore(2)            # "at most 2 agents running at once"

async def run_agent(task):
    async with sem:                     # holds a slot...
        children = await plan(task)
        await asyncio.gather(*(run_agent(c) for c in children))
        # ...while waiting for children that each need a slot

Walk it through. The root takes slot 1. It spawns three children. Child 1 takes slot 2. Children 2 and 3 wait for a slot. Child 1 plans and spawns grandchildren, which also wait for a slot. Now the root holds a slot while it waits for its children, and child 1 holds a slot while it waits for its children. No slot will ever free up. The program doesn't crash, use CPU or print anything. It just stops. That is the hold-and-wait condition in Figure 17.4. Ask yourself which part of an agent's life actually needs to be limited: the whole lifetime, or only the model calls and tool runs?

Pitfall

A deadlocked asyncio program is silent. With no timeouts, the only symptom is a trace that stops growing while tasks are still pending. Add a watchdog: if no event has been recorded for T seconds and tasks are still alive, dump every pending task with asyncio.all_tasks() and fail the run.

Livelock

In a livelock, everyone is busy and nothing progresses. With LLM agents, livelock often looks like politeness:

Trace · two siblings with peer messaging
harness
agent-2 and agent-3 have overlapping scope: pricing + features. Peer messages on.
agent-2
→ agent-3: You take pricing, I'll take features.
agent-3
→ agent-2: You found the pricing page first, so you should take pricing. I'll do features.
agent-2
→ agent-3: Good point, but you have more context on pricing. Let's swap: I do features, you do pricing.
agent-3
→ agent-2: Happy to adapt! You do pricing, I'll do features.
harness
8 messages · 0 tool calls · 0 findings · 11% of budget used. Nobody is blocked. Nothing is done.

Compare the two signals. Deadlock: the event count stops rising. Livelock: the event count rises, but the progress count (tool calls that return new information, findings, completed subtasks) stays flat. You can only detect livelock if you count progress separately from activity. The fixes are the same as for any symmetric conflict: a deterministic tie-break (“lower id wins”), randomized backoff (Chapter 11), a cap on messages per pair, or, best of all, a parent that assigns disjoint scopes so the negotiation never starts.

Ordering

One asyncio.Queue is first-in, first-out. But a receiver with several senders has no guarantee about the relative order of their messages. B can receive A's message after C's, even if A sent first. Across processes it gets worse, because messages can be delayed or reordered on the way. If order matters, give each sender a sequence number. When you need causal order across many agents, look up Lamport clocks (Lamport, 1978). Also expect replies to arrive late, after the requester has timed out and moved on. The on_reply code above drops those on purpose.

Duplicate work

The most common coordination failure in research swarms isn't dramatic at all. Two siblings get overlapping tasks, both search the same sources, and both return the same facts. You pay twice, and the aggregator has to merge near-duplicates. Anthropic's write-up of its multi-agent research system names exactly this: early versions had subagents duplicating each other's searches until the lead agent's task descriptions became more specific. There are three places to prevent it:

  • At decomposition (best): the parent writes disjoint subtasks with explicit boundaries (“cover 2020–2023 only; another agent covers 2024”).
  • During the run: claims with leases on a blackboard, so a sibling can see that a source or subtopic is taken.
  • At aggregation (last resort): deduplicate findings by source URL or content hash before synthesis.

Consensus and voting

Sometimes the question isn't who does what, but what is true. Several agents answer, and the system has to settle on one answer. The common methods:

Majority vote
Run k agents (or one agent k times) and take the most common answer. This is self-consistency (Chapter 05) spread across agents. It only works when answers can be compared, such as a number, a label or a choice.
Judge
A separate agent reads all answers and picks or merges. It carries every LLM-as-judge bias from Chapter 13: position, length, self-preference.
Debate
Agents see each other's answers and revise over several rounds. Chapter 18 covers what the evidence says.

Voting is powerful only when the voters' errors are independent. Work it through with three voters that are each right 80% of the time:

independent errors:  P(majority right) = p³ + 3p²(1−p) = 0.512 + 0.384 = 0.896
perfectly correlated errors:  P(majority right) = p = 0.80
same model, same prompt, same context → errors are strongly correlated → closer to the second line

Three copies of one model reading the same misleading source tend to make the same mistake. So a vote among them mostly measures how confident the model is, not whether it's right. To get closer to independence, vary something that matters: different sources, different decompositions, different prompts, or different models.

Two meanings of “consensus”

In distributed systems, consensus algorithms such as Paxos and Raft make replicas agree on one value despite crashes and lost messages. They guarantee agreement, not correctness: all replicas can agree on a wrong value. The Byzantine generals problem (Lamport, Shostak and Pease, 1982) adds participants that lie, and shows you need more than three times as many participants as liars. When people say LLM agents “reach consensus”, they mean something much weaker: opinions are aggregated. Don't let the word borrow the guarantees.

Speech acts: typing the intent of a message

Philosophers noticed long before computers that saying something is often doing something. “I promise”, “I request”, “I refuse” are actions, not descriptions (J. L. Austin, 1962; John Searle, 1969). Speech act theory separates a message's content (what it is about) from its force (what the speaker is doing with it).

Multi-agent systems research of the 1990s turned this into protocols. KQML (Finin et al., 1994) and then FIPA ACL (standardized around 2000–2002) gave every message a performative: a word from a fixed list, about twenty in FIPA's case, naming the act. Neither saw wide industrial use. They came with formal semantics about agents' beliefs and intentions that real programs couldn't check, and they assumed shared ontologies that were expensive to build.

LLMs remove the ontology problem, because the content can be plain language. The performative is still worth keeping, because it lets code route a message without having a model read it first:

requestasking the receiver to perform an actiontreat as a task: check permission and budget first
query-refasking for a valueopen a request/reply with a timeout
agree / refuseaccepting or declining a requesta refusal is an explicit answer, not a silence to time out on
failurereporting that an attempted action failedan error returned as data (Chapter 11)
not-understoodsaying the last message made no sensea validation error to return to the sender

Key idea

Free text is fine for content. Intent should be an enum. “Did B refuse, fail, or just not answer yet?” is a question your harness must be able to answer without calling a model.

The contract net protocol

Reid Smith's contract net protocol (1980) is the classic way to allocate tasks by negotiation instead of assignment. It has four steps, and you'll recognize your own recursive tree inside it: any contractor can become a manager for subtasks of its own.

Contract net is elegant, and it maps onto LLM agents with one serious catch: a bid is a self-report. If an LLM agent bids “I can do this well in 2 minutes”, that number is generated text. Models tend to be overconfident about their own abilities, and every agent will happily say it's a good fit. A market where every bidder is optimistic just picks whoever is most optimistic.

The fix is to bid on things the harness can measure: which tools an agent actually has, how much budget it has left, its current queue length, whether it already holds relevant context or cached sources, and its past success rate on similar tasks from your evaluation logs. Let the model write the proposal text. Let code compute the score.

Standard protocols: MCP and A2A

Two open protocols now cover the two directions an agent can connect. They are often mentioned together, and they solve different problems.

Do you need either one?

For agents inside one Python process, no. Your message bus is a dict of queues, and a protocol would add serialization and network failure modes you don't have yet. The protocols matter at boundaries: when tools live in another process or team (MCP), or when an agent belongs to another organization (A2A). The concepts are worth stealing either way: typed tasks with explicit states, self-descriptions that can be discovered, and outputs as named artifacts.

Misconceptions to drop
  • “More communication means better coordination.” Each channel adds latency, tokens and failure modes. Most good multi-agent systems talk very little.
  • “The agents will sort out who does what.” Without a tie-break or an assigner, they negotiate politely forever (livelock) or both do it (duplicates).
  • “A hang means something crashed.” In asyncio a hang usually means a wait with no timeout, often in a cycle.
  • “Three agents agreeing means it's right.” Agreement among copies of one model mostly measures shared bias.
  • “We need A2A to build a swarm.” Only across process or organization boundaries. In one process, a dict of queues is enough.
In your swarm harness
  • Stage 7, the gate. Write the one-sentence justification from the top of this chapter before any code. Then decide: does your need look more like a blackboard (facts and claims) or like direct messages (questions and answers)? What would the trace of your demo look like under each?
  • Stage 7, the message type. Go through the schema fields above. Which ones does your harness set, and which, if any, does the model get to set? What stops agent-4 from writing "from": "root"?
  • Stage 2 and 7, tracing. Is a sent message one trace event or two (sent, delivered)? What do you need to be able to tell, afterwards, that a message was delivered but never read?
  • Stage 5–6, concurrency. Look at the semaphore example. Does your concurrency limit cover an agent's whole life, or only its model and tool calls? Write a test with a limit of 2 and a tree of depth 2 that must either finish or fail within a few seconds. What does it show?
  • Budgets. When agent-3 sends a message that agent-5 then reads on five later calls, whose budget pays for those tokens? Is your answer something your code can actually enforce?

Check yourself

Answer each one out loud or on paper before you open it.

Recall Name a typical bug of shared state and a typical bug of message passing. What does each look like in a trace?

Shared state: a lost update or a check-then-act race. Two agents write the same key and one write vanishes, or both claim the same subtask. In a trace you see two writes or claims for the same key close together, and the earlier one has no effect. Message passing: a deadlock, a lost message, or an unbounded inbox. In a trace you see a request with no matching reply (or a timeout), or an inbox length that keeps growing.

Recall What is a correlation id for? In the request/reply code above, what happens to a reply that arrives after the timeout?

It ties a reply to the request it answers, so a sender with several requests in flight can resolve the right future. After a timeout, the finally clause has already removed the pending entry, so on_reply finds nothing and drops the late reply. That is deliberate: the requester has moved on, and resolving a stale future would be a bug.

Apply Twelve agents. How many channels in a full mesh, and how many in a star? What is the ratio?

Mesh: 12·11/2 = 66. Star: 11. The ratio is 6, which is n/2. Doubling to 24 agents gives 276 vs 23, a ratio of 12.

Apply For five minutes, your trace's event count keeps rising, but no new findings or completed subtasks appear. Deadlock or livelock? What do you check next?

Livelock. A deadlock would show the event count stopping. Next, group the recent events by type and by agent pair. A cluster of messages between the same two agents with no tool calls points to a negotiation loop. A single agent repeating the same tool call points to a single-agent loop (Chapter 11). The fix is a tie-break, a per-pair message cap, or reassigning scopes from the parent.

Apply Explain why the semaphore example deadlocks, using Coffman's conditions. Give two different fixes.

Each agent holds a slot (mutual exclusion) while waiting for children that need slots (hold and wait). Nothing can take a slot back (no preemption), and parents wait on children that wait on the parents' slots to free up (a circular dependency through the shared pool). Fixes: acquire the semaphore only around model and tool calls, not around the whole agent lifetime, which breaks hold-and-wait. Or add a timeout to slot acquisition and fail the spawn, which breaks no-preemption. Separate limits per depth also work.

Design You implement contract net, and LLM agents bid with a self-rated fit score from 1 to 10. What goes wrong, and how would you redesign the bid?

Self-ratings are generated text. They're overconfident and similar across agents, so the auction picks whoever writes the most confident number. Redesign the bid so that code computes the score from measurable facts: the tools the agent actually has, its remaining budget, its queue length, whether it already holds relevant context, and its past success rate on similar tasks. The model can still write a short plan as part of the proposal, but the plan doesn't set the score.

Interview “What's the difference between MCP and A2A, and would you use them inside a swarm harness?”

MCP connects an agent to tools and data. Servers expose tools, resources and prompts over JSON-RPC, and the host sees every schema and result. A2A connects an agent to another agent it treats as opaque: discovery through an agent card, then tasks with states, messages and artifacts. Inside one process I'd use neither for internal messaging. A plain bus is simpler and has fewer failure modes. I'd use MCP to plug external tool servers into the tool registry, and A2A only if a child had to be an agent owned by another team or organization.

Interview “Our orchestrator-worker system works. Product wants workers to message each other directly. How do you respond?”

Start with the need: which information has to move between workers during their runs, and why the orchestrator re-planning between waves isn't enough. Check the cheaper options first: better decomposition, or a shared findings store. If peer messaging is still justified, scope it narrowly: specific message types, a cap per pair, timeouts on every wait, harness-set sender ids, peer messages treated as untrusted input, and trace events for send, deliver and read. Then measure against the current system on cost, latency and quality. Expect the number of possible channels to grow from n−1 to n(n−1)/2.

Recall card

Five lines to rehearse. If you can expand each into a minute of explanation, you know this chapter.

  1. Add sideways communication only when information is needed during a sibling's run. Re-planning, a shared store or better decomposition is usually cheaper.
  2. Shared state fails by lost updates and races. Message passing fails by deadlock, lost or duplicated messages and unbounded inboxes.
  3. Request/reply needs a correlation id, a future and a timeout. Without the timeout, a missing reply is a silent hang.
  4. Deadlock means no events. Livelock means events without progress. Count progress separately from activity.
  5. A mesh has n(n−1)/2 channels and a star has n−1. Votes among copies of one model share their errors. MCP goes down to tools; A2A goes across to opaque agents.
