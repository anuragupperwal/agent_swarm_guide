Observability and evaluation

An agent run doesn't repeat itself: the same input can take a different path next time. So you need two things. A trace that lets you reconstruct exactly what happened in one run, and an evaluation that tells you what happens across many. This chapter builds both, from the record format up.

The big idea

With ordinary code, you debug by reproducing the bug: run it again with the same input and watch. With an agent, that doesn't work. The same input can lead to a different trajectory, and the failure you're chasing may not happen again for twenty runs. And with a swarm, twelve agents interleave their work, so even a perfect log of each one doesn't show you how they affected each other.

So the strategy changes in two ways:

Observability: record enough during every run that you can reconstruct it afterwards, without running it again. The record is the reproduction.

Evaluation: stop judging the system by single runs. Run each task many times and measure rates, spreads and costs.

Key idea

A trace tells you what happened once. An eval tells you what happens in general. You need both, and they share one foundation: a structured event record written by the harness, not by the model. If the record is good, every metric, every debugging session and every eval in this chapter can be computed from it.

Logs, metrics and traces

These three are usually called the pillars of observability. They aren't three tools. They're three views of the same events, each answering a different question.

LogsMetricsTraces
ShapeOne record per eventCounters, gauges, histogramsA tree of spans per run
Agent examples“child-2 called search”, “validation failed: field subtasks”Tokens per run, p95 model latency, retry rate, failure rate by kindRoot → children → model and tool calls, with timing and parent links
Good forDetail of one stepTrends, alerts, comparisons across runsCausality and latency inside one run
Weak atShowing structure. Interleaved lines from 12 agents are hard to read.Explaining a single caseAggregates, unless you compute them from many traces

That's predict question 1. Interleaved print output tells you what each agent said, but not which agent caused which, how long each step waited, or where the tokens went. You can't recover structure that was never recorded.

Traces and the span model

A trace is the record of one run. It's built from spans. A span is one unit of work with a start and an end: an agent's whole lifetime, one model call, one tool call. Every span has:

Identity
A trace id (shared by every span in the run) and a span id (unique to this span).
A parent
The span id of the span that caused this one. The root span has none. These parent links turn a flat list of spans into a tree.
Timing
Start and end timestamps. The duration is what the waterfall in Figure 13.2 draws.
Attributes
Key-value facts: model name, token counts, tool name, stop reason.
Status and events
Whether it succeeded, plus point-in-time events inside it, such as “retry 2 after 529”.

Reading a waterfall is a skill worth practicing. Start with the root's duration. Find the child whose end lines up with the next thing the root does: that's the critical path. Then look inside it for gaps, retries and long single calls. Shortening any span that isn't on the critical path doesn't make the run faster. Here, speeding up child C would save nothing.

Tracing a spawn tree

In a swarm harness, the span tree and the spawn tree are the same tree. Every agent is a span. Its parent span is the agent that spawned it. Its model and tool calls are child spans inside it. If each record carries the right ids, the whole run can be rebuilt from a flat file of events.

Your Stage 1 plan already names six fields for each JSONL event. Here's how they line up with the span model, and what each one makes possible:

Your fieldSpan-model equivalentWhat it lets you compute
run_idtrace idEverything from one run, and comparisons between runs
agent_idspan id of the agent's spanWho did this
parent_idparent span idThe tree: depth, fan-out, which branch spent what
eventspan name, or an event inside a spanFiltering and counting: retries, failures, spawns
tsstart and end timesOrdering and durations, but only if you can pair a start with its end
tokensusage attributesCost and budget checks, per agent and per branch

Look at the last two rows closely. A single ts per event gives you ordering, but a duration needs two timestamps that you can match up, so a model call needs either start and end events with a shared call id, or one event that records both times. And a single tokens number hides the split between input and output tokens, which are priced differently and grow differently (ch01). Neither is wrong for Stage 1, but you should decide it on purpose.

The other practical problem is propagation: how does code deep inside a child know its own agent_id and its parent's, without passing them through every function? In Python's asyncio, a new task gets a copy of the current contextvars context when it's created. A context variable set just before spawning a child task is therefore visible inside that task, and changing it inside the child doesn't affect the parent. That's the same mechanism tracing libraries use.

The OpenTelemetry GenAI conventions

OpenTelemetry (OTel) is the vendor-neutral open standard for traces, metrics and logs. Its semantic conventions define standard names for attributes, so that any OTel-compatible tool can display your data without custom parsing. There's a set of conventions specifically for generative AI. It covers spans for model calls, with attributes such as gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens and gen_ai.response.finish_reasons, and has been extended to agent operations such as invoking an agent and executing a tool, named by a gen_ai.operation.name attribute.

Note

The GenAI conventions were still marked as in development when this guide was written, and some attribute names have already changed between versions. Treat the names above as examples of the shape, and check the current specification before you depend on any of them.

For your project, the sensible order is: write your own JSONL format first, because you'll learn more by deciding each field yourself. If the fields map cleanly onto spans, exporting to OTel later is a translation step, not a redesign. If they don't map cleanly, that's a sign the record is missing structure, usually a parent link or a paired start and end.

What to record

The test for a good record is simple: could someone who wasn't there explain this run from the record alone? That needs these events at minimum:

EventWorth recordingAnswers
Run start and endTask, config, limits; final status and totalsWhat was asked, under what rules, and how it ended
Agent start and endTask text, depth, budget granted; status, error kind, usageWho did what, and how it went
Model callModel, input and output tokens, latency, stop_reason, attempt numberWhere time and money went
Tool callTool name, arguments (redacted), duration, is_errorWhat the agent actually did in the world
Spawn proposed, granted or rejectedRequested vs granted capabilities, and the reason for any rejectionHow the tree got its shape (ch11, ch12)
Control eventsValidation failed, retry, limit hit, breaker openedWhere the harness stepped in

Full prompts and responses are the most useful data for debugging and the worst to put in every event line: they're large, and they contain whatever sensitive data the agent read. A common pattern is to store them in a separate content store, keyed by a hash, and put only the hash in the event. You need the full content anyway for replay (ch09) and for the trajectory evaluations later in this chapter. Scrub secrets before writing either one (ch12).

Common pitfall

Recording what the model says instead of what happened. “I've used about 3,000 tokens and searched twice” is model output, and it can be wrong. Token counts come from the API's usage field. Tool calls are recorded by the executor that ran them. Status comes from your harness. The record is ground truth only if the harness writes it.

Metrics then come almost for free, as aggregations over the event records: tokens and cost per run, per agent and per depth; p50 and p95 latency for each kind of call; retry rate; failure rate by error kind; agents per run; how often each limit fires. When a metric looks wrong, the run_id takes you straight to the trace.

In your swarm harness
  • Stage 1. From your six fields alone, can you compute (a) the tree, (b) each agent's duration, (c) the critical path, and (d) the cost of each branch? For each one you can't, name the field that's missing.
  • Stage 3. Many tasks will write to one JSONL file. In a single event loop, can two lines get mixed together? Reason it through from ch10: where are the await points in your write?
  • Stage 6. Your plan includes a cost report. Make it a pure function of the trace file, with no other input. What does that requirement force you to record?

Outcome, trajectory and component evals

Now the second half: evaluation. The first question is what you grade, because one run offers three different things to grade.

Outcome

Compare the final result with a reference answer or a rubric. This is the level users care about. Its weakness: it can't tell you why a run failed, and it passes a run that got the right answer by a lucky or wasteful path.

Trajectory

Grade the path, using the trace. You can match it exactly against a reference path, which is brittle because there are usually many valid paths, or you can check properties: no forbidden tools, at most N steps, validation before every write, no repeated calls.

Component

Test one step in isolation with a fixed input. Given this task, does the planner produce a valid plan? Does the router choose the right branch? Fast and cheap, and good for catching regressions. Real traces are the best source of inputs.

Graders: code, model, human

Once you know what to grade, you need something to do the grading. There are three kinds of grader, and a good eval suite uses all three, each where it's strongest.

GraderHow it worksStrengthsWeaknesses
CodeExact match, unit tests, schema checks, regex, numeric tolerance, trace queriesFast, cheap, deterministic, unbiasedOnly works when “correct” can be written down precisely
LLM as judgeA model scores an output against a rubric, or compares two outputsHandles open-ended output, and scalesBiased, non-deterministic, and must be checked against human judgment
HumanPeople label outputs or compare pairsThe best judge of subjective quality, and the definition of ground truthSlow, expensive, and people disagree with each other too

Use code wherever you can. A surprising amount of agent behavior can be checked by code: did the tests pass, does the file exist, is the JSON valid, did the trace contain a forbidden call. Use a model as judge for the qualities code can't capture, such as whether the explanation is clear or the design is sound. Use humans to build the reference labels, and to check the model judge.

The biases of a model judge

Zheng and colleagues studied LLM judges in detail in 2023, in the paper that introduced MT-Bench and the Chatbot Arena. They found strong judges agreed with human preferences about as often as humans agreed with each other, and they also documented systematic biases:

BiasWhat happensMitigation
PositionIn a pairwise comparison, the judge favors one position, often the first answer, regardless of contentJudge both orders. Count a win only if it holds in both.
VerbosityLonger answers score higher, even when they add nothingA rubric that rewards concision. Compare answers of similar length.
Self-preferenceA judge favors outputs written by itself or by similar modelsUse a judge from a different model family. This is predict question 3.

Two more practices make a model judge much more reliable. First, prefer several pass or fail checks, one per criterion (“cites at least two sources”, “states the trade-off”), over a single score from 1 to 10. Scores in the middle of a scale drift from run to run. Second, calibrate before trusting it: grade 30 to 50 outputs yourself, run the judge on the same outputs, and measure how often you agree. If agreement is poor, fix the rubric before you trust a single number from it.

Key idea

A grader is a model of your judgment, and it needs testing like any other model. An eval built on an unvalidated judge measures the judge's preferences, not your system's quality.

pass@k vs pass^k

Because runs vary, “does it pass?” has no single answer. Two metrics turn the variation into numbers, and they answer opposite questions. Take an agent that succeeds on a task with probability p = 0.8 per attempt, and assume attempts are independent.

pass@k: at least one of k attempts succeeds.

pass@k = 1 − (1 − p)k

pass@5 = 1 − 0.25 = 0.99968

pass^k: all k attempts succeed.

pass^k = pk

pass^5 = 0.85 = 0.32768

Which one is honest depends on how the system will be used:

  • pass@k fits when you can check answers cheaply. If a test suite tells you which of five generated patches works, you only need one. pass@k comes from code-generation research, where the Codex paper (Chen and colleagues, 2021) gave the standard way to estimate it.
  • pass^k fits when every run has to work. A deployed agent serves each user once, with no verifier. If a thousand users run it, you care about the chance it works every time, which is a measure of consistency. τ-bench (Yao and colleagues, 2024) introduced pass^k for exactly this reason, and showed agents whose pass^k dropped steeply as k grew.

Reporting pass@k for a system that runs once per user, without saying so, overstates its reliability. That's a red flag in a paper and in an interview answer.

Run every eval N times

Sampling, changing tool results, the order in which concurrent children finish, and changes on the provider's side all make runs differ. You can't switch the variation off, so the only option is to measure it. One run is an anecdote. The question is how many runs make a measurement.

Some practical rules follow from Figure 13.5:

  • Report a rate with its interval, plus the mean and spread of cost and latency. Never a single run.
  • Compare systems on the same tasks. Running A and B on the same task set and comparing task by task (a paired comparison) detects smaller differences than comparing two overall averages.
  • Version everything in the record. Model id, prompts, tool definitions and harness version go into the run-start event. Otherwise “B is better than A” may really mean “the provider updated something between Monday and Tuesday”.
  • Budget for it. N runs of a swarm cost N times a swarm. That's a real reason to keep component evals cheap and run the expensive outcome evals less often.

Benchmarks and their caveats

Public benchmarks let you compare against other people's numbers. You'll meet these in papers and interviews, so know what each one actually measures.

BenchmarkWhat it testsHow it's gradedWatch out for
SWE-bench
Jimenez et al., 2023		Resolving real GitHub issues in popular Python repositoriesCode: the repository's own tests must pass after the patchTest quality varies, which led to a human-checked subset, SWE-bench Verified (2024). The repositories are public, so training data may contain the fixes.
GAIA
Mialon et al., 2023		General-assistant questions that need browsing, tools and several reasoning steps, in three difficulty levelsCode: exact match against a short, unambiguous answerAnswers can leak online over time. Only the final answer is graded, not the path.
τ-bench
Yao et al., 2024		An agent with tools talks to a simulated user in retail and airline settings, under written policiesCode: the final database state is compared with the expected oneThe user is simulated by a model, which adds its own variation. Source of pass^k.
WebArena
Zhou et al., 2023		Tasks on realistic, self-hosted websites (shopping, forums, code hosting)Code: functional checks on the resulting stateHeavy environment setup. Results depend on how the agent sees the page.
AgentDojo
Debenedetti et al., 2024		Task success and resistance to prompt injection, togetherCode: task checks and attack checksCovered in ch12. Measures a defense's cost in utility as well as its security.

Caveats that apply to all of them:

  • The harness counts as much as the model. The same model in two different harnesses can score very differently. A benchmark number describes a model plus its scaffolding, so check what scaffolding was used.
  • Contamination and saturation. Public test sets leak into training data, and once top systems score near the maximum, a benchmark stops telling them apart.
  • Cost is often missing. A higher score bought with ten times the tokens is a different result. Ask for cost per task alongside accuracy.
  • Your task isn't the benchmark. Twenty to fifty tasks taken from your actual use, with clear pass criteria, tell you more about your system than any public leaderboard.

The single-agent baseline

This is the most important evaluation habit for anyone building multi-agent systems. Always compare the swarm with a single agent, and give the single agent the same budget.

The reason is that more tokens often help by themselves: more searching, more checking, longer reasoning. Anthropic reported, about its own multi-agent research system, that token usage alone explained most of the variance in performance on the BrowseComp benchmark. So a swarm that beats a cheap single agent may simply be buying the improvement. To claim the architecture helps, you have to beat the single agent at an equal budget. Chapter 14 looks at when that actually happens.

This is exactly what your Experiment 001 tests. Its value depends on decisions you make before the first run: what counts as success for an architecture design, how it's graded, how many runs each arm gets, and which budgets the single agent receives.

In your swarm harness
  • Stage 5. Write the success criteria for Experiment 001 before you run it. A RAG architecture design is open-ended output. Which parts can a code grader check, and which need a rubric? Write the rubric as pass or fail checks.
  • Stage 5. If you use a model judge, which model family will it come from, and how many outputs will you grade by hand to calibrate it?
  • Stage 5. How many runs per arm can you afford? Using Figure 13.5, what's the smallest difference between arms that number of runs could detect?
  • Stage 6. Your plan has an answer-quality eval. Will you report pass@k, pass^k, or both? Write the sentence justifying the choice in terms of how the harness will be used.
Misconceptions to drop
  • “It worked when I ran it.” One run is one sample from a distribution (Chapter 01). Report a rate, with the number of runs.
  • “pass@k is the success rate.” It's the chance that at least one of k tries succeeds. Users usually experience something closer to pass^k.
  • “An LLM judge is objective.” It has position, verbosity and self-preference biases. Validate it against human labels before you trust it.
  • “A high benchmark score means it'll do well on my task.” Benchmarks measure their own tasks, under their own harness, and they can leak into training data.
  • “Tracing is a production concern.” From Stage 1 on, your trace is your debugger.

Check yourself

Answer each one out loud or on paper before you open it.

Recall Logs, metrics, traces: what question does each answer best?

Metrics answer “is something wrong, and is it getting worse?” They are cheap aggregates over many runs. Traces answer “where, and because of what?” They are the causal tree of one run. Logs answer “what exactly happened at this point?” They hold detail attached to one event. A good debugging session goes metric → trace → log.

Recall What makes a set of spans into a tree, and how does a spawn tree map onto it?

Every span has a span id, a trace id shared by the whole run, and a parent span id. Plus start and end times and attributes. The parent link makes the tree. In a swarm, each agent is a span whose parent is the agent that spawned it, and its model calls and tool calls are child spans inside it.

Apply Each run succeeds independently with p = 0.9. What are pass@3 and pass^3?

pass@3 = 1 − 0.1³ = 0.999. pass^3 = 0.9³ = 0.729. The same agent “almost always works” if a user may retry until one attempt succeeds. It fails at least once in about a quarter of three-try sessions if every attempt must work.

Apply Your swarm passes 8 of 10 runs and your single agent passes 6 of 10. Can you say the swarm is better?

No. With 10 runs each, the uncertainty ranges overlap heavily (Figure 13.5), so the difference is well within noise. Also check that both arms had the same token budget (Figure 13.6). Next steps: more runs, the same task set for both arms (a paired comparison), and success criteria fixed before running.

Design You'll use an LLM judge for Experiment 001. Name three biases and one mitigation for each.

Position bias: grade each pair in both orders and only accept consistent verdicts. Verbosity bias: grade against pass/fail rubric items, not overall quality, and keep length out of the rubric. Self-preference: use a judge from a different model family than the one being judged. Then calibrate: grade a sample by hand and measure how often the judge agrees with you.

Design Write three trajectory checks for a spawning run that an outcome eval would miss.

Examples: no spawn was attempted beyond the depth limit; no two siblings received near-duplicate subtasks; every child's result was actually used in the parent's aggregation; no agent made the same tool call with the same arguments three times in a row. Each one can be checked by a code grader over the trace, without reading the final answer.

Interview “How would you show that your multi-agent system is actually better than a single agent?”

Fix the task set and success criteria before running. Compare against a single agent given the same token budget, not a cheap one. Run each arm many times on the same tasks and report rates with uncertainty, plus cost and latency. Validate the grader against human labels. Then look at traces from wins and losses to explain why. If the gap disappears at equal budget, the architecture isn't what helped.

Recall card

Five lines to rehearse. If you can expand each into a minute of explanation, you know this chapter.

  1. Metrics say something is wrong, traces say where and why, logs give the detail. Go in that order.
  2. A span is one timed unit of work with a parent link. A spawn tree is a trace.
  3. Record facts from the harness (the API usage field, the tool executor), never the model's account of itself.
  4. Evaluate outcome, trajectory and component. A grader is a model of your judgment and must be validated.
  5. pass@k is optimistic, pass^k is reliability. Run N times, and compare against a single agent with the same budget.
