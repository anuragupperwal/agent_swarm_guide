The framework landscape

You now know the concepts well enough to read a framework the way an engineer should: as a bundle of opinions about the loop, tools, state, control flow and delegation. This chapter maps seven frameworks and two protocols onto the concepts you already have, and shows you how to judge the next one that appears.

The big idea

Every framework in this chapter implements the same few things you've studied: a loop that calls a model (Chapter 03), tools (Chapter 04), some state (Chapter 09), some way to decide the next step (Chapter 09), and usually some way for agents to delegate (Chapters 15–16). They differ in which of these they make explicit and which they hide.

Key idea

A framework is a harness with opinions. Read any framework by asking three questions: Who decides the next step: your code, or the model? How much harness comes included: a thin loop, or tools, permissions and context management too? And what does it hide: which prompts, retries and state changes happen where you can't see them?

Seven frameworks, one at a time

For each framework: its core abstraction, a mental-model diagram, what it gives you, what it hides, and when it fits. Read the “hides” line most carefully. Anthropic's “Building effective agents” makes the same point: frameworks help you start quickly, but they can obscure the prompts and responses underneath, and that's where debugging happens.

A · LangGraph

Core idea
You define a state graph: a typed state object, nodes (functions that read the state and return an update), edges, and conditional edges (a function of the state picks the next node). Reducers say how updates merge, for example “append to the message list” rather than “overwrite”. A checkpointer saves the state after each step under a thread_id, which gives you resume, replay and human-in-the-loop interrupts. Fan-out to a variable number of parallel branches is supported.
Gives you
Explicit, inspectable control flow (Chapter 09 made concrete), durable state, pause and resume, subgraphs for nesting.
Hides
Less than most. The prebuilt agents hide their prompts. Reducer semantics can surprise you when two parallel branches update the same key.
Fits when
You can draw the flow in advance, or need durable, resumable runs with human checkpoints.

B · OpenAI Agents SDK

Core idea
A small set of primitives. An Agent is instructions, a model, tools, and optionally handoffs, guardrails and an output type. A Runner runs the loop: call the model; if it produced a final output, stop; if it chose a handoff, switch the active agent; if it called tools, run them and loop, up to a turn limit. Handoffs appear to the model as tools (“transfer to the billing agent”) and pass control. Agents as tools keep control with the caller. Guardrails check input or output and can trip to halt a run. Tracing is built in. It is the production successor to OpenAI's experimental Swarm (Chapter 18).
Gives you
A fast start for routing and handoff topologies (Chapter 15), plus tracing without extra work.
Hides
The loop itself, the text that describes handoffs to the model, and what history the next agent receives on a handoff (configurable, so look it up).
Fits when
Your problem is triage and routing between specialists, or you want few concepts and good defaults. It can use non-OpenAI models through adapters; check the current docs.

C · Claude Agent SDK

Core idea
The harness that runs Claude Code, offered as a library for Python and TypeScript (it was called the Claude Code SDK before it was renamed). You pass a prompt and options: system prompt, allowed tools, permission mode, MCP servers, subagent definitions and hooks. It runs the whole loop, including built-in tools for files, shell commands and search, automatic context compaction, subagents with their own context windows, hooks that run your code before or after tool calls, and permission checks.
Gives you
A production-tested harness: almost every component from Chapter 08, already written. It is the clearest worked example of “harness as a product”.
Hides
A lot, by design: the loop, the compaction strategy, the tool implementations, and the default system prompt unless you replace it.
Fits when
Your agents work in a computer environment (files, code, shell), and you'd rather configure a mature harness than write one. It is built for Claude models.

D · AutoGen and AG2

Core idea
Agents as participants in a conversation. In the original design (v0.2), a conversable agent can send and receive messages. An assistant agent writes, and a user-proxy agent can run code or stand in for a human. A group chat has a manager that selects the next speaker: round-robin, chosen by a model, or by your rule. Version 0.4 (early 2025) rebuilt AutoGen in layers: an event-driven core where agents pass messages like actors, and a high-level layer with ready-made teams.
Lineage
In late 2024 some of AutoGen's original authors continued the v0.2-style project as AG2, under a separate organization. In late 2025 Microsoft announced the Microsoft Agent Framework, bringing together ideas from AutoGen and Semantic Kernel, and pointed new projects towards it. Treat the status of each as something to check, not assume.
Hides
The speaker-selection prompt, and how fast the shared conversation grows: every agent reads every message, so context grows with agents × turns.
Fits when
You are exploring conversation-shaped collaboration: debate, critique, code-and-review loops (Chapter 17).

E · CrewAI

Core idea
Agents as job roles. Each agent has a role, a goal and a backstory, plus tools. Tasks have a description and an expected output, and are assigned to agents. A crew runs its tasks under a process: sequential (each output feeds the next) or hierarchical (a manager agent delegates and checks). Flows add event-driven, stateful control around crews when you need explicit steps.
Gives you
A vocabulary that maps well to business processes, and quick prototypes of pipeline and hierarchical topologies.
Hides
The prompts generated from role, goal and backstory, and the delegation prompts in hierarchical mode. Role-play framing can also encourage agents to imitate a process rather than verify facts.
Fits when
The work really is a sequence of role-shaped tasks with clear expected outputs.

F · Strands Agents

Core idea
An open-source SDK from AWS (2025) built around a model-driven approach: an agent is a model, tools and a prompt, and the model plans, chooses tools and decides when it's done. The SDK runs the loop. Tools are ordinary decorated Python functions, and MCP servers can supply more. It supports several model providers, with Amazon Bedrock as the default. Later versions added multi-agent patterns, including agents as tools, swarm and graph.
Gives you
Very little code for a working agent, and OpenTelemetry-based observability.
Hides
Not much code, but nearly all control: the trajectory belongs to the model. Your limits and checks must come from configuration, hooks or the tools themselves.
Fits when
You trust a strong model to plan, want thin code, and often when you deploy on AWS.

G · smolagents

Core idea
A Hugging Face library with a deliberately small core. Its main idea: a code agent writes each action as a Python snippet instead of a JSON tool call. One snippet can call several tools, loop, and keep variables, which saves steps. This builds on the CodeAct research (Wang et al., 2024), which found code actions can improve agent success rates. Code runs in a restricted local interpreter or a remote sandbox. A standard tool-calling agent is also available, and agents can manage other agents.
Gives you
A core small enough to read in an afternoon. If you want to see a real agent loop in someone else's code, read this one.
Hides
Little. The risk is in what it does: running model-written code. That is Chapter 12's threat model in its sharpest form, so sandbox it.
Fits when
You're learning, doing research, or solving data-heavy tasks where code is the natural action.
Key idea

None of these frameworks gives you your swarm harness's hardest parts for free. Recursive spawning with enforced depth, fan-out and budget limits, an atomic budget ledger across concurrent agents, and failure-as-data aggregation are things you either write or configure deliberately in every one of them. That's why building them yourself first (Stages 1–6) makes you better at using any of them.

Two protocols: MCP and A2A

Frameworks are libraries inside one program. Protocols are agreements between programs. Two matter for agents, and they solve different problems. Chapter 04 introduced MCP and Chapter 17 compared the two; here they are side by side.

A common confusion

“We'll use MCP for our agents to talk to each other.” You can wrap an agent as an MCP tool, and people do, but then the caller treats it as a function: one request, one result, no task lifecycle, no negotiation. That's the agent-as-tool pattern. A2A exists for the case where the remote side is a peer with its own long-running work. Pick based on which relationship you actually have.

How to evaluate a framework

A framework README tells you what's easy. These questions find out what's hard. Each has a test you can run in about a day, using a task you already understand (Experiment 001 is ideal, because you know what the right trace looks like).

AskWhy it mattersA one-day test
Who owns control flow?Decides whether you can express your topology, or only approximate itBuild Experiment 001's tree. Count the workarounds.
Where do limits live?Limits the model can bypass aren't limits (Chapter 20)Ask the model to spawn 50 children. Who stops it, and where?
Is it async-native?Parallel children need real concurrency and cancellation (Chapter 10)Run 10 children with a limit of 3. Cancel the run halfway.
What happens on failure?Hidden retries cost money; hidden exceptions crash trees (Chapter 11)Make one tool raise and one child time out. Read the trace.
Can I see every prompt?Hidden prompts are where behavior you didn't write comes fromLog the exact request sent to the model on step 1.

What persists?Resume, replay and human approval all depend on it (Chapter 09)Kill the process mid-run. What can you recover?
Can I export traces?Your company's tooling, not the framework's dashboard (Chapter 13)Get one run into OpenTelemetry or your JSONL format.
How locked in am I?Model providers and APIs change faster than your projectSwap the model provider. Count the files you touched.
What's the security story?Tools that run code or reach the network are the attack surface (Chapter 12)Find where permissions and sandboxing are configured.

Build vs adopt

The honest answer is usually “both, at different layers”: adopt the boring parts (HTTP clients, schema validation, tracing exporters) and decide deliberately about the orchestration core. The flow below is a heuristic for that one decision.

Traps when choosing
  • Learning the framework instead of the concept. If you can't say which Chapter 03–17 concept a class implements, you're memorizing an API that will change.
  • “Supports multi-agent” ≠ “supports your swarm”. Most frameworks support delegation. Few enforce recursive depth, fan-out and budget limits the way your requirements need.
  • Old tutorials. Many AutoGen examples online use the v0.2 API, which differs a lot from v0.4. Check the version of every snippet.
  • Mixing two frameworks' abstractions in one program. You get two loops, two state models and two tracing systems.
  • Trusting default prompts. They were tuned for someone else's tasks and models.
In your swarm harness · Stage 9
  • Pick one framework (your choice; the evaluation table is how you choose). Rebuild Experiment 001 in it, with the same tasks, model and limits.
  • Compare on things you can measure: lines of code, tokens and wall time per run, how a child failure appears in the trace, and how many of the twelve evaluation questions it answers well.
  • Write a one-page “build vs adopt” note for your company use case. It's allowed to conclude “adopt”: Stages 1–8 were for learning, and Stage 9 is for deciding.
  • Design question for you: which interface in your harness would let you swap your executor for a framework's runner without touching the spawn service?

Check yourself

Answer each one out loud or on paper before you open it.

Recall What's the difference between a handoff and calling an agent as a tool?

In a handoff, control transfers: the new agent takes over the conversation and the original agent is no longer driving. As a tool, the calling agent keeps control: it sends a request, gets a result back, and decides what to do next. Your spawn-and-aggregate design is the agent-as-tool shape.

Recall MCP vs A2A in two sentences.

MCP standardizes how an agent's host connects to tool and data servers, so integrations become M + N instead of M × N. A2A standardizes how one agent asks a remote, opaque agent to do a task, with discovery through an Agent Card and a task lifecycle.

Apply You build your swarm in LangGraph. Where would your depth limit and budget check live?

As fields in the graph state (depth, agents used, tokens reserved) and in the logic that decides whether to fan out: a node or conditional edge that checks the limits before creating parallel branches or entering a subgraph. The reducer for the counters must make concurrent updates combine correctly. The point: the framework gives you the place to put the check, but not the check.

Apply In a handoff-based system, two agents keep handing the conversation back and forth. Which harness concept is missing, and where would you add it?

Loop detection and a step budget (Chapter 11). Most runners have a maximum-turns limit, which stops it eventually but late. Better: count handoffs per run in your context, refuse a handoff back to an agent that just handed off, and record it as a trace event so you can see how often it happens.

Design A colleague proposes adopting CrewAI for the company version. Which three evaluation questions would you ask first, and why?

One defensible set: “Where do limits live?” (recursive spawning with hard limits is your core requirement), “Can I see every prompt?” (role and backstory prompts are generated for you), and “What happens on failure?” (partial results are part of your design). The important part is that you choose from your requirements in Figure 20.1, not from the framework's feature list.

Interview “Why did you build your own harness instead of using an existing framework?”

Structure: (1) the goal: learning the mechanisms, and specific requirements: recursive spawning with enforced limits, an atomic budget across concurrent agents, failures as data. (2) The evidence: a Stage 9 side-by-side on the same task, with numbers. (3) Credit where due: what the framework did better (for example persistence or tracing UI). (4) What you'd do in production: possibly adopt it behind your own interface. Avoid “frameworks are bad”; that's a red flag.

Interview “What is MCP, and what are its risks?”

An open protocol (JSON-RPC based) between a host application's clients and servers that expose tools, resources and prompts, so one server works with many hosts. Risks: a malicious or compromised server can put instructions into tool descriptions or results (indirect prompt injection), tools may have more permission than needed, and combining private data, untrusted content and an exfiltration channel recreates the lethal trifecta (Chapter 12). Mitigate with least privilege, allow-lists of servers, and human approval for risky tools.
