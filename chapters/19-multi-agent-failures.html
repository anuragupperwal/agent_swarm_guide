How multi-agent systems fail

A single agent fails in one place, and you can read its trace top to bottom. A tree of agents fails between places: a constraint lost in a hand-down, a confident “Done.” that hides nothing done, three agents agreeing on the same wrong answer. This chapter is a catalog of those failures, the fingerprint each one leaves in a trace, and the test that catches it before production does.

Why multi-agent failure is different

Everything that goes wrong with one agent (Chapter 11) can still go wrong with many. Multi-agent systems add four properties that make failures worse:

  • Errors cross boundaries. A child's mistake becomes the parent's input. The parent has no way to see how the child produced it, only what it returned.
  • Failure looks like success. A child that returns a wrong answer with status success is far more dangerous than one that crashes. Crashes are caught by code. Confident mistakes are passed on.
  • Errors are correlated. Agents built on one model share its blind spots. Adding agents adds chances to fail, but not independent chances to catch failures (Chapter 17).
  • The trace is a tree. Finding the cause means walking across agents, not reading down one list. Without good tracing (Chapter 13), most multi-agent failures can't be diagnosed at all.

The first property has simple arithmetic behind it. If a result depends on n steps or agents in sequence, and each succeeds with probability p, the whole chain succeeds with probability pn (assuming independent failures):

P(chain succeeds) = pn
p = 0.95:   n = 5 → 0.77  ·  n = 10 → 0.60  ·  n = 20 → 0.36
with a check that catches 60% of errors before they pass on: peff = 0.95 + 0.05·0.6 = 0.98 → n = 10 → 0.82

Read the last line carefully, because it's the argument for the whole second half of this chapter. You can't make each agent perfect. You can put checks between agents, and even an imperfect check changes the compounding a lot.

A map of failures: the MAST taxonomy

Cemri et al. (2025) studied why multi-agent LLM systems fail. They collected execution traces from several open-source multi-agent frameworks, had human experts annotate what went wrong, and built the Multi-Agent System Failure Taxonomy (MAST). They then used an LLM annotator, checked against human labels, to scale the analysis. MAST has 14 failure modes grouped into three categories:

FC1 · Specification and system design
The failure was built in before the run started: vague task descriptions, unclear roles, no defined stopping condition, a context that drops history. Agents “disobey” instructions that were ambiguous to begin with.
FC2 · Inter-agent misalignment
The parts work on their own but not together. An agent doesn't ask when it should, holds back information another agent needed, ignores a peer's input, drifts off task, or says one thing in its reasoning and does another.
FC3 · Verification and termination
The run stops too early, or it stops after checking nothing, or it checks the wrong thing. This is the column your harness can most directly fix.

Three findings from the paper are worth remembering. Treat the details as approximate and read the paper for the numbers. First, failures were spread across all three categories. No single category explained most of them, so no single fix will either. Second, many failures trace back to system design, not to the model being weak. Third, the authors tried straightforward interventions, such as clearer role prompts and changes to how agents were organized. These helped somewhat but left most failures in place. The authors argue that more structural changes are needed, which is exactly what a harness is for.

Key idea

Your Predict ranking was probably a guess, and that's fine. The lesson is that “use a smarter model” is rarely the fix. Specification, coordination and verification are engineering problems, and most of them live in code you write.

A catalog of swarm failures

Each failure below gets the same four parts: the mechanism (why it happens), the signal (what it looks like in a trace), a test (how to reproduce it with a fake model), and the closest MAST mode, where there is one. Some failures are harness-level problems that MAST, which studies agent behavior, doesn't name.

1 · Runaway spawning

Mechanism
Each planner decides independently that its task is “big enough to split”. Nobody sees the whole tree. With fan-out f and depth d, the tree has 1 + f + f² + … + fd agents (Chapter 16).
Signal
The spawn rate rises over time instead of falling. The tree keeps getting deeper. Leaf tasks are near-copies of their parents' tasks.
Test
A fake model that always proposes three subtasks. Assert that the total number of agents never exceeds the limit, and that every rejected spawn is a logged event, not an exception.
MAST
Closest is 1.5 (unaware of stop conditions). Mostly a harness failure: the limit was missing or not enforced.

2 · Duplicate work

Trace · two children with overlapping scopes
root
spawn child-1: "Research EU rules for AI systems" spawn child-2: "Research AI regulation in Europe"
child-1
web_search(query="EU AI Act obligations")
child-2
web_search(query="EU AI Act requirements")
results
both fetch the same 4 of their top 5 URLs
aggregate
11 findings, 9 near-duplicates · about twice the tokens for one subtask's worth of information
Mechanism
The planner wrote two subtasks that look different but mean the same thing. Neither child can see the other.
Signal
Siblings make tool calls with near-identical arguments. Their results cite the same sources. The aggregator throws away a large share of findings as duplicates.
Test
Give the fake planner two overlapping subtasks. Assert that your semantic plan check flags the overlap, or that the claim store makes the second child skip the shared sources.
MAST
1.1 at the planner level (a specification problem), and 2.4 if a sibling found something and didn't share it.

3 · The telephone game

Chapter 16 introduced this failure: every hand-down is a rewrite. A parent model doesn't forward the task, it summarizes it into a subtask, and summaries are lossy. The parts that are easiest to lose are the constraints, because they aren't the main point of any one subtask.

Mechanism
Each parent writes a child's task in its own words. Models compress, and a constraint that looks unrelated to the subtask looks safe to drop. Two hops compound the loss.
Signal
Compare each child's task text with the root task's constraint list. A constraint present at the root and missing at a leaf is the fingerprint. You can only see this if the trace records the exact task each agent received.
Test
Plant a “canary” constraint in the root task, for example “every finding must include a source URL”. Run a depth-2 tree with a fake model that paraphrases. Assert that the constraint reaches every leaf, and that every leaf result obeys it.
MAST
1.1 (disobey task specification) at the leaf, caused by 2.4 (information withholding) at the parent.

4 · Groupthink

Debate and voting (Chapters 17 and 18) are supposed to catch errors. They can also manufacture agreement. When agents see each other's answers, a minority with the right answer can give way to a majority with the wrong one.

Mechanism
Agents that share a model share its errors, so the majority is often wrong in the same way. Models also tend to defer to views put to them: Sharma et al. (2023) document sycophancy toward users. It's plausible, though less studied, that a similar pull applies to peer agents' messages.
Signal
An agent changes its answer with no new tool call, source or argument in between. Agreement rises across rounds while the number of distinct sources stays flat.
Test
Give one agent a fixture with the correct, newer document and two agents a planted outdated one. Assert that the final answer follows the evidence, not the headcount.
MAST
2.5 (ignored other agent's input) applies to the majority. 3.3 (incorrect verification) applies if a vote count was treated as a check.

5 · Cascading hallucination

Trace · one invented number becomes two citations
child-2
write_finding(text="Vendor B uptime was 99.99% in 2025", source=None)
board
finding f-7 · author child-2 · source: none · accepted (no check)
child-3
read_board() → uses f-7 "Since B's uptime is 99.99%, its penalty clause rarely applies."
root
"Vendor B: 99.99% uptime, confirmed by two independent research threads."
Mechanism
A child invents a plausible fact. Shared state (a blackboard, a summary, a parent's context) spreads it. Each agent that builds on it adds apparent support, and the aggregator mistakes repetition for corroboration.
Signal
Findings with no source. Two citations for one claim that both trace back to the same agent. A claim whose cited source doesn't contain it.
Test
A fake child that writes one finding with source=None and one with a source that doesn't mention the claim. Assert that the aggregator rejects or flags both, and that the final answer doesn't contain either claim as fact.
MAST
3.2 (no or incomplete verification). The invented fact itself is a single-agent error. Letting it spread is a system error.
Same path, worse payload

Prompt injection travels the same way (Chapter 12). A child reads a web page that contains instructions, and writes them into its result. Its parent reads that result as trusted text. Anything that can carry a hallucination from one agent to another can carry an attack. Provenance helps with both, because a finding that records where it came from can be treated with the trust level of its source.

6 · Premature termination and false success

This is your Predict question 3.

Trace · status says success, content says otherwise
task
child-4: "Extract the penalty clauses from the 3 SLA PDFs. Return a list of {vendor, clause, page}."
child-4
read_pdf(path="vendor_a.pdf")
tool
38 pages · truncated to the first 8,000 tokens
child-4
"Done. The penalty clauses have been extracted and summarized." status=success
contract
clauses=[] (required, empty) · files read: 1 of 3 → reject: status success, content missing
Mechanism
The model can't tell “I finished” from “I wrote words that sound finished”. Truncated tool output, a tight step budget or an unclear stopping rule all push it to wrap up early. The status field is just more model output, so it can't be trusted on its own.
Signal
A very short result, empty required fields, fewer tool calls than inputs (1 call, 3 files), or success reported straight after a truncation or error observation.
Test
A fake child that returns exactly "Done." with status success. Assert that the harness records the result as failed or unverified, never as success, and that the parent's next step sees that status.
MAST
3.1 (premature termination) plus 3.2 (no or incomplete verification).
Key idea

A child's status is a claim. The harness turns it into a fact by checking the result against the return contract, with code, before the parent sees it. That's the “model proposes, harness disposes” rule (Chapter 8) applied to results instead of actions.

7 · Never terminating

Trace · a writer and a reviewer with no exit
reviewer · r1
"Section 2 needs more detail on pricing."
writer · r1
revises section 2 (+420 tokens)
reviewer · r2
"Section 2 is now too long. Tighten it."
writer · r2
revises section 2 (−380 tokens)
reviewer · r3
"Section 2 could use more pricing detail."
harness · r9
change between revisions: 2% · budget used: 70% · acceptance criterion: none defined
Mechanism
A reviewer prompted to find problems will always find one. With no acceptance criterion agreed in advance, “good enough” never arrives, and the loop runs until a budget stops it.
Signal
The round counter rises while the difference between versions shrinks. The same critique comes back in different words. The output oscillates (longer, shorter, longer).
Test
A fake reviewer that always asks for one more change. Assert that the loop stops at the round limit or when the change between versions falls below a threshold, and that it returns the best version so far with a reason for stopping.
MAST
1.3 (step repetition) and 1.5 (unaware of stop conditions).

8 · Cost explosion

Chapter 1 showed that one agent's input tokens grow with the square of its step count, because each call re-sends the whole history. With n steps, a starting context of b tokens and growth of a tokens per step, the total is n·b + a·n(n−1)/2. Now let agents broadcast to each other. Every message an agent posts lands in every other agent's context, so it increases a for all of them:

AgentsGrowth per step, ownGrowth per step, from peers (500 tokens each)Input tokens per agent, 20 stepsInput tokens, whole run
10, no broadcast4k00.80M8.0M
10, broadcast4k9 × 500 = 4.5k1.66M16.6M
20, no broadcast4k00.80M16.0M
20, broadcast4k19 × 500 = 9.5k2.61M52.1M

Assumes b = 2k tokens and n = 20 steps. Per agent: 20·2k + a·190. For example, a = 13.5k gives 40k + 2,565k ≈ 2.61M.

Mechanism
Doubling the agents doubles the run without broadcast, but more than triples it with broadcast, because total peer traffic grows with n(n−1). Nothing here is a bug. Every agent behaves correctly, and the bill is still the failure.
Signal
Input tokens per step keep rising, and the share of each context taken by other agents' messages keeps growing. Cost per useful finding rises with the number of agents.
Test
Run the same fake task with 2, 4 and 8 agents. Assert that total tokens stay within the budget pool, and plot tokens against agents to see the curve's shape.
MAST
Not a MAST mode. It's a resource failure, which is why budgets live in the harness (Chapter 11).

9 · Deadlock

Trace · two agents waiting on each other (timestamps in UTC)
10:02:11
agent-3 → agent-5 request(id=81) "Send me your vendor list."
10:02:12
agent-5 → agent-3 request(id=82) "Send me your criteria first."
10:02:12
agent-3 awaiting reply to 81 (no timeout) agent-5 awaiting reply to 82 (no timeout)
10:07:12
watchdog: no events for 300 s · 2 tasks pending → dump wait graph: 3 → 5 → 3 → fail run, keep partial results
Mechanism
All four Coffman conditions hold (Chapter 17): each agent holds its own state, waits for the other, nothing can take the wait away, and the waits form a cycle.
Signal
The run goes quiet. No events, no tokens spent, tasks still pending. This is the one failure that's cheap, which is why it's easy to miss in a cost dashboard.
Test
Two fake agents scripted to request from each other before replying. Assert that a timeout or the watchdog ends the run within a bound, and that the trace names the cycle.
MAST
Closest is 2.2 (fails to ask for clarification) or 1.5. The real fix is structural: timeouts on every wait, or a rule that requests only flow down the tree.

Mitigations at a glance

Each failure above has a first line of defence, and nearly all of them live in the harness rather than in a prompt. A prompt can ask an agent not to over-spawn. Only code can make over-spawning impossible.

Design for verification

The MAST authors argue that many of these failures come from how the system is designed, not from weak models, so a better model alone won't remove them. Their third category, verification and termination, is the one you control most directly. A system that checks its work at every boundary turns most of the catalog from silent failures into visible, recoverable ones.

Five rules make this work:

  1. Check at every boundary, not only at the end. An error caught at the child costs one retry. Caught at the root, it may cost the run.
  2. Prefer code checks. “Has a status, has a non-empty result, stays within its assigned scope, every claim has a source id” is all checkable without a model.
  3. Give a model verifier different information. A verifier that reads the same summary as the parent inherits the same blind spots. Give it the sources, or the original brief, and ask a narrow question.
  4. A check must be able to say no, and the harness must act on it. A verifier whose “fail” is logged and ignored is decoration.
  5. Verify termination too. The root must not report success when a required child failed. That's a code rule on the aggregate, not a judgment.

Misconceptions to drop
  • “A smarter model will fix it.” Most of the catalog is specification, coordination and verification. Those are code.
  • “Every agent succeeded, so the run succeeded.” Statuses are claims. A confident, under-budget, all-green run can still be wrong.
  • “More agents means more checking.” Only if some of them are given different information and the power to say no.
  • “Majority vote is a safe aggregator.” Not when the agents share a model, a prompt and each other's answers. Correlated errors vote together.
  • “A cheap run is a healthy run.” Deadlock is the cheapest failure there is.
In your swarm harness
  • Stage 1–2. Which fields must a child's Result carry so that a contract check can be written in code at all? If a child can return free text only, what can't you check?
  • Stage 4. Your plan validator already rejects duplicates. How will it decide that two subtasks are “the same” when their wording differs? What's the cheapest test that would show it failing?
  • Stage 5. Rows 3 and 5 of the table above aren't on any break-it list. Decide whether each belongs in Stage 5 or Stage 6, or write down why it's out of scope. Either answer is fine. Not deciding isn't.
  • Stage 6. For each failure in the catalog, which trace signal would you alert on? Which ones can't your current trace fields detect?

Check yourself

Answer each one out loud or on paper before you open it.

Recall Name MAST's three categories and give one failure mode from each.

Specification and system design (for example, disobeying the task specification, or being unaware of termination conditions). Inter-agent misalignment (for example, failing to ask for clarification, withholding information, ignoring another agent's input). Task verification and termination (for example, premature termination, or no or incorrect verification).

Recall Why is deadlock easy to miss on a cost dashboard, and what catches it?

A deadlocked run spends nothing: no tokens, no events, just pending tasks. Cost alerts never fire. What catches it is a timeout on every wait, plus a watchdog that notices “no events for N seconds while tasks are pending” and dumps the wait graph.

Apply A planner always proposes 3 children, and nothing limits it. How many agents exist four levels below the root? Which single limit bounds the total, whatever the depth?

1 + 3 + 9 + 27 + 81 = 121. A depth limit bounds the depth but not the width at each level. A cap on total agents (or a shared budget pool) bounds the total directly, whatever shape the tree takes.

Apply Every agent reported success and the answer reads well, but one key “fact” came from a page a child misread. Which failure is this, what does the trace show, and which check would have caught it?

Cascading hallucination. In the trace, the claim first appears in one child's result with either no source or a source that doesn't support it, then shows up unchanged in every level above. A contract rule that every claim carries a source id, plus a final check that the cited source exists and contains the claim, would catch it at a boundary.

Design You add a three-agent debate for the final recommendation. Give two protocol rules that resist groupthink.

Each agent writes its first answer independently, before seeing the others. A change of position must cite new evidence, not just agreement. Also good: the aggregator weighs evidence instead of counting votes, and a minority position is kept in the output when its evidence is strong.

Design For each check, choose code or a model verifier: (a) every child result follows the return contract; (b) the final architecture recommendation is sound.

(a) Code: it's structure and rules, so it's checkable exactly and cheaply. (b) A model verifier with a pass/fail rubric, given the sources and the original task rather than the parent's summary, and validated against your own grading on a sample (Chapter 13).

Interview “Your multi-agent system sometimes returns confidently wrong answers. How do you debug it?”

Collect failing runs and their traces. For each, find the first span where the wrong content appears, and name the failure mode. Ask which boundary check should have caught it and why it didn't. Reproduce it as a deterministic test with a fake model. Fix the structure (contract, provenance, verification), not just the prompt. Then re-run the eval many times to confirm the rate changed, and watch cost and latency while you do.
