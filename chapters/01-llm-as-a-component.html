The LLM as a component

Before you can build an agent, be precise about the part you're building around. A large language model is a stateless function: it takes text in and puts text out. Everything people call memory, action or judgment in an agent is code someone wrote around that function.

The big idea

Picture the model as a function with frozen weights. You give it a sequence of tokens. It gives back a probability for every possible next token. That's all it does. It doesn't wait, remember or act, and it can't see anything you didn't put in the input.

Key idea

The model is the reasoning engine. The agent is the program around it. The program stores the conversation, decides what the model sees, runs the actions the model asks for, and stops it when it should stop. When this guide says “harness”, it means that program. Every later chapter is about one part of it.

This framing matters for your project. Every time you're tempted to say “the agent decides” or “the agent remembers”, ask which line of your code does it. If you can't point to one, the behavior is either luck or a bug waiting to happen.

Tokens and the generation loop

Text is split into tokens: subword pieces, roughly three-quarters of an English word on average. The exact split depends on the tokenizer. The model never sees characters, only token IDs. That's why it can be bad at spelling and character counting, and why every limit and price is set in tokens.

Generation is autoregressive. One forward pass over the context gives a probability distribution for the next token. One token is sampled from it and appended to the context, and the model runs again. The response you get is the result of hundreds or thousands of these passes.

Two loops are easy to confuse, and your project depends on keeping them apart:

Generation loopAgent loop
Runs whereInside the provider, during one API callIn your code, across many API calls
One iterationOne forward pass, one tokenOne model call, then zero or more tool runs
Ends whenStop token, stop sequence, or max_tokensThe model stops requesting tools, or one of your limits fires
Controlled byThe provider (you set a few knobs)You, entirely

Chapter 03 is about the second loop. This chapter is about the box that sits inside it.

Stateless: the context window is its only memory

The model keeps nothing between calls. No session, no hidden memory, no learning from your last request. If a chat product seems to remember you, it's because the client sent your earlier messages again, or retrieved notes and put them into the input.

The context window is the maximum number of tokens one call can handle, input and output together. Think of it as the model's whole world for that call. Three consequences follow:

  1. You own the history. The conversation is a list in your program. You can append to it, trim it, summarize it, or give two agents different lists. That editing is context engineering (Chapter 06).
  2. Every token you send is paid for and processed on every call. History isn't free just because it's old.
  3. Multi-agent systems start here. A sub-agent is useful largely because it gets a fresh, small context window instead of inheriting a huge one (Chapter 14).

Anatomy of one call

Strip away every SDK and an agent call is one HTTP request with a JSON body. The fields below follow Anthropic's Messages API, which this guide uses as its reference shape. Other providers name things differently, but the parts are the same.

Request

{
  "model": "claude-opus-5-5",
  "max_tokens": 16000,
  "system": "You are a research assistant. Use tools when you need facts.",
  "tools": [{
    "name": "search_docs",
    "description": "Search the internal docs. Returns the top 5 passages.",
    "input_schema": {
      "type": "object",
      "properties": { "query": { "type": "string" } },
      "required": ["query"]
    }
  }],
  "messages": [
    { "role": "user", "content": "What does our retry policy say about 429 errors?" }
  ]
}

Response

{
  "role": "assistant",
  "content": [
    { "type": "text", "text": "I'll check the docs." },
    { "type": "tool_use", "id": "toolu_01A...", "name": "search_docs",
      "input": { "query": "retry policy 429" } }
  ],
  "stop_reason": "tool_use",
  "usage": { "input_tokens": 412, "output_tokens": 61 }
}
model
Which model version runs the call. Pin it. Behavior changes between versions, so an upgrade can quietly change an agent's trajectory.
max_tokens
A cap on output tokens for this call. Hit it and the response stops mid-sentence, or mid-JSON.
system
Standing instructions. There's nothing special about it: it's text placed before the conversation.
tools
What the model is allowed to ask for: a name, a description, and a JSON Schema for the inputs. Chapter 04 covers this in depth.
messages
The whole conversation so far, alternating user and assistant turns. Your code builds this list on every call.
content
A list of blocks, not one string. A single response can mix text and several tool_use blocks. Reasoning models can also return thinking blocks (Chapter 05).
stop_reason
Why generation stopped. Your code's next move depends on it (next section).
usage
The tokens billed for this call. Log it on every call. It's your only accurate cost meter.
Key idea

The model never ran search_docs. It wrote a request to run it and stopped. Whether that request is executed, changed, or refused is up to your code. The rule in your spec, “the model proposes, the framework disposes”, isn't a design preference you impose. It's how the API already works.

stop_reason: your first control-flow decision

Every response says why it ended. Code that reads only the text and ignores stop_reason breaks the first time an output gets truncated or a tool gets requested. Branching on it is the first if in any agent loop.

Pitfall

max_tokens is the quiet one. A truncated plan looks like a short plan unless you check. If your planner returns three subtasks and stop_reason is max_tokens, there may have been a fourth that got cut off.

Structured output is a proposal, not a fact

Modern APIs can constrain decoding to a JSON Schema. Tokens that would break the schema are never sampled, so the output always parses and always has the right fields and types (unless it was truncated or refused). That's a real improvement. It's also where people stop checking, and that's the mistake.

The schema can't express “three to six subtasks, no duplicates, none of them the parent's own task again, total depth within budget”. Those are your rules, so your code enforces them. A useful habit: write the semantic and policy checks before you write the prompt. They're the contract the prompt is trying to satisfy.

Latency and cost, and why agents get expensive

Two numbers dominate how a call feels and what it costs:

  • Latency. Time to first token grows with input length. After that, output streams at a roughly fixed rate, so output tokens drive wall-clock time. A model that thinks for 2,000 tokens before answering is slower than one that answers in 200. Running calls in parallel cuts wall-clock time, not tokens.
  • Cost. You pay for input and output tokens, and output tokens cost several times more per token. Thinking tokens are billed as output. For exact prices, check the provider's current price list. They change, so this guide doesn't quote them.

The part most people miss is how input tokens accumulate in an agent. Because the model is stateless, step k re-sends everything from steps 1 to k−1. Each step is a little bigger than the last, so the total grows much faster than the step count.

total_input ≈ n·b + a·n(n−1)/2
b = base tokens per call · a = tokens added per step · n = steps

n = 10:  10·2K + 4K·45  = 200K
n = 20:  20·2K + 4K·190 = 800K  ← twice the steps, four times the tokens

The n² term is why long-running agents get expensive, and it's one of the honest arguments for multi-agent designs. Five workers with 8 steps each re-send far less history than one agent with 40 steps, because each worker starts with an empty context.

Prompt caching softens this but doesn't remove it

Providers can cache the processed form of a prompt prefix. If the next request starts with exactly the same tokens, that part is read from cache, which is faster and billed at a fraction of the normal input price. The catch is that it's a prefix match. Change one byte early in the prompt, such as a timestamp in the system prompt or a reordered tool list, and everything after that byte is a cache miss. The rule is simple: put stable content first (tools, then system prompt, then old history) and changing content last. Chapter 06 goes deeper.

Non-determinism

Generation samples from a distribution (Figure 1.1), so the same input can produce different outputs. You can't fully turn this off. Anthropic's current API doesn't accept the sampling parameters at all (temperature, top_p, top_k). Even on stacks that do, “temperature 0” isn't bit-for-bit repeatable, because batching and floating-point arithmetic vary between runs. Model upgrades change behavior too.

Design for this from the start rather than fighting it:

  • Test the harness with a fake model that returns scripted responses. Your harness logic (spawning, budgets, failure handling) should be fully deterministic even though the model isn't. This is principle 2.9 in your spec.
  • Evaluate over many runs, not one. Chapter 13 explains the difference between “passes at least once in k tries” and “passes all k times”.
  • Validate everything that crosses from model to action (Figure 1.4).

Misconceptions to drop
  • “The model remembers the conversation.” Your code sends it again.
  • “The model called the tool.” It wrote a request. Your code ran it.
  • “Structured output means valid data.” It means valid shape.
  • “Temperature 0 makes it deterministic.” Not reliably, and some APIs no longer accept it.
  • “A bigger context window means better memory.” More room doesn't mean better attention (Chapter 06).

Check yourself

Answer each one out loud or on paper before you open it.

Recall Why is “the model remembers the conversation” misleading?

The model is stateless. The client stores the conversation and sends all of it on every call. Memory is a harness feature built on re-sending or retrieving context, not a property of the model.

Recall What is the difference between the generation loop and the agent loop?

The generation loop runs inside the provider during one call: one forward pass per token, until a stop condition. The agent loop runs in your code across many calls: call the model, run any requested tools, append the results, call again. You control the second loop completely.

Apply Your 10-step agent becomes a 30-step agent (same 2K base, +4K per step). Roughly how do total input tokens change, and what three levers reduce them?

30·2K + 4K·(30·29/2) = 60K + 1,740K ≈ 1.8M, which is about 9× the 200K. Three times the steps means about nine times the tokens. Levers: prompt caching for the repeated prefix (cheaper, not fewer, tokens); trimming or summarizing old tool results; and splitting the work across sub-agents, each with its own small context.

Apply Which stop_reason values must an agent loop handle, and what does each mean for control flow?

end_turn: done, return the answer. tool_use: run the tools, append the results, loop. max_tokens: truncated, so continue or fail, but never treat it as complete. pause_turn: re-send to let a server-side tool finish. refusal: surface it, don't retry blindly. stop_sequence: one of your custom stop strings was hit.

Design A planner returns valid JSON with 40 subtasks, two of which repeat the parent's own task. Which validation layers catch this, and what should happen next?

Syntax and schema pass. The semantic layer should catch the duplicates and the self-delegation. The policy layer should catch “40 exceeds the fan-out limit”. Next: reject before creating anything, then either re-prompt with the specific errors (bounded retries) or fail the step as data. Never execute part of it and hope.

Interview “Why not just set temperature to 0 and make the agent deterministic?”

Some current APIs don't accept sampling parameters at all. Where they do, temperature 0 still isn't bit-exact, because batching and floating-point arithmetic vary. Model versions change behavior. And in an agent, tiny differences compound over many steps. So design for non-determinism: deterministic harness tests with a fake model, validation at every boundary, bounded retries, and evaluation over many runs.

Recall card

Five lines to rehearse. If you can expand each into a minute of explanation, you know this chapter.

  1. An LLM is a stateless function: context in, next-token probabilities out, sampled one token at a time.
  2. Every call re-sends everything. “Memory” is the harness re-sending or retrieving context.
  3. stop_reason is the first branch in any agent loop. tool_use keeps the loop going.
  4. Input tokens across an agent run grow with the square of the step count. Caching reduces the price, not the growth.
  5. Model output is a proposal. Check syntax, schema, semantics and policy before acting on it.
