Context engineering

On every call, the model knows exactly what's in its context window and nothing else. Context engineering is deciding, call by call, which tokens go in, in what order, and which come out. In a long agent run it matters more than any single prompt you write.

The big idea

Chapter 01 established that the model is stateless: the context window is its only memory. Chapter 05 showed that reasoning patterns are ways of arranging calls. This chapter is about the contents of each call. Your harness builds the context from scratch on every request, so every token in it is there because your code put it there.

Prompt engineering is about writing one good set of instructions. Context engineering is the wider job in an agent loop: on every turn, choosing what the model sees from everything that could be in the window (instructions, tool definitions, history, tool results, retrieved documents, notes) and deciding what to drop as the run grows.

Key idea

Find the smallest set of high-signal tokens that makes the right next step likely. This is the framing in Anthropic's “Effective context engineering for AI agents” (2025). Context is a budget, not a container. Each token you add costs money and time, and it competes for the model's attention with every token already there.

Anatomy of a context window

Here is one request from a realistic coding agent, twelve steps into a bug fix, drawn to scale against a 200K-token window. The numbers are illustrative, but the proportions are typical of agents that read files and run commands.

Tool definitions
Name, description and JSON Schema for every tool, sent on every call. Twenty tools with detailed descriptions can take several thousand tokens before the conversation starts.
System prompt
Role, rules and output expectations. Anthropic's post recommends the “right altitude”: specific enough to guide behavior, general enough that it isn't a brittle list of if-then rules.
Project instructions
A file loaded at the start of every run, such as a CLAUDE.md. It's preloaded context (see “Just-in-time” below).
History
Every assistant turn and every tool result so far. It grows every step, and tool results are usually the biggest part.
Reserved output
Space for the response. Input plus max_tokens must fit in the window, so the usable input space is smaller than the advertised window.

Why more context isn't free

A bigger window means you can include more. It doesn't mean the model uses all of it equally well. Three findings explain why, from mechanism to measurement.

1 · The attention budget

In self-attention (Vaswani et al., 2017), each token computes weights over all earlier tokens, and for each attention head those weights are normalized to sum to 1. So attention is a budget that gets shared. With 1,000 tokens in context, each one competes with 999 others for a share of the model's focus. With 100,000, it competes with 99,999. The number of token pairs grows with the square of the length. Models also see far fewer very long sequences in training than short ones. This is an intuition rather than a precise law, but it predicts what the measurements show: relevant information gets harder to use as more irrelevant information surrounds it.

2 · Lost in the middle

Liu et al. (2024) gave models a question and 20 documents, only one of which held the answer, and moved that document from first to last position. Accuracy was highest when the answer was near the start or the end of the context, and lowest in the middle. In some settings, mid-context accuracy fell below the accuracy with no documents at all.

3 · Context rot

“Context rot” is the general observation that a model's ability to use information in its context degrades as the input grows, even on simple tasks. Chroma's 2025 report of that name found the drop across many models, and found it worse when the context held distractors: passages that look relevant but aren't. The RULER benchmark (Hsieh et al., 2024) found that a model's effective context length, where it still performs well, is often much shorter than its advertised window.

Distractors are the agent-specific problem. An agent's history is full of near-misses: the wrong file it opened first, the test output from before the fix, the search results it rejected. They're exactly the passages that look relevant but aren't.

Key idea

Every token you add competes with every token already there. Practical rules that follow: put standing instructions at the start (system prompt) and restate the current goal near the end (the latest turn). Don't bury a critical fact in the middle of 60K tokens of logs. Remove stale tool output instead of keeping it “just in case”. When in doubt, a smaller context with the right things in it beats a larger one.

Ordering and the prompt-cache prefix

Chapter 01 showed that an agent re-sends its whole history on every call. Prompt caching is how providers make that affordable. The provider stores the processed state of a request's opening tokens, and a later request that begins with exactly the same bytes reuses that work instead of recomputing it. It's a prefix match. Any change, even one character, invalidates everything after that point.

The Anthropic API renders a request in a fixed order: tools, then system, then messages. So the rule for ordering is simple: stable first, volatile last. Content that never changes goes earliest, per-session content goes after it, and per-turn content goes at the end. Anything that changes on every request (a timestamp, a request ID) should be removed or moved to the very end.

The request and the usage it returns

You mark where a cacheable prefix ends with a cache_control breakpoint. A request can have up to four. A typical agent marks the end of the frozen system prompt, plus the end of the newest message, so the whole conversation so far is cached for the next call.

Request at step 12 (JSON wire shape, trimmed)

{
  "model": "…",
  "max_tokens": 16000,
  "tools": [ /* sorted by name, identical on every call */ ],
  "system": [
    {"type": "text", "text": "You are a coding agent… (frozen for the run)",
     "cache_control": {"type": "ephemeral"}}
  ],
  "messages": [
    /* turns 1 … 11, never edited after they were sent */
    {"role": "user", "content": [
      {"type": "tool_result", "tool_use_id": "toolu_12", "content": "…test output…",
       "cache_control": {"type": "ephemeral"}},
      {"type": "text", "text": "Current goal: make test_retry_backoff pass without touching shared/."}
    ]}
  ]
}

The usage block in the response

"usage": {
  "cache_read_input_tokens":     82650,  // the prefix that matched: billed at a fraction of the input rate
  "cache_creation_input_tokens": 3230,   // new prefix written to the cache: billed at a premium
  "input_tokens":                120,    // only what follows the last breakpoint
  "output_tokens":               310
}
// prompt size = 82,650 + 3,230 + 120 = 86,000 tokens (the request in Figure 6.1)

Two things to notice. First, input_tokens is not the size of the prompt. It's only the uncached remainder. A budget meter that reads only that field undercounts by a factor of several hundred here. Second, the healthy signature of a cached loop is that cache_read_input_tokens grows every turn while cache_creation_input_tokens stays about the size of the last turn's new content. If writes are large on every call, something early in the prefix is changing. The short “Current goal” line after the breakpoint follows the advice from the attention section: restate the goal near the end. It stays in the history, so next turn it's part of the cached prefix.

Silent invalidators

The cache never fails loudly. It just stops hitting, and the only symptom is cost and latency. These are the usual culprits:

Three cache facts that matter for a swarm

  • Forks reuse the parent's prefix only if they copy it exactly. A side call (summarize this history, or spawn a helper that sees the same context) hits the parent's cache only if it sends the same model, tools and system prompt and appends its instruction at the end. A sub-agent with its own system prompt and tool set starts its own cache.
  • Parallel requests don't share a cache entry that doesn't exist yet. The entry becomes readable only once the first response begins streaming. Fire five siblings with the same 20K prefix at the same instant and all five pay to write it. Sending one first, waiting for its first token, then sending the other four lets four of them read it, at the cost of one time-to-first-token of extra latency.
  • Entries expire. The default lifetime is about five minutes, with a longer option you can request. A loop that pauses for a slow tool or a human approval longer than that loses its cache. The minimum cacheable prefix length also varies by model, so a tiny prompt may not be cached at all.
Key idea

Caching makes a long prefix cheaper and faster. It doesn't make it smaller. The model still attends to every cached token, so everything in the attention section still applies. Ordering for the cache and pruning for attention are separate jobs, and they can conflict: removing an old tool result helps attention but breaks the prefix at that point. The compaction section deals with that trade-off.

Just-in-time retrieval vs preloading

There are two ways to get outside information into the window. Preloading decides up front what might be relevant and puts it all in before the model starts, as classic retrieval-augmented generation does with its top-k chunks. Just-in-time retrieval puts only lightweight identifiers in the context (file paths, URLs, record IDs, query names) and gives the agent tools to load the content when it decides it needs it.

Just-in-time retrieval works because identifiers carry signal before any content is loaded. A path like billing/retry.py tells the agent what's inside. A folder structure, file sizes and modification times tell it where to look first. Each step reveals the next layer. This is progressive disclosure: list the directory, grep for the term, read lines 30 to 80, and stop when there's enough.

The same idea applies to the parts of the context that aren't data:

  • Tools. Rather than sending 200 tool schemas on every call, a tool-search tool lets the agent find and load the few it needs. Loaded schemas are appended, not swapped in, so the cached prefix survives.
  • Instructions. Skills keep only a short description in context, and the agent reads the full instruction file when the task calls for it.
  • Intermediate results. With programmatic tool calling, the model writes a script that calls tools. Intermediate results go back to the script, not the context, and only the script's final output reaches the model.

Tool design is part of context engineering (Chapter 04). A tool that returns a whole 3,000-line file has made a context decision for the agent. A better one returns a bounded window and tells the agent how to get more:

A tool result designed for progressive disclosure (plain Python)

MAX_RESULT_TOKENS = 4_000

def read_file(path, start_line=1, end_line=None):
    lines = open(path).read().splitlines()
    end_line = end_line or len(lines)
    chunk = "\n".join(lines[start_line - 1:end_line])
    if count_tokens(chunk) > MAX_RESULT_TOKENS:
        chunk = truncate_to_tokens(chunk, MAX_RESULT_TOKENS)
        chunk += (f"\n[truncated: {path} has {len(lines)} lines. "
                  "Call read_file with start_line and end_line to see more.]")
    return chunk

Anthropic's post describes Claude Code as a hybrid: project instruction files are loaded at the start, and the agent uses glob and grep to find everything else as needed. The fixed part should hold what's needed on almost every step and can't be cheaply discovered: conventions, constraints, where things live.

Compaction and clearing old tool results

Retrieval decides what comes in. In a long run you also need to decide what goes out. There are three levers, from lightest to heaviest:

  1. Clear old tool results. Replace the content of an old tool_result with a short stub. The tool_use block that produced it stays, so the model can still see that it read billing/retry.py, and can read it again if it needs to. Anthropic's post calls this the lightest-touch form of compaction.
  2. Compact. When the context nears a threshold, have the model summarize the run so far, then continue from a fresh context that holds the summary instead of the history.
  3. Start fresh from notes. The agent keeps its state in files outside the window, and a new context reads them back (next section).

Context management between loop steps (plain Python, generic client)

CLEAR_AT    = 100_000   # prompt tokens: clear old tool results
COMPACT_AT  = 150_000   # prompt tokens: summarize and restart
KEEP_RECENT = 2         # newest tool results kept verbatim

def prompt_tokens(usage):          # all three fields, not just input_tokens
    return (usage.input_tokens + usage.cache_read_input_tokens
            + usage.cache_creation_input_tokens)

def manage_context(messages, usage):
    if waiting_for_tool_result(messages):   # mid tool round: never cut here
        return messages
    size = prompt_tokens(usage)
    if size > COMPACT_AT:
        summary = llm.complete(
            model=MODEL, system=SYSTEM, tools=TOOLS,   # same prefix as the loop, so a cache hit
            messages=messages + [user(COMPACTION_PROMPT)],
        ).text
        return [user("Summary of the work so far:\n" + summary + "\n\nContinue the task.")]
    if size > CLEAR_AT:
        return clear_old_tool_results(messages, keep_last=KEEP_RECENT)
    return messages

def clear_old_tool_results(messages, keep_last):
    results = [b for m in messages for b in m.content if b.type == "tool_result"]
    for block in results[:-keep_last]:
        block.content = stub_for(block)     # "[cleared: read_file billing/retry.py, 4.2K tokens. Re-run to see it.]"
    return messages                         # tool_use blocks untouched, so every pair stays intact

A compaction prompt

Summarize this session so a fresh copy of you can continue it with no other context.
Keep: the goal and every constraint the user gave; decisions made and why;
what is done; what is failing, with the exact error; open questions;
the file paths, IDs and commands needed to find details again.
Drop: raw tool output and anything that can be re-fetched by re-running a call.
For dead ends, write one line: "Tried X; failed because Y", so they aren't retried.

Clearing and compaction against the cache

Here the two goals of this chapter collide. Clearing an old tool result edits the history, so the cached prefix breaks at the first cleared block and the next call re-writes everything after it. Clearing a little on every turn would break the cache on every turn. So clear in batches: wait until a threshold, clear a lot at once so the context drops well below it, then let the prefix grow and cache again. In the sketch above, clearing at 100K and keeping only the newest two results drops the context far under the threshold, so the next clear is several steps away rather than one.

There's a second constraint you met in Chapter 05. On models whose thinking blocks carry a signature bound to the earlier conversation, rewriting earlier history on the client side can invalidate the thinking that follows it, or get the request rejected. Two ways around it:

  • Use the provider's server-side features. The Anthropic API offers context editing, which clears old tool results and thinking blocks once thresholds are crossed, and server-side compaction, which summarizes earlier context into a compaction block. Both are designed to work with these rules.
  • Compact client-side in the simple shape. The new context is the summary as a single user message, followed by the next turn. No older turns are replayed, so no old thinking needs to validate. This is what the sketch's return line does.

And never cut between a tool_use and its tool_result. A request with an orphaned half is invalid.

Pitfall

The summary drops the one constraint that mattered. At step 40 the user said “don't touch shared/clock.py”. At step 90 the context is compacted, the summary mentions the bug and the fix but not the constraint, and at step 95 the agent edits the file. Summaries are lossy and nobody checks them. Defenses: keep standing constraints outside the region that gets summarized (system prompt, project file or a notes file that's re-read). Have the compaction prompt list the kinds of things to keep. Test compaction directly: run the same task with and without it and diff the outcomes. Anthropic's post suggests tuning a compaction prompt for recall first, so nothing important is lost, and then trimming for precision.

Structured notes and scratchpads

Compaction has a summarizer decide what mattered, after the fact. Structured notes have the agent decide while it's working, when it knows best. The agent writes its progress to a file outside the context window (a NOTES.md, a to-do list, a progress log) and reads it back when it needs to: after a compaction, at the start of a new session, or when it has lost the thread.

Why this works: the notes are short, they're written by the agent while it knows what matters, and they live outside the window, so they survive anything that happens to it. Some variations:

  • A to-do list the agent updates as it goes. It's a plan (Chapter 05) that persists, and the next item is always visible.
  • A scratchpad file for bulky work in progress, such as a table being filled in or partial results. The conversation holds only a pointer, and the agent reads back the part it needs.
  • Machine-readable state such as a JSON file of test results that both the agent and the harness read. Use it when code, not just the model, needs to know progress.
  • Version control as a log. Commit messages are notes with timestamps and diffs attached.

The costs: the agent must be told to write notes and to read them, notes are tokens too when they're read back, and notes can go stale or contradict each other. Once notes outlive a session, they're memory, and Chapter 07 covers the risks.

Sub-agents as context isolation

A sub-agent is a separate loop with its own fresh context window. The lead gives it a task, it explores as long as it needs to, and it returns a condensed result. All the file reads, dead ends and search results stay in the sub-agent's window. The lead only ever sees the task it sent and the result it got back.

Anthropic's write-up of its multi-agent research system (2025) describes this as the core benefit: sub-agents search in parallel, each in its own context window, and condense what they found for the lead. The same post is candid that the approach uses far more tokens in total than a single agent. Chapter 14 weighs that trade.

What you trade for a clean lead context:

  • Information loss at the boundary. The lead knows only what the summary says. A detail the sub-agent judged unimportant is gone, and the lead can't tell that it's missing. Chapter 16 calls this the telephone game.
  • Total tokens. The lead's context shrinks, but every sub-agent pays for its own prefix and history. If two sub-agents read the same files, you pay twice. The next section does the arithmetic.
  • The handoff is now a design problem. What does the child receive (the whole parent context, or a distilled task)? What must it return? A return contract with a size cap, the evidence (paths, IDs) and a list of what it didn't check makes the lead's next decision better informed.
  • Caching. A sub-agent with its own system prompt and tools has its own cache. It doesn't disturb the lead's cache, which is also why a sub-agent can use a cheaper model without breaking the lead's prefix. Siblings with an identical prefix can share one cache entry if you stagger the first request, as described in the caching section.

The token growth math, revisited

Chapter 01 derived how input tokens add up over an agent run. If every call re-sends a base of b tokens plus a history that grows by a tokens per step, then over n steps:

total_input ≈ n·b + a · n(n − 1) / 2

The second term grows with the square of n. Each technique in this chapter attacks it differently. Take Chapter 01's numbers (b = 2K, a = 4K) and 30 steps of work:

StrategyWhat happensArithmeticTotal input
One agent, no managementHistory grows 4K every step for 30 steps30·2K + 4K·(30·29/2) = 60K + 1,740K≈ 1.8M
One agent, history capped at 40K by clearingGrows for the first 10 steps, then holds at about 42K per call(10·2K + 4K·45) + 20·42K = 200K + 840K≈ 1.0M
Lead plus 3 sub-agentsLead: 6 steps, adding 2K per step. Each child: 8 steps from an empty historyLead: 6·2K + 2K·15 = 42K. Children: 3 × (8·2K + 4K·28) = 3 × 128K≈ 0.43M

The mechanisms are worth stating in general form:

  • A cap turns quadratic into linear. Once history is held at a ceiling H, each further call costs about b + H, so the total after that point grows in a straight line with n.
  • Splitting divides the quadratic term. Cut n steps into m independent contexts of n/m steps each and the quadratic part goes from about a·n²/2 to about m · a·(n/m)²/2 = a·n²/(2m). Three children cut it to about a third, plus the lead's own small cost. This is your Predict answer 3.
  • Caching changes the price of those tokens, not their number. A cached token is cheaper and faster, but it's still in the window, competing for attention.

The sub-agent row assumes the three pieces of work are independent. If the children need each other's findings, you pay in one of two ways: duplicated reading (tokens go back up) or missing information (quality goes down). That's the question Chapter 14 asks before you reach for multiple agents.

Common misconceptions
  • “The window is 1M tokens, so I don't need to manage context.” Capacity isn't the same as effective use. Lost in the middle, context rot and distractors all get worse as the window fills.
  • “Caching makes long context free.” It makes it cheaper and faster. The tokens are still there for the model to wade through.
  • “input_tokens is my prompt size.” With caching it's only the uncached remainder. Sum all three input fields.
  • “A summary keeps everything important.” It keeps what the summarizer thought was important at that moment. Test it.
  • “More retrieved documents, better answers.” Past a point, extra documents are distractors.
  • “Sub-agents save tokens.” They keep the lead's context small. Total tokens often go up.

  • Stage 4 · ordering. Does your prompt builder put the stable parts first? Is anything that changes per agent or per call (agent ID, remaining budget, depth, a timestamp) placed early? Where should the remaining-budget line go so it doesn't break the prefix every call?
  • Stage 5 · what crosses the boundary. The plan asks: what context goes from parent to child, everything or a distilled objective? What comes back, full output or a summary? Answer with Figure 6.6 in mind. What is the token cap on a child's result, and is it enforced by the prompt or by code?
  • Stage 5 · fan-out and the cache. Siblings spawned together often share a prefix. Do you fire them all at once (simplest) or send one first so the rest read its cache? Is the extra latency worth it at your scale? You can measure this from the usage fields.
  • Stage 5 · does any agent need compaction? If child loops have a low iteration limit, maybe no context ever gets near the window. Which is simpler to test with your fake client: compaction logic, or a limit that makes it unnecessary?
  • Stage 6 · counting. Does your budget meter sum input_tokens, cache_read_input_tokens and cache_creation_input_tokens? Your cost report should show cache reads separately, or you can't tell whether ordering is working.

Check yourself

Answer each one out loud or on paper before you open it.

Recall Give three reasons a bigger context can make an agent worse, from mechanism to measurement.

Mechanism: attention weights are normalized to sum to 1, so every added token competes for a share of the same budget, and the number of token pairs grows with the square of the length. Models also see fewer very long sequences in training. Measurement: lost in the middle (Liu et al.): information in the middle of a long context is used worst. Measurement: context rot (Chroma) and RULER (Hsieh et al.): performance falls as input grows, effective length is shorter than the advertised window, and distractors make it worse. An agent's history is full of distractors.

Recall In what order does the API render a request for caching, and what rule follows from it?

tools, then system, then messages. Caching is a byte-exact prefix match, and any change invalidates everything after it. So: stable content first and volatile content last. Never-changing material goes earliest, per-session material next, per-turn material at the end, and anything that changes on every request is removed or moved to the very end. Changing the tools or the model invalidates everything.

Apply A response reports cache_read_input_tokens: 41000, cache_creation_input_tokens: 900, input_tokens: 3100. How big was the prompt, and is caching healthy?

The prompt was 41,000 + 900 + 3,100 = 45,000 tokens. A meter reading only input_tokens would say 3,100. Caching looks healthy: a large read and a small write is the signature of a prefix that grows without changing. The 3,100 is content after the last breakpoint. If that's the newest turn, fine. If it's large and recurs every call, move the breakpoint later so it gets cached.

Apply A 20-step run with b = 2K and a = 4K. What's the total input with no management, and with history capped at 40K by clearing?

No management: 20·2K + 4K·(20·19/2) = 40K + 760K = 800K, as in Chapter 01. Capped: the first 10 steps cost 10·2K + 4K·45 = 200K, and the remaining 10 steps cost about 42K each, so 420K. Total ≈ 620K, about a quarter less. At 30 steps the cap saved almost half (1.8M to 1.0M). The longer the run, the more a cap is worth, because it turns the quadratic tail into a straight line.

Apply You spawn five sub-agents with an identical 20K prefix at the same instant. How many read the prefix from cache?

None. A cache entry becomes readable only once the first response begins streaming, so all five requests arrive before any entry exists and all five pay to write it. To share it, send one request, wait for its first token, then send the other four, which can then read the 20K prefix. The cost is one time-to-first-token of extra latency. Whether that's worth it depends on prefix size and how often you fan out, and the usage fields tell you whether it worked.

Design An agent answers questions about a 3,000-file repository. What do you preload, and what do you leave to just-in-time retrieval?

Preload what's needed on almost every step and can't be discovered cheaply: conventions, a short map of where things live, hard constraints, how to build and run tests. That's a few thousand tokens at most. Leave file contents to just-in-time retrieval through glob, grep and a bounded read_file whose truncation notes tell the agent how to read more. The directory listing itself is a set of identifiers that carry signal. Then watch the traces. If the agent often fails to find things, improve tool descriptions or add a search tool (Chapter 07's retrieval), rather than preloading more.

Design After a compaction, the agent edits shared/clock.py, which the user forbade 50 steps earlier. What failed, and what are three defenses?

A standing constraint lived only in the part of the history that got summarized, and the summary dropped it. Defenses: (1) keep standing constraints out of the summarizable region, in the system prompt, a project file or a notes file that's always re-read; (2) make the compaction prompt list the kinds of things that must survive, constraints first, and test it by running tasks with and without compaction and comparing; (3) don't rely on the model at all for hard rules: the harness's file-write tool refuses paths under shared/. The model proposes and the harness disposes (Chapter 08). Permission checks in code survive any context loss.

Interview “Context windows are a million tokens now. Why does context engineering still matter?”

Capacity isn't effective use. Benchmarks such as RULER show effective length below the advertised window, and lost-in-the-middle and context-rot results show that the position of information and the presence of distractors matter. Cost and latency scale with tokens, and in an agent loop input tokens grow with the square of the step count. Caching lowers the price of a stable prefix, but the model still attends to all of it. So the work remains: order for the cache, prune for attention (clear tool results, compact), retrieve just in time, keep durable notes, and isolate exploration in sub-agents. Then measure, because which levers matter depends on the task and the model.

Recall card

Five lines to rehearse. If you can expand each into a minute of explanation, you know this chapter.

  1. Context is a budget, not a container: find the smallest set of high-signal tokens. In a long run, old tool results are most of the window.
  2. More tokens dilute attention: lost in the middle, context rot, distractors. Instructions go first, the current goal goes last.
  3. Caching is a byte-exact prefix match over tools, then system, then messages. Stable first, volatile last. It makes tokens cheaper, not fewer.
  4. Retrieve just in time through identifiers and bounded tools. Remove with clearing (light, re-fetchable) or compaction (lossy), in batches, never mid tool round.
  5. Notes persist what matters outside the window. Sub-agents isolate exploration and split the quadratic term, at the cost of what the summary leaves out.
