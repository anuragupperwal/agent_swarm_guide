The agent loop

Strip away the frameworks and every agent is the same small program: call the model, run what it asks for, show it the results, repeat until something says stop. This chapter takes that loop apart piece by piece, runs it once step by step, and spends a long time on the part people get wrong: how it ends.

The big idea

Chapter 02 drew the agent line: the model chooses the next action, sees its result, and decides when it's done. This chapter is about the program that makes that possible. It's surprisingly short. The core is about twenty lines of code, and every agent product you've heard of has a version of it at the center.

Key idea

The loop is easy. The edges are the work. Writing “call, act, observe, repeat” takes a minute. Deciding what the model may do, what it sees, what happens when a step fails, and who is allowed to end the run is where reliable agents are separated from demos. Your harness is mostly edges.

One framing to keep from Chapter 01: the model never runs anything. In every iteration it writes a proposal, your code decides whether and how to act on it, and your code writes the result back into the conversation. The loop is the place where “LLM proposes, framework decides” actually happens, once per step.

Anatomy: the minimum pieces

Take any agent and remove things one at a time. The pieces you can't remove without it becoming something else (a function, a chatbot, or a program that never ends) are its minimum anatomy. There are seven.

PieceWhat it isRemove it and you get…In the trace below
Modelthe policy: chooses the next action given everything so faran ordinary programthe four model calls
Instructionsthe system prompt: goal, rules, when to stop, how to use toolsan agent with no idea what “done” means“answer ops questions using the tools”
Toolsan action space: names, schemas, and code that runs thema chatbot. It can talk about the world but can't touch itquery_logs, read_config
Loopthe driver that calls, acts and feeds back, repeatedlya single call or a router (Chapter 02's example b)steps 1–4
Statethe message history plus counters (steps, tokens, time)an agent that forgets each result immediately, because the model is statelessthe growing messages list
Stop conditionrules that end the run: model says done, or a limit firesa program that may never end, or ends without a statusend_turn at step 4
Environmentwhatever the tools act on and observenothing to get feedback from: the model grades its own guessesthe log store and config

Two things to notice. First, “memory”, “planning” and “reflection” aren't on the list. They're useful, and Part 2 covers them, but an agent works without them. Second, the environment is on the list even though you don't write it. An agent's quality depends on the feedback it gets, and the feedback comes from the environment. That's why coding agents work comparatively well: compilers and tests give fast, honest feedback.

The vocabulary underneath

Agents existed in AI long before LLMs. Russell and Norvig's textbook definition is still the cleanest: an agent is “anything that can be viewed as perceiving its environment through sensors and acting upon that environment through actuators.” The LLM version borrows its vocabulary from reinforcement learning, and research papers use these words without defining them:

environment
Everything outside the agent that its actions affect and its observations come from.
action
One thing the agent does: a tool call with arguments, or a final answer.
observation
What comes back from the environment after an action: a tool result, including errors.
policy
The rule for choosing an action given what's been seen. Here, the model plus its instructions and context.
trajectory
The full sequence of observations and actions in one run. In practice, the message history. Also called a trace or rollout.
episode
One run from task to stop.
step
One iteration of the loop: one model call, then zero or more tool runs.

The CoALA framework (Sumers et al., 2024) extends this into a full architecture for language agents, with separate memory modules and internal actions such as reasoning and retrieval. You'll meet it again in Chapters 05 and 07. For now, the seven pieces are enough.

The loop in code

Here is a textbook version with all seven pieces. It's plain Python with a generic llm.complete(...) client. The message shapes follow the usual pattern: the assistant's tool requests are content blocks with an id, and each result goes back as a tool_result block that names the tool_use_id it answers. Chapter 04 covers that protocol in detail.

textbook agent loop · for understanding, not for copying

async def run_agent(task, tools, llm, limits):
    messages = [{"role": "user", "content": task}]          # state
    budget = Budget(limits.max_total_tokens)

    for step in range(limits.max_steps):                         # loop, bounded by code
        reply = await llm.complete(
            system=INSTRUCTIONS,                                    # instructions
            tools=[t.schema for t in tools.values()],              # tool definitions
            messages=messages,                                      # the whole history, every time
        )
        budget.charge(reply.usage)                                  # code counts, not the model
        messages.append({"role": "assistant", "content": reply.content})

        if reply.stop_reason == "end_turn":                       # the model says it's done
            return Result("done", output=reply.text, steps=step + 1)
        if reply.stop_reason != "tool_use":                       # max_tokens, refusal, ...
            return Result("failed", reason=reply.stop_reason, steps=step + 1)

        results = []
        for call in reply.tool_calls:                               # act
            try:
                output = await tools[call.name].run(**call.input)
                results.append({"type": "tool_result", "tool_use_id": call.id,
                                "content": output})
            except ToolError as e:                                  # errors are observations
                results.append({"type": "tool_result", "tool_use_id": call.id,
                                "content": str(e), "is_error": True})
        messages.append({"role": "user", "content": results})       # observe

        if budget.exhausted():                                      # a limit fires
            return Result("stopped", reason="budget", steps=step + 1)

    return Result("stopped", reason="max_steps", steps=limits.max_steps)

Read it again and find each of the seven pieces. Then look at the two highlighted lines. They're the ones beginners leave out:

  • The assistant message is appended before the tool results. The provider checks that every tool_result answers a tool_use in the immediately preceding assistant message. Skip the append and the next call is rejected, or the model loses track of what it asked for.
  • All results from one step go back in one user message. If the model asked for two tools, both results travel together. Splitting them across messages teaches the model to stop calling tools in parallel (Chapter 04).

Every call has a status. The function never just returns text: it returns done, failed or stopped, with a reason and a step count. A caller, such as a parent agent in your swarm, can't make a good decision about a child without knowing how it ended.

What this version doesn't handle

It's written to be read, not run in production, and your Stage 5 loop is yours to design. Things it ignores on purpose, each covered later:

  • A model asking for a tool that doesn't exist: tools[call.name] raises KeyError, which isn't a ToolError, so the loop crashes (Chapter 04).
  • Timeouts on the model call and on each tool, and cancellation (Chapter 10).
  • Retries for transient API errors such as rate limits and overload (Chapter 11).
  • Running independent tool calls in parallel instead of one by one (Chapters 04, 10).
  • Context growth: by step 30 the history may not fit (Chapter 06).
  • Tracing each step, and loop detection (Chapters 11, 13).
  • The budget is checked after the call, so the last call can overshoot. Where would you check it instead, and what would you need to know in advance?

Three things in this trace are worth a second look:

  • Step 2 is the agent working, not failing. The tool error came back as an observation, the model read it and corrected itself. If the loop had raised instead, the run would have died on a typo. This answers Predict question 3: a tool error is usually data for the model, not an exception for the harness. The exceptions are errors the model can't fix, such as an expired credential, which should stop the run.
  • The error message did half the work. “Top-level keys: alerts, db, cache” told the model what to try next. A bare “KeyError” would have made it guess. Writing error messages for a model to read is part of tool design (Chapter 04).
  • The final answer is a claim. end_turn means the model stopped asking for tools. It doesn't mean the answer is right. Here you can check it: 1840 − 1500 = 340. Often you can't, which is the subject of the stop-conditions section.

How the loop ends: stop conditions

A loop with no exit is a bug. A loop with only one exit, “the model says it's done”, is a bug that hasn't happened yet. Stop conditions come from two places, and a reliable agent needs both.

Natural end (end_turn)modeldone (claimed)a confident wrong answer looks exactly like a right one

Key idea

end_turn means “the model stopped asking for tools.” It does not mean “the task succeeded.” Treat the model's “done” as a claim to verify whenever verification is cheap: run the tests, validate the output, check the file exists. When the check fails, send the failure back as an observation and let the loop continue, within its limits. That turns a false “done” into one more step instead of a wrong answer.

Code-enforced limits are not a sign of distrust. They exist because the model can't see them. It doesn't know how many steps it has used, what they cost, or how long it's been running, unless you tell it. Some harnesses do tell it (“you have 3 steps left, wrap up”), which gives the model a chance to finish gracefully rather than be cut off. That's a design choice worth making on purpose.

Agent vs function

From the outside, an agent can look exactly like a function: you call it with a task and get a result back. The difference is inside.

Function (even one that calls an LLM)Agent
Control flowfixed in code; you can read itchosen at run time; you can only see it in the trace
LLM calls per runa known number1 to max_steps, varies per run
Cost and latencyroughly constanta distribution with a long tail
Testingunit tests with fixed inputsa scripted fake model for the harness; many real runs for behavior
How it failsraises, or returns a wrong valuealso: wanders, loops, stops early, claims false success
Return valuethe outputthe output plus how it ended: status, reason, steps, usage

The last row is the one that matters for a swarm. If run_agent is an async function that returns a Result, then a parent agent can start one as a coroutine (Chapter 10), wait for it or not, and decide what to do based on its status. “Spawning a child agent” is, at its core, the harness running this function on the parent's behalf, after deciding the parent is allowed to. That's the bridge to your Round 2 Q2, and Chapter 16 builds it out fully.

Variations on the same loop

Almost every agent design you'll read about is this loop with one part changed. Recognizing which part was changed is a fast way to understand a new paper or framework.

Bugs everyone writes once
  • Forgetting to append the assistant message. The tool results then answer requests the API can't see, and the call is rejected.
  • Mismatched IDs. Each tool_result must carry the tool_use_id of the request it answers. Make one up, or reuse one, and the request fails.
  • Treating end_turn as success. It's a claim. Verify when you can.
  • No step limit, “because the model will stop.” One bad observation can make it retry the same thing forever.
  • Crashing on tool errors, or the opposite: swallowing them. Hiding an error from the model (returning an empty result) is worse than crashing, because the model then reasons from false data.
  • Dumping huge tool outputs into the context. A 50,000-token log result is in every later call. Truncate, summarize, or page it.

Check yourself

Answer each one out loud or on paper before you open it.

Recall Name the seven minimum pieces of an agent, and what you get if you remove each one.

Model (no model: an ordinary program). Instructions (no instructions: no definition of the goal or of done). Tools (none: a chatbot). Loop (none: a single call or a router). State (none: each result is forgotten). Stop condition (none: it may never end, or ends without a status). Environment (none: no feedback, so the model grades its own guesses).

Recall Why must the assistant message be appended before the tool results, and why do all results from one step go in one message?

Each tool_result must answer a tool_use block in the immediately preceding assistant message, so that message has to be in the history. Results from one step go back together in one user message because that's what the protocol expects for parallel calls, and splitting them discourages the model from making parallel calls in future.

Apply Your coding agent returns done after 2 steps saying “Fixed the bug.” The tests still fail. What went wrong in the harness, and what would have caught it?

The harness treated end_turn as success. A goal check would have caught it: on end_turn, run the tests. If they fail, append the failure output as an observation and continue the loop, within the step limit. The model's “done” becomes a request to be checked.

Apply The model calls read_config {"key": "alerts.5xx"} four times in a row, getting the same error each time. Which part of the loop should catch this, and what should it do?

A loop detector, which is a code-enforced stop condition: compare (tool name, input) across recent steps. On the first repeat, it can add a note to the observation (“you already tried this; it failed the same way”). On the third, it stops with a status that says why. The step limit catches it eventually, but only after wasting every remaining step.

Design Design the stop policy for a coding agent that must never run longer than 10 minutes and must never report success when the tests fail.

A wall-clock timeout of 10 minutes with real cancellation of in-flight calls; a step limit and token budget as backstops; loop detection on repeated tool calls; and a verifier on every end_turn that runs the tests. If the tests fail, the failure goes back as an observation. The run can only return done when the tests pass. Every other exit returns stopped or failed, with the reason and the last test output, so the caller knows what it's holding.

Interview “What's the difference between an agent and a function that calls an LLM?”

In a function, the control flow is fixed in code and the LLM fills in content. In an agent, the LLM chooses the next action, sees its result and decides when it's done, in a loop. Consequences: an agent's cost and step count vary per run, it can fail in new ways (looping, false success), and it has to return how it ended, not just an output. Then say that an agent can be wrapped as a function, and that this is how delegation between agents works.

Interview “Walk me through one iteration of an agent loop.”

Send the system prompt, tool definitions and full message history to the model. Charge the usage to the budget. Append the assistant reply to the history. Branch on stop_reason: on end_turn, verify if possible and return; on tool_use, validate and run each requested tool, turning errors into is_error results; on anything else, return a failure. Append all the results as one user message, check the limits, and go round again. Mention the things you'd add in production: timeouts, retries, parallel execution, context management and tracing.
