Control flow and state

At every moment a harness must answer two questions: what runs next, and what is true now. This chapter makes both answers explicit data: a state machine for each agent's lifecycle, a graph for what runs next, reducers for merging updates, checkpoints for pausing and resuming, and an event log that records it all.

The big idea

Chapter 08 named the loop driver. This chapter is about what the driver drives. Every harness, at every moment, holds two things: control (which piece of work runs next) and state (everything the run knows so far).

The simplest harness keeps both implicitly. Control is wherever the Python interpreter happens to be in your while loop. State is local variables on the call stack. That works until you need to pause, resume, inspect or test the run. Then you discover it all lives in a process's memory, and dies with it.

Key idea

Make the run a value. When control and state are explicit data (a status field, a named next step, a state record, a log of events), the run can be saved, inspected, paused, resumed, replayed and tested. When they live only in the call stack, a crash erases them.

Each section below makes one more piece explicit. Status becomes a state machine. “What runs next” becomes a graph. “How updates combine” becomes reducers. “Where we were” becomes checkpoints. “What happened” becomes an event log.

The agent lifecycle as a state machine

Start with the smallest explicit thing: one field saying what condition an agent is in. A finite state machine turns that field into a contract. Six terms are enough:

State
A named condition the agent is in, such as running. Exactly one at a time.
Event
Something that happened, such as children_done. Events are the only things that change state.
Transition
A rule: in state X, on event E, move to state Y. Any pair not listed is illegal.
Guard
An extra condition on a transition, such as “only if the output validated”.
Terminal state
A state with no way out. A finished agent never starts again; a retry is a new attempt with a new record.
Invariant
Something always true, for example “every agent ends in exactly one terminal state”.

In code, a state machine is a lookup table plus one function that refuses everything the table doesn't allow. The table is the whole design, and it fits on one screen.

A transition table and the only function allowed to change status

TRANSITIONS = {                                    # (state, event) -> next state
    ("created", "registered"):              "queued",
    ("queued", "slot_free"):                "running",
    ("running", "spawned_children"):        "waiting_on_children",
    ("waiting_on_children", "children_done"): "running",
    ("running", "needs_human"):             "waiting_on_human",
    ("waiting_on_human", "answered"):       "running",
    ("running", "final_valid"):             "succeeded",
    ("running", "error"):                   "failed",
    ("running", "limit_hit"):               "budget_exceeded",
}
TERMINAL = {"succeeded", "failed", "cancelled", "budget_exceeded"}

def transition(agent, event):
    if agent.status in TERMINAL:
        raise IllegalTransition(f"{agent.id} already {agent.status}")
    if event == "cancel":
        new = "cancelled"                           # legal from any non-terminal state
    else:
        new = TRANSITIONS.get((agent.status, event))
        if new is None:
            raise IllegalTransition(f"{event} not allowed in {agent.status}")
    tracer.emit("transition", agent_id=agent.id, old=agent.status, new=new, on=event)
    agent.status = new

Two details carry most of the value. First, an illegal transition raises. That's a bug in your harness, not a failure of the agent, so it should crash loudly in tests rather than turn into a Result. Second, every transition is traced. If the tracer records each (old, new, event), you can rebuild any agent's whole life from the log, which is where this chapter ends.

When a flat machine grows too many states, David Harel's statecharts (1987) add nesting. running can contain sub-states such as thinking and acting, and one “cancel” arrow on the outer state covers all of them. That's the idea behind the dashed boundary in Figure 9.1.

Explicit vs implicit control flow

A state machine says what condition an agent is in. Control flow says what work runs next. There are two places that decision can live.

In implicit control flow, the next step is whatever the model asks for. The agent loop from Chapter 03 is the purest case: call the model, do what it requested, repeat until it stops. The program never names the steps in advance. You only learn the path by running it.

In explicit control flow, the program declares the possible steps and the paths between them before anything runs. A model may still choose which path to take at a branch, but only among paths the program declared.

Implicit (model-driven loop)Explicit (declared graph)
Who picks the next stepThe model, every stepThe program, sometimes asking a model to pick among declared edges
Handles surprisesWell: it can take any path the tools allowOnly along paths you foresaw
TestingHard: the path changes run to runEach node and each edge can be tested alone
Pause and resumeYou have to invent a place to stopNatural: save the state and the name of the next node
Typical failureWanders, loops, stops earlyRigid: the task needed a path you didn't draw

This is Chapter 02's workflows-versus-agents distinction, seen from the harness side. Real systems mix them. Your swarm harness is a good example. Which children get spawned is implicit: the planner decides. But how each agent moves through its life is explicit: Figure 9.1, or whatever you design instead. Getting that split right is most of the design work.

Graphs: nodes, edges, conditional edges

A graph is the standard way to write explicit control flow down. It needs only three ideas:

Node
A unit of work: a function that reads the state and returns an update to it. A node can call a model, run a tool, or do plain computation.
Edge
A fixed rule: after node A, run node B.
Conditional edge
A function of the state that returns the name of the next node. This is where branching and looping live.

Cycles are allowed, and they matter. A graph with no cycles is a pipeline. The cycle (check, then back to act) is what lets a graph behave like an agent while staying inspectable.

Declaring the graph and running it are separate. Here is the declaration, then a runner that can execute any graph declared this way.

Declaring the graph in Figure 9.3

g = Graph()
g.add_node("plan", plan)                    # each node: state -> partial update
g.add_node("act", act)
g.add_node("check", check)
g.add_edge("plan", "act")
g.add_edge("act", "check")
g.add_conditional_edge("check", route, allowed={"act", "plan", END, STOP})

def route(state):
    if state["budget_left"] <= 0:    return STOP
    if state["verdict"] == "done":   return END
    if state["verdict"] == "replan": return "plan"
    return "act"

A runner for any such graph

def run_graph(g, state, start="plan", max_steps=50):
    node = start
    for step in range(max_steps):
        if node in (END, STOP):
            return state, node
        update = g.nodes[node](state)              # run one node
        state = apply_update(state, update)        # reducers decide how to merge
        nxt = g.next(node, state)                  # fixed edge or conditional edge
        if nxt not in g.allowed_after(node):
            raise BadRoute(node, nxt)                # the router invented a path
        save_checkpoint(state, next_node=nxt, step=step)
        node = nxt
    return state, STOP                             # step limit: a stop, not a hang

Look at what the runner checks. If the router is a model call, its answer is a proposal, and allowed_after disposes of it, exactly as in Chapter 08. The runner also saves a checkpoint after every node, and it stops at max_steps even if every router keeps saying “continue”.

LangGraph formalizes exactly this abstraction: a state schema, nodes that return partial updates, fixed and conditional edges, reducers on state keys, and a checkpointer. Once you've written the 20 lines above yourself, its documentation reads as a description of choices you've already met.

State and reducers

In the runner, a node returns an update, not a whole new state. Something has to combine the update with the existing state. With one node at a time, “overwrite each key” almost works. With nodes running in parallel, it fails badly. A reducer is the rule, declared per key, for combining an old value with a new one.

A worked merge

Two branches, A and B, start from the same state and run in parallel. B finishes first, then A.

Start state

notes = ["plan"]
tokens_used = 1000
verdict = None

Branch A returns

notes: ["fact A"]
tokens_used: +400
verdict: "needs_more"

Branch B returns

notes: ["fact B"]
tokens_used: +700
verdict: "done"

KeyOverwrite (last writer wins)Declared reducer
notes["fact A"]. B's note and the plan are both lost.append: ["plan", "fact A", "fact B"]
tokens_used400. The run now under-reports by 1,700 tokens.add: 1000 + 400 + 700 = 2100
verdict"needs_more", only because A happened to finish lastNo safe default. You must declare a rule: raise on conflict, or “done only if every branch says done”.

Every overwrite result depends on which branch finished last, which is timing, which is luck. The bug won't show up in a test that runs branches one at a time. It will show up in production, intermittently.

Reducers per key, applied in a fixed order

def append(old, new):    return old + new
def add(old, new):       return old + new      # only correct if updates are deltas
def overwrite(old, new): return new

REDUCERS = {"notes": append, "tokens_used": add}   # verdict: needs its own rule

def apply_updates(state, updates):
    out = dict(state)
    for u in sorted(updates, key=lambda u: u.branch):   # branch order, not finish order
        for key, value in u.values.items():
            out[key] = REDUCERS.get(key, overwrite)(out[key], value)
    return out

Two rules hide in those lines.

  • The reducer and the update must mean the same thing. If A reports its total (1,400) instead of its delta (+400), the add reducer gives 1000 + 1400 + 1700 = 4,100, which is wrong in a new way. Decide once whether updates are deltas or absolutes, per key, and write it down.
  • Apply in a fixed order. Sorting by branch, not by finish time, makes the merged list identical on every run and every replay. Without it, notes comes out in a different order each time.
Key idea

A parent aggregating its children's Results is running a reducer. Every question above applies to your swarm: what each child contributes, in what order it's merged, and what a failed child adds. A child's spending is a delta charged to a shared total, which is the tokens_used row exactly.

Checkpoints, resume, replay and fork

A checkpoint is a saved copy of the state plus the name of the next step, keyed by run and step number. The runner above saves one after every node. That one line buys four abilities:

  • Resume: after a crash, load the latest checkpoint and continue.
  • Inspect: answer “what did the state look like at step 3?” without guessing.
  • Fork: load step 2, change something, and run on from there as a new branch, keeping the original.
  • Replay: re-run steps to reproduce a bug exactly.
Starts fromCalls the model again?Result
ResumeThe latest checkpointYes, for the steps not yet doneThe same run, finished
ForkAny checkpoint, with edited stateYesA new branch beside the original
ReplayAny checkpoint, or the startNo: recorded outputs are fed backIdentical states, for debugging

Replay is the subtle one. Re-running a step from a checkpoint calls the model again, and the model will write something different (Chapter 01). To reproduce a run you must record every non-deterministic input as it happens: model replies, tool results, clock readings, random numbers. A replay then feeds the recordings back instead of making the calls. That's your Stage 4 fake LLM, given a script recorded from a real run.

Pitfall · the checkpoint between propose and execute

Suppose a checkpoint is saved after the model proposed send_email but before you know whether the email went out. The process crashes. On resume, do you send it? If you do, it may go twice. If you don't, it may never go. A checkpoint alone can't answer this. The next section can.

Durable execution and idempotency

Every side effect has a dangerous window: after the effect happened, before your harness recorded that it happened. A crash in that window leaves you with two bad options on restart.

  • Don't retry (at-most-once): the effect may be lost.
  • Retry until recorded (at-least-once): the effect may happen twice.

You can't make the window disappear. What you can do is make the second attempt harmless. An operation is idempotent if doing it twice has the same effect as doing it once. “Set the status to succeeded” is idempotent. “Add 5 to the counter” is not. Retrying until recorded, combined with idempotent operations, gives you what people loosely call exactly-once: the effect happens once, even when the code runs more than once.

When an operation isn't naturally idempotent, give it an idempotency key: a unique id for one intended effect, built so that every retry of that effect carries the same key. The receiver remembers the keys it has processed. When a repeat arrives, it returns the stored result instead of acting again. Many payment and messaging APIs accept a key like this for exactly this reason.

OperationIdempotent as written?To make retries safe
Read a fileYesNothing needed
Write a file's whole contentYesNothing needed
Append a line to a fileNoCheck for a marker first, or write the whole file
Send an emailNoIdempotency key, deduplicated by the sender service
Charge a cardNoIdempotency key, which payment APIs commonly accept
Spawn a child agentNoA deterministic child id; “create” does nothing if that id exists

The last row is yours. If a parent crashes after creating its children but before recording that it did, a naive resume creates a second set. Now two copies of each child do the same work and spend from the same budget.

Durable execution, Temporal-style

Durable execution systems, of which Temporal is the best-known example, turn these ideas into a runtime. Code is split in two:

  • Workflow code decides what to do. It must be deterministic: given the same inputs and history, it makes the same calls in the same order.
  • Activities do anything non-deterministic or external: model calls, tool calls, HTTP, the clock.

Each activity's result is appended to an event history that is saved durably. If the worker crashes, another worker runs the workflow code again from the top. Each activity call first looks in the history. If a result is recorded, it returns that result without running anything. The first activity with no recorded result is where real execution resumes.

The core of an activity call, in plain Python

def activity(run, name, fn, *args):
    key = f"{run.id}:{run.next_seq()}:{name}"   # n-th activity in workflow order: same on every attempt
    if key in run.history:                      # finished before the crash
        return run.history[key]                  # replay: return the recording, don't run
    result = fn(*args, idempotency_key=key)       # the receiver dedupes on the key
    run.history.save(key, result)                 # durable write before moving on
    return result

Now you can see why workflow code must be deterministic. The key depends on next_seq(), the position of this call in the workflow's order. If attempt 2 calls activities in a different order, because it read the clock or a random number, the keys stop lining up with the history. Then replay hands step 3's result to step 4. That's why the clock and randomness have to go through activities too.

It also solves the replay problem from the last section. A model call is an activity, so its reply is in the history. Attempt 2 doesn't ask the model again; it reads what the model said the first time.

Scope

You don't need Temporal for your harness, and Stage 6 doesn't ask for it. The point is the mechanism: record results durably, rebuild by replaying, key every side effect. You can apply it to your own JSONL log and your own spawn function at whatever depth Stage 6 needs.

Human-in-the-loop interrupts

An interrupt is a planned pause. The run saves a checkpoint, records what it's waiting for, moves to waiting_on_human, and releases its process. When the answer arrives, whether seconds or days later, the harness loads the checkpoint and continues, with the answer as a new input.

Compare that with calling input() inside the loop. A blocking call holds a process, a connection and an open slot the whole time. It dies on every deploy or restart, and a thousand waiting runs need a thousand live processes. A durable interrupt holds nothing except a row in the state store.

Four kinds of interrupt cover most needs:

  • Approve or reject a proposed action.
  • Edit the proposal before it runs, for example changing an email's recipient.
  • Answer a question the agent asked.
  • Review an output before anything downstream uses it.
Run r19 · an approval that waits two hours
tool_usesend_email {"to": "all-staff@example.com", "subject": "Q3 results draft"}
harnesspolicy: ask (external send) · checkpoint saved at step 6 · status running → waiting_on_human · process released
reviewer(2 h 10 min later) Edit: to = "finance-team@example.com". Approve.
harnessload checkpoint step 6 · status waiting_on_human → running · apply edit · execute with key r19:6:send_email · approver recorded
tool_resultSent to finance-team@example.com
answerDraft sent to the finance team for review, as edited by the reviewer.

To resume, the harness needed five things: the run id, the checkpoint, the pending proposal (with its tool_use_id), the human's response, and who gave it. The last one is for the audit trail. If any of the five isn't stored, the run can't be resumed safely.

Pitfall · what runs twice on resume

Some frameworks resume an interrupted node by running it again from its beginning; LangGraph documents this behavior. Anything the node did before the interrupt point then happens twice. Put side effects after the interrupt, or make them idempotent. It's the durable-execution problem again, in a smaller form.

Event sourcing

There are two ways to store a run.

  • State-based: store the current state and overwrite it on every change. The answer to “what is true now?” is one read. The answer to “how did we get here?” is gone.
  • Event-sourced: store the changes themselves, as an append-only log of events. The current state isn't stored at all. It's computed by starting from an initial state and applying every event in order.

That computation is a fold, also called a reduce: state = fold(apply, events, initial). apply takes a state and one event and returns the next state. It's the same idea as the reducers earlier in this chapter, applied over the whole history instead of one step.

Rebuilding state from the log in Figure 9.6

def apply(state, e):
    if e["event"] == "run_started":
        state.agents[e["agent"]] = Agent(parent=None, status="running")
    elif e["event"] == "spawned":
        state.agents[e["data"]["child"]] = Agent(parent=e["agent"], status="running")
    elif e["event"] == "model_call":
        state.tokens_spent += e["data"]["tokens"]
    elif e["event"] in ("succeeded", "failed"):
        state.agents[e["agent"]].status = e["event"]
    return state

state = RunState()
for e in sorted(events, key=lambda e: e["seq"]):   # order is part of the meaning
    state = apply(state, e)

What you get, and what it costs

You get

  • An audit trail for free. What happened, in what order, is the data itself.
  • Time travel. Fold the first n events to see the state at step n.
  • New views without migration. Write a new apply; the log doesn't change.
  • A natural fit for append-only files, such as JSONL.

It costs

  • Rebuild time. Folding a long log is slow, so you save snapshots: the folded state at seq n. Rebuild = load snapshot + fold the events after n.
  • Event schema changes. Old events stay in old shapes, so apply must handle every version.
  • Discipline. apply must be deterministic, and each event must carry enough data to rebuild from.

The last cost is where trace logs usually fall short. An event that says “a1 succeeded” but leaves out the result can tell you that a1 finished, not what it returned. You can't rebuild a parent's aggregation from that.

Connecting the pieces

These ideas are one idea seen from different sides. Temporal's event history is an event log. A checkpoint is a snapshot. Replay is a fold. Reducers are apply for one step. Once your run is a value built from a log of events, you can resume it, fork it, audit it and replay it.

Misconceptions to drop
  • “A checkpoint makes resume safe.” It makes resume possible. Safe also needs idempotent side effects (Figure 9.5).
  • “A graph means no model decides anything.” A conditional edge can be a model call. The graph only limits its answer to the names you declared.
  • “Durable execution means exactly once.” Activities run at least once. An exactly-once effect needs an idempotency key on the receiving side.
  • “We log everything, so we have event sourcing.” Only if every event carries enough data to rebuild state. “a1 succeeded” with no result is a log line, not an event.
  • “State is whatever the variables hold.” State the program can't save and reload is state a crash will erase.
In your swarm harness
  • Stage 1. Your trace is a JSONL event log. Could you rebuild the whole agent tree, with each agent's final status, from that file alone? List the fields each event must carry for that to work. Is seq one of them, and why isn't ts enough?
  • Stage 2. A spawn that the policy rejects: does the rejected child ever exist as an agent with a state, or only as an event on the parent? Which choice makes your Stage 6 counts simpler?
  • Stage 6. Write (on paper first) the apply that folds your trace into a per-agent token table. If you can't write it, your events are missing data. Find out which before Stage 6, not during it.

Check yourself

Answer each one out loud or on paper before you open it.

Recall What does “make the run a value” mean, and what does it buy you?

Control and state are stored as explicit data (a status field, a named next step, a state record, an event log) instead of living only in the call stack. Because it's data, the run can be saved, inspected, paused, resumed, replayed and tested. A crash erases a call stack. It doesn't erase a file.

Recall What are resume, fork and replay, and how do they differ?

Resume continues from the latest checkpoint. Fork starts a new branch from an older checkpoint, leaving the original history intact. Replay re-runs steps using recorded outputs instead of live calls. That makes replay the only one of the three that is deterministic with an LLM in the loop, and the one you debug with.

Apply The run total is 1,000 tokens. Two children finish at the same time: one spent 300, the other 500. What is the total under an “overwrite” reducer, and under an “add” reducer?

Overwrite: each child read 1,000 and writes back its own total, 1,300 or 1,500. Whichever writes last wins, and the other update is lost. Add: each child contributes a delta, merged in either order, giving 1,800. Shared counters need reducers that merge deltas, which is the tokens_used row in this chapter's reducer table.

Apply The process crashes after a send_email activity ran but before its completion was recorded. What does a durable-execution engine do on restart, and what keeps it from sending twice?

It replays the workflow from its history. The activity has no recorded completion, so it runs again: activities are at-least-once. The idempotency key passed with the request lets the email service recognise the duplicate and drop it. The engine guarantees the retry. The key makes the retry harmless.

Design You want a human to approve any plan with more than five children. Where does the interrupt go, what must be saved, and what can go wrong on resume?

Put the interrupt after the plan is validated and before anything is spawned. Save the validated plan, the agent's state and the budget reservation, so the resumed run acts on exactly what the human saw. The risk: if the framework re-runs the interrupted node from its beginning, anything before the interrupt runs again, such as a second planning call that produces a different plan. Keep side effects and fresh model calls after the interrupt, or record their results.

Design Your trace logs {"event": "succeeded", "agent": "a1"}. What can't you rebuild from it, and what is the smallest fix?

You know that a1 finished, but not what it returned, so you can't rebuild the parent's aggregation, replay the parent, or check the parent's answer against its inputs. Smallest fix: include the Result in the event (or a reference to where it's stored), plus the tokens charged. Then the event, not the process memory, is the source of truth.

Interview “When would you model an agent system as an explicit graph instead of letting the model drive the loop?”

Use a graph when the steps are known in advance and you need guarantees: required review steps, approvals, audit, resumable long runs, and testable routing. Let the model drive when the path really can't be known in advance and the task needs flexibility. A common middle ground: a declared graph whose conditional edges are model calls, with each answer checked against the declared edge names. Mention the cost: graphs are more code and less adaptive, and model-driven loops are harder to bound and debug.
