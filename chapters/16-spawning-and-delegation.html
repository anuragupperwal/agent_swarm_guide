Spawning and recursive delegation

How an agent creates another agent, hands it work, and gets the result back, and how a harness stops that from becoming a thousand agents spending your budget. This is the chapter your project is built around, so it asks more questions than it answers.

The big idea

In your harness, an agent does not “decide to become many agents”. It makes a tool call. One of the tools it has is spawn_agent, and calling it is a request. The harness checks the request against limits, creates the child, runs it, and hands the child's result back to the parent as an ordinary tool_result. From the parent model's point of view, a subagent is a slow, expensive tool that happens to think.

This framing matters because it puts every multi-agent question into a place you already understand: a tool call has a schema (what the parent may ask for), an executor (what the harness does), and a result (what comes back). Recursion is just the child having the same tool.

Key idea

The model proposes, the harness disposes. The model decides whether to delegate and what to delegate. The harness decides whether the request is allowed, assigns the child's identity, depth and budget, and enforces every limit. Anything the model sets can be wrong; anything the harness sets is a guarantee.

Subagent as a tool

Frameworks use the same shape. The OpenAI Agents SDK can turn an agent into a tool with as_tool(); Claude Code exposes subagents to its main agent through a tool. Chapter 15's distinction applies: this is agent-as-tool, so control returns to the parent. A handoff would never come back.

What should the spawn tool's input look like? Here is one possible shape, written as the JSON Schema the model would see. It is an illustration to argue with, not a recommendation:

A possible spawn_agent definition (illustrative; the // notes are annotations, not JSON)
{
  "name": "spawn_agent",
  "description": "Delegate one self-contained subtask to a new agent. Returns its result.",
  "input_schema": {
    "type": "object",
    "properties": {
      "objective":       { "type": "string" },  // what done looks like
      "context":         { "type": "string" },  // what the child must know
      "tools":           { "type": "array", "items": { "enum": ["web_search", "fetch_url"] } },
      "expected_output": { "type": "string" },  // format of the return
      "must_succeed":    { "type": "boolean" }  // can the parent finish without it?
    },
    "required": ["objective", "expected_output"]
  }
}

Notice what is not there: no depth, no budget, no id. If the model could set its child's depth, a confused model could reset it to zero and recurse forever.

The spawn lifecycle

Between the model asking for a child and the parent receiving its result, eight things happen. Most bugs in recursive systems come from doing them in the wrong order or skipping one.

StepQuestion it answersIf you skip it
1 ProposeDoes the parent want help, and with what?(Nothing to skip: this is the model's call.)
2 ValidateIs the request well formed, and allowed by every limit?A malformed or over-limit request becomes a real agent.
3 CreateWhat is the child's identity, depth, budget and tool set?No stable id to trace, no depth to check next time.
4 RegisterDoes the run's state know this child exists?Counters lag behind reality; two concurrent spawns both pass a limit check.
5 ScheduleWhen may it start, given concurrency limits?Fifty children hit the API at once and all get rate-limited.
6 RunThe child's own agent loop.(The point of the exercise.)
7 ReturnDoes the result meet the return contract?The parent receives garbage it cannot tell from a real answer.
8 AggregateHow does this result combine with the others?Results are pasted together and the parent's window fills up.

Create is not run

Steps 3 and 6 are separated on purpose. Creating a child means building its record: an id, a parent id, a depth, a budget, a status of pending. Running it means starting its loop. The gap between them is where the harness does its checking and where cancelling costs nothing, because nothing has been spent yet.

In Python's asyncio the same gap exists at a lower level: calling a coroutine function only builds a coroutine object; asyncio.create_task schedules it; it actually starts executing only when the event loop next gets control. If your limit check reads a counter, then awaits something, then increments the counter, two siblings can both pass the check in that window. That is chapter 10's check-then-act race, and it is why step 4 (register) belongs before any await. See chapter 10.

What a child receives, and what it returns

A child starts with an empty context window. Everything it knows comes from what the spawn gives it; everything the parent learns comes from what the child sends back. These two envelopes are the whole interface, so design them as carefully as you would an API.

Why status needs more than “success”

A boolean throws away the difference between “I finished”, “I got halfway and ran out of budget” and “I crashed”. The parent's next move differs in each case: use the result, use what there is and note the gap, or retry or carry on without it. A useful set of terminal states is ok, partial, failed, timeout, over_budget and cancelled. Notice that the last three are set by the harness, not by the child: a child that has been cancelled cannot report it.

Pitfall

Returning status: ok with an answer the child made up because it couldn't find one. An explicit gaps field, plus a prompt that rewards admitting gaps, gives the child a respectable alternative to inventing something. Provenance gives the parent a way to check.

Context passing and the telephone game

How much of what the parent knows should go into the child's brief? And how much of what the child found should come back? There are three broad answers.

StrategyWhat movesStrengthWeakness
FullThe whole history (Cognition's “share full traces”)Nothing is lost; implicit decisions are visibleDefeats context isolation; cost grows with depth
DistilledA written brief down, a summary upSmall, focused windowsLossy at every level; the writer decides what matters
ReferenceA summary plus a pointer to full findings in a shared storeSmall by default, complete on demandNeeds a store, ids and a tool to read it

The telephone game is not only about losing facts. Each level also re-frames: it decides what the question was, which source is authoritative, and how confident to sound. A hedge (“one blog claims…”) at depth 2 can become a fact at depth 1 and a headline at the root. Provenance that travels with each claim is the antidote, which is why it is in the return contract.

Limits and the growth math

If every agent may spawn up to f children, and the tree may go d levels below the root, the maximum number of agents is a geometric series: one root, f children, f2 grandchildren, and so on.

Key idea

Prompt guidance (“use one subagent for simple questions”) shapes the typical run. Harness limits bound the worst run. You need both, and you should only trust the second. A rejected spawn should come back to the model as an error observation it can read and adapt to, not as a crash.

Budgets: slices or a pool

A token budget for the whole run has to be shared out somehow. There are two basic designs, and most real systems end up in between.

Required and optional children

When a child fails, the parent's correct reaction depends on whether it could finish without that child. That's why must_succeed appears in the spawn request: the parent's model knows which parts of its plan are essential.

Required child fails. The parent can retry (a new child with a clearer brief, not the same brief again), or fail itself with status failed and a reason that names the child. A retry costs budget, so it should be counted against the same limits.

Optional child fails. The parent carries on, and records the hole in its own gaps field. The final answer should say what is missing, rather than quietly covering less ground.

The harness can add a policy on top of the model's choice, for example “if more than half of a parent's children fail, the parent fails”. Ask yourself which of these should be fixed in code and which should be left to the model.

Aggregation

Step 8 turns several results into one. In a recursive tree it happens at every level, because each parent aggregates its own children before returning, so its design compounds with depth.

StrategyHowCostWhat it losesUse when
ConcatenatePaste results in orderNoneNothing, but the parent's window fillsFew, short results
MergeCombine structured fields in code; de-duplicate by keyCheap, deterministicConflicts need a rule (newest? best source?)Results share a schema, such as lists of facts with sources
SynthesizeOne more model call writes a single answer from all inputsOne large callNuance; it may invent connections between sourcesA prose answer, such as your RAG explanation
VoteMajority or judge among duplicate attemptsk × the workA minority answer that was rightSeveral attempts at the same question
Pitfall

Synthesizing in the same call that does the parent's other work. If the parent's window already holds its own research plus every child's result, synthesis quality falls for the reasons in chapter 06. Merging in code first, then synthesizing from the merged, de-duplicated version, keeps that final call small.

Termination

A run has ended only when every agent in it has reached exactly one terminal state. The root returning its answer is not enough: a child still running after its parent has returned is an orphan. It keeps spending budget and its result goes nowhere.

Two rules prevent orphans:

  1. A parent cannot finish while any child is still running. It must wait for each child, or cancel it, before it returns.
  2. Cancelling a parent cancels its whole subtree. A deadline at the root must reach every leaf.

This is structured concurrency: the lifetime of every task is nested inside the lifetime of the task that started it. Python 3.11's asyncio.TaskGroup enforces it for a group of tasks: the block cannot exit until all its tasks are done, and if one fails with an exception the others are cancelled. Whether “one child failed, cancel its siblings” is the behaviour you want for optional children is a design question, not a library default to accept unexamined.

Check yourself

Answer each one out loud or on paper before you open it.

Recall List the eight steps of the spawn lifecycle, and say who owns each.

Propose (parent's model), validate, create, register, schedule (harness), run (child), return (harness checks the child's result), aggregate (parent's model, or code the parent calls).

Recall Why are depth, budget and id missing from the spawn tool's input?

They are guarantees, so the harness must assign them. A model that could set its child's depth could reset it and recurse without bound; one that could set its own budget could exceed the run's.

Apply Fan-out 4, depth 3 below the root. Maximum number of agents?

(44 − 1) / (4 − 1) = 255 / 3 = 85, that is 1 + 4 + 16 + 64.

Apply The total-agent cap is 20 and 19 exist. Two siblings request a spawn at the same moment. What can go wrong, and what fixes it?

If each checks the count, then awaits something, then increments, both see 19 and both pass, giving 21. The check and the registration must happen together with no await between them (or under a lock), so the second request sees 20 and is rejected.

Apply With slices, a parent splits 90k into three equal parts. Child A needs 45k; B and C need 10k each. What happens, and what happens with a pool?

Slices: A hits its 30k cap and returns partial, while B and C strand 20k each. Pool: A can take 45k, total use is 65k, and nothing is wasted, but if A had started first and needed 90k, it could have starved B and C. A per-child cap on a pool limits that.

Design A required child times out. List the parent's options and what each costs.

Retry with a new child and a clearer or smaller brief (more budget and time, counted against limits); do the work itself (fills its own window); or fail with a reason naming the child (honest, but the run produces less). Repeating the same brief to a fresh child usually repeats the failure.

Interview “How do you stop a recursive multi-agent system from running away?”

Layered limits enforced by the harness, not the prompt: max depth, fan-out and total agents checked atomically at spawn time; a shared token budget with reservations; a root deadline that cancels the whole tree; a concurrency semaphore; max steps per agent. Rejections come back to the model as readable errors. Structured concurrency ensures no orphans, and a trace of the spawn tree makes runaway behaviour visible.

Interview Compare full, distilled and reference context passing.

Full keeps every implicit decision visible but defeats context isolation and grows with depth. Distilled keeps windows small but loses information at every level (the telephone game). Reference passes a summary plus a pointer to complete findings in a shared store, small by default and complete on demand, at the cost of building and securing that store.
