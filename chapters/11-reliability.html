Reliability engineering

Everything in an agent run fails sometimes: the network, the provider, the model's output, the tools, and the agent's own judgment. A reliable harness doesn't prevent failure. It turns every failure into a contained, visible event that the code around it can respond to.

The big idea

A single model call fails rarely enough that you can ignore it in a demo. An agent run makes dozens of calls, and a swarm makes hundreds. Small per-step failure rates multiply, and the result surprises almost everyone the first time they calculate it.

Key idea

Every failure must end up as data, in a known place, with a known owner. Your spec calls this principle 2.8, “failures are data”. A failure that becomes a value can be retried, logged, counted, shown to the parent, or reported to a human. A failure that escapes as an uncaught exception, or that the model quietly papers over, can't be handled by anyone.

The chapter follows the order in which a harness meets a failure. First, recognize what kind it is (the taxonomy). Then contain it (errors as values). Then decide whether to try again (retries, idempotency), how long to wait (timeouts), how much to spend (budgets), and whether the output is any good (validation, guardrails). Last come the techniques for keeping one failure from spreading: circuit breakers, graceful degradation, loop detection and hard stopping mechanisms.

A failure taxonomy

“The agent failed” isn't actionable. The right response depends entirely on the kind of failure, so the first job is to sort failures into classes. The most useful single question is “would trying the exact same thing again plausibly work?” If yes, the failure is transient. If no, it's permanent, and retrying only burns money.

ClassExamplesRetry?Typical response

Permanent request error400 invalid request, 401 or 403 auth, 413 request too large, prompt over the context limitNoFail fast. The request or the config is wrong, and it will be wrong next time too.
Output shapeInvalid JSON, schema violation, stop_reason: max_tokens cut the output offSometimesRe-ask once or twice with the exact error. For truncation, raise max_tokens or ask for less.

Notice where the boundaries fall. Infrastructure failures are the easy ones: the HTTP status tells you the class. Model failures are harder because the call succeeded: you got a 200 and a well-formed response, and the problem is in the content. Behavioral failures are the hardest because no single response is wrong. The failure only shows up as a pattern across many steps, so you can only catch it by watching the trajectory.

Common pitfall

Retrying everything. A blanket retry(3) around the model call retries 400s, auth failures and refusals, which never succeed, and it hides the real problem behind three times the latency and cost. Retry is a decision you make per failure class, not a wrapper you put around everything.

Errors as values

Python's default is to raise an exception and let it climb the stack until something catches it. Inside a single function that's fine. Across a tree of agents it's dangerous: an exception thrown in a grandchild travels up through code that wasn't written to expect it, and it can take the whole run down with it.

The fix is a boundary. At the edge of every agent, the harness catches whatever went wrong and converts it into a Result: a plain value that says what happened. Inside the agent, exceptions are fine. Across the boundary, only values travel. The parent never has to guess what a child might throw, because a child can only ever return.

Two rules keep the boundary honest:

  • Never swallow cancellation. In Python 3.8 and later, asyncio.CancelledError inherits from BaseException, so except Exception doesn't catch it. That's deliberate. If the boundary catches it and returns a Result, the parent's timeout or shutdown silently stops working (ch10). Let cancellation pass through, or record it and re-raise.
  • Keep the error's class. A Result that only says "error: something went wrong" throws away the one fact the parent needs: was it transient or permanent? Keep a machine-readable kind next to the human-readable message.

Retries, backoff and jitter

For transient failures, trying again is the right move. How you try again is where most of the engineering lives. Three ideas matter.

Exponential backoff
Wait longer after each failure: 1 s, then 2 s, then 4 s, up to a cap. If the provider is overloaded, hammering it at a fixed interval keeps it overloaded. Backing off gives it room to recover.
Jitter
Add randomness to each wait. Without it, every client that failed at the same moment retries at the same moment, and the retries arrive as a synchronized spike. This is the thundering herd. A swarm creates the herd itself: ten children launched together all hit the same rate limit together.
A stopping rule
Limit the number of attempts and the total time spent retrying. Four attempts with a 60-second cap can take over a minute, and that minute has to fit inside the caller's deadline.
wait = random(0, min(cap, base × 2attempt))

That's “full jitter”, from Marc Brooker's analysis of retry strategies (see Sources). It completes the work with fewer total calls than backoff without jitter. When the provider tells you how long to wait, for example with a retry-after header on a 429, prefer its number over yours.

Retries multiply across layers

Here's predict question 2. If the model client makes 3 attempts, and the child wraps its work in 3 attempts, and the parent wraps the child in 3 attempts, one bottom-level outage produces 3 × 3 × 3 = 27 requests. That's for a single grandchild call. Multiply by the fan-out and a swarm can turn a 30-second provider blip into thousands of requests that keep the outage going. This is retry amplification.

  • Retry at one layer. Usually that's the lowest layer that can see the failure class, which is the model client or the tool executor. Higher layers receive a failed Result and make a different decision, such as re-plan, skip or fail. They don't blindly repeat.
  • Know what your SDK already does. Provider SDKs commonly retry some errors on their own. The Anthropic Python SDK, for example, retries a small number of times by default and lets you set max_retries. Wrap it in your own retry loop without checking, and you've already multiplied.
  • Use a retry budget. Google's SRE book describes capping retries as a fraction of all requests (around 10% per client). When retries exceed the budget, the client stops retrying and fails fast, because at that point the problem is clearly not transient.

Idempotency

An operation is idempotent if doing it twice has the same effect as doing it once. Setting status = "done" is idempotent. Appending a row, sending an email, charging a card and spawning a child agent are not.

This matters because a timeout doesn't tell you what happened. When the 30-second email call in predict question 3 times out, there are three possibilities:

  1. The request never arrived. Retrying is correct.
  2. It arrived, the email was sent, and the response was lost on the way back. Retrying sends a second email.
  3. It's still running. Retrying may send a second email in a few seconds.

From the caller's side, all three look identical. So the honest answer to predict question 3 is: retry only if the operation is idempotent, or can be made idempotent.

Tool kindExamplesSafe to retry blindly?How to make retries safe
Read-onlysearch, read file, GETYesNothing needed, apart from cost
Idempotent writewrite file with full content, PUT, set a fieldYesMake sure the tool really is idempotent, not just named like it
Non-idempotent writeappend, send, pay, create ticketNoAn idempotency key the receiver uses to drop duplicates, or a check before acting
Spawn a child agentdelegate a subtaskNoRegister the spawn under a deterministic id first; on retry, look it up before creating another
Model callmessages.createNo side effects, but costs tokens and may answer differentlyRecord the response as an event; on replay, reuse it instead of calling again (ch09)

An idempotency key is an id for the logical operation, not for one attempt. The caller sends the same key with every retry, and the receiver remembers keys it has already completed. For a harness, a good key is derived from things that stay the same across a replay, such as the run id, the agent id, the step number and the call's position in that step. A random UUID generated at call time is a bad key: the retry generates a new one, and the duplicate gets through.

Note

Model calls look safe to retry because they have no side effects. They aren't free, though. A retried call can return a different answer, and if the first answer was already logged and partly acted on, your history now contradicts itself. That's why durable-execution systems record each model response as an event and replay it rather than call the model again.

Timeouts at every level

Every await on something outside your process needs a bound. A call with no timeout can hang forever, and here's the trap: a hung call spends no tokens. Your token budget never fires, your step counter never advances, and the run sits there until a human notices. Only a clock catches a hang.

Timeouts exist at several levels, and they nest:

  • Connection and read timeouts on each HTTP request.
  • Per call: one model call or one tool call.
  • Per agent: total wall time for an agent, including all its steps and children.
  • Per run: the deadline for the whole tree.

Two practical consequences:

  • Pass deadlines, not durations. “Finish by 14:05:00” stays correct as it travels down the tree. “You have 60 seconds” is wrong as soon as it's been queued for 10 seconds. Each level computes its remaining time from the absolute deadline it was given.
  • Leave room to report. An agent that uses its whole allowance has no time left to return a useful partial result. A common pattern is a soft deadline, where the agent is told to wrap up, ahead of the hard deadline, where the harness cancels it.

Pick values from measured latency, not guesses. Model latency grows with the number of output tokens, so a call that writes a long plan has a much longer tail than a call that picks a route. Chapter 13 shows how to record the latencies you need to choose these numbers.

Budgets and where they are enforced

A timeout bounds time. A budget bounds spend. A run needs both: a fast agent can burn a large token budget in a minute, and a hung agent can sit inside its token budget forever. The things worth metering are:

Tokens: input and output separately. Input grows fastest, because every step resends the history (ch01).

Steps: model calls per agent. A simple backstop against loops.

Wall time: the deadline from the previous section.

Agents: total spawned, depth and fan-out. These bound the shape of the tree.

Cost: tokens multiplied by price. Keep prices in config, because they change.

Tool calls: especially calls with external cost or side effects.

Defining a budget is easy. The hard part is choosing where in the loop it's checked, because a check in the wrong place records the overspend instead of preventing it.

The most common budget bug in a concurrent harness comes straight from chapter 10. Two children each check “are at least 5,000 tokens left?”. Both see 8,000, both pass, both spend 5,000, and the run is 2,000 over. The check and the spend were separated by an await, and another task ran in between. The fix is a reservation: check and deduct in a single step with no await inside it, then refund the difference once the real usage is known.

Budgets also need a policy for what happens as they run out:

  • Soft limit, for example at 80%: tell the agent, through its context, to wrap up and report what it has.
  • Hard limit at 100%: the harness stops the agent, whatever the agent thinks, and returns a Result with a budget_exceeded status and whatever partial output exists.
In your swarm harness
  • Stage 2. Is there one budget meter for the whole run, or one per agent that rolls up? Draw both for depth 2. Which one makes “the run spent at most N tokens” easy to prove?
  • Stage 3. Write the test first: launch 10 children concurrently against a budget that only fits 6. What exact outcome should the test assert?
  • Stage 4. How will point ① estimate the cost of a call before making it? Which part of the estimate is exact, and which is a ceiling?

Validating output, and guardrails

Chapter 01 introduced four checks on model output, in order: syntax (does it parse?), schema (right fields and types?), semantics (does it make sense in this world, for example does the file exist?), and policy (is it allowed?). This chapter adds what to do when one fails.

Check failsExampleResponse
SyntaxOutput isn't valid JSONRepair loop: re-ask once with the parser's exact error. Often fixed by strict tool schemas instead.
Schemasubtasks is a string, not a listRepair loop with the validator's message, which names the field.
SemanticsA plan with 40 subtasks when the fan-out limit is 5; two subtasks that are the sameRe-plan with the rule stated explicitly, or clip and record it. Never silently accept.
PolicyA tool call that writes outside the workspaceReject. Don't ask the model to try again until it finds a version that slips past (ch12).

A repair loop is different from a retry. A retry sends the same input and hopes for a different outcome. A repair sends a new input that contains the specific error, so the model has something to fix. Bound it to one or two rounds. If the model can't produce valid output after two precise corrections, a third rarely helps, and the loop becomes a cost leak.

Key idea

The model proposes, the framework disposes (spec 2.2). A plan from the planner is a proposal. Your validator decides whether it runs. That decision lives in code you can test, not in a sentence in the prompt you can only hope the model follows.

Guardrails

A guardrail is a check that runs around the agent rather than inside its reasoning. There are three positions for one:

  • Input guardrails run before the model sees something, for example rejecting a request that's off-topic for this agent.
  • Tool guardrails run between the model's tool_use and the actual execution. They check an allowlist, the argument ranges and the permissions. This is the most important position, because it's the last point before something happens in the world.
  • Output guardrails run before a result leaves the agent: to the parent, to the user, or to an external system.

A guardrail can be plain code (a regex, a schema, an allowlist) or a separate, cheaper model acting as a classifier. Code is deterministic and testable, so use it wherever the rule can be written down. Use a classifier model only where the rule can't, and remember that it's another fallible component, with its own failure rate and its own exposure to injection (ch12).

Circuit breakers

Retries handle a blip. They make an outage worse. When the provider is actually down, every agent in the swarm keeps trying: each call waits through its full timeout, retries with backoff, and fails. Children pile up waiting, deadlines expire, and the provider gets hammered just when it's trying to recover.

A circuit breaker watches calls to one dependency and stops sending them once failures cross a threshold. It's named after the electrical part, and was popularized for software by Michael Nygard's Release It!.

Compare it with the retry loop. A retry is optimistic and works on one call: “that probably was a blip”. A breaker is pessimistic and works across calls: “the last 20 calls tell me this isn't a blip”. You want both, and the breaker sits outside the retry, so an open breaker stops the retries too.

In a swarm, where the breaker lives matters. With one breaker per agent, each of 50 agents has to discover the outage separately. With one breaker per dependency (one for the model provider, one for each external API), the first few failures protect everyone. That breaker is shared mutable state, so it raises the same concurrency questions as the budget meter.

Graceful degradation and partial results

A parent sends out five children. Four come back with status: ok and one times out. The parent has four options, and choosing between them is a policy decision you make in advance, not something to improvise at run time:

  1. Fail the whole task. Correct when every part is essential, for example all the steps of a migration.
  2. Retry or replace the failed child, if there's time and budget left, and the failure was transient.
  3. Return a partial result that says exactly what is missing and why.
  4. Fall back to something cheaper: a smaller model, a cached answer, a simpler method.

The policy is much easier to write if every subtask is marked required or optional when it's planned. A failed required child fails the parent, or triggers a re-plan. A failed optional child leaves a documented gap. The planner can propose the marks, and your validator can check them, but someone has to decide them before the run, not after.

Common pitfall

The silent gap. The parent asks the model to “write the final answer from these results”, and one result is an error message. The model, trying to be helpful, writes a confident, complete-looking answer that simply leaves that part out, or worse, invents it. A partial result that looks complete is more dangerous than an honest failure. Make coverage a field the harness fills in (“3 of 4 sections; the cost analysis child timed out”), not something the model may or may not mention.

Every fallback should be visible too. If the answer came from the smaller model because the breaker was open, the Result should say so. Otherwise your evaluations in chapter 13 will measure a mix of two systems and you won't know it.

Loop detection

Behavioral failures don't show up in any single response. Each call looks reasonable, and the problem is the pattern. The harness has to watch the trajectory for signals such as these:

SignalHow to detect it in code
Same call, again and againHash the tool name plus canonical JSON of the arguments. Count repeats within a window.
Same error, again and againCount consecutive is_error results with the same error kind.
Oscillation (A, B, A, B)Look for a repeating cycle in the last few action hashes.
No progressSteps keep coming but the state (files written, facts gathered, subtasks completed) doesn't change.
Delegating the same taskA child proposes a subtask that matches its own task, exactly or almost. Swarm-specific, and it recurses until a depth limit stops it.

The response is usually two-step. First, tell the agent, through an observation, what you've seen: “you've called search with these exact arguments 3 times, and the result won't change”. Models often recover once the pattern is pointed out. If the pattern continues, stop the agent and return a Result that says why. Loop detection is a heuristic, though. It will miss loops it wasn't designed to recognize, which is why it can't be the only stopping mechanism.

Stopping runaway recursion

An agent that can spawn agents can, in principle, spawn forever. Every layer in this chapter contributes a brake. They aren't equally strong, and the useful way to rank them is to ask: can a confused, wrong or manipulated model get around it?

The prompt instruction is the least trustworthy for four separate reasons. The model may misjudge what “too many” means for this task. It may lose the instruction in a long context. An injected document can override it (ch12). And every child gets its own prompt, so the instruction has to survive being passed down the tree, which is the telephone game from chapter 16. The instruction is still worth having: a model that rarely over-spawns makes the hard limits fire less often, which saves money. Just never count it as a guarantee.

Two details decide whether the hard limits actually work:

  • Check at create time, not run time. A depth or count limit checked after the child has started has already let it spend. The check belongs between “the model proposed a spawn” and “the harness created an agent”.
  • A rejected spawn is an observation, not a crash. Tell the model, as a tool result, that the limit was reached, so it can do the work itself or return a partial result. A raw exception would only turn a limit into a failure.
Key idea

You should be able to prove your run terminates. With a depth limit and a fan-out limit, the tree is finite. With a step limit and a deadline on every agent, every node finishes. Put those together and the run must end, whatever the model does. If you can't write that argument for your harness in three sentences, one of the hard limits is missing.

Check yourself

Answer each one out loud or on paper before you open it.

Recall What single question separates transient failures from permanent ones? Give two examples of each.

“Would sending exactly the same request again plausibly succeed?” Transient: a 429 rate limit, a 529 overloaded response, a connection reset, a read timeout. Permanent: a 400 invalid request, a 401 auth failure, a prompt over the context limit, a refusal. Retry only the first group.

Recall Exponential backoff already spaces out retries. What problem does jitter fix that backoff doesn't?

Synchronization. Backoff slows each client down, but clients that failed at the same moment still wait the same amounts and retry at the same moments, so the load arrives in spikes. Jitter randomizes each wait so the retries spread out. A swarm makes this worse, because it launches many children at once.

Apply A 12-step run where each step succeeds with p = 0.97. What's the chance that no step fails?

0.9712 ≈ 0.69. Roughly 3 runs in 10 hit at least one failed step, which is why recovery has to be built into the loop, not bolted on.

Apply Two concurrent children both check “at least 5,000 tokens left?”, both see 8,000, and the run ends up 2,000 over budget. What went wrong, and what's the fix?

A check-then-act race across an await (ch10): another task ran between the check and the spend. The fix is a reservation that checks and deducts in one step with no await in between, followed by a refund of the unused part once the real usage is known.

Apply The run deadline is 14:00:00. It's now 13:58:30 and a child asks for 120 seconds. What deadline does the child get, and what should it do with it?

min(13:58:30 + 120 s, 14:00:00) = 14:00:00, so 90 seconds. It should plan for 90, not 120, and leave a margin before the hard deadline to return a partial result.

Design A tool creates tickets in an external tracker. A call times out. How do you make retrying it safe?

You can't tell from a timeout whether the ticket was created. Options: send an idempotency key derived from run id, agent id, step and call index, so the tracker or a check-before-create step drops duplicates. Or look the ticket up by that key before retrying. Or don't retry: return an is_error result saying “outcome unknown” and let a human or the parent decide. A random key generated per attempt doesn't work.

Design Where should the circuit breaker for the model provider live in a swarm, and how does it relate to the retry loop?

One breaker per dependency, shared by every agent, so the first failures protect the whole swarm instead of each agent learning separately. It sits outside the retry loop, so an open breaker also stops the retries. Because it's shared mutable state, its updates need the same care as the budget meter.

Interview “Our multi-agent system sometimes runs for hours and costs hundreds of dollars. How would you make that impossible?”

Don't start with prompts. Start with hard limits enforced in code: a run deadline that propagates down the tree, a shared budget pool with reservations, depth, agent-count and fan-out limits checked before any agent is created, and per-agent step limits and timeouts. Then give the termination argument: a bounded tree where every node is bounded must end. Add a circuit breaker so outages fail fast, retries at one layer only, and loop detection for wasted steps. Finish with tracing (ch13), so the next expensive run shows you exactly where the money went.

Recall card

Five lines to rehearse tomorrow, without looking.

  1. Reliability compounds as pn: at 0.95 per step, a 20-step run succeeds only about 36% of the time.
  2. Sort every failure by “would the same request work again?”. Retry only transient ones, at one layer, with backoff and full jitter.
  3. Deadlines nest: child deadline = min(own limit, parent's deadline). Pass deadlines, not durations. Only a clock catches a hang.
  4. Budgets: check the worst case before, charge the actual after, reserve before a spawn, refund on return. Check and deduct with no await between.
  5. Hard limits checked at create time, plus a step limit and deadline on every agent, make termination provable. A prompt instruction is the weakest brake.
