Designing a swarm harness

Nineteen chapters of parts. This one assembles them into one possible shape for a swarm harness: what it must guarantee, which component owns which state, how one run moves through them, and which decisions are still yours. It is a reference to argue with, not a blueprint to copy.

The big idea

Chapter 08 ended with a sentence: a swarm harness is a harness of harnesses. Each agent runs the same small loop you met in Chapter 03 (call the model, run tools, repeat). The swarm harness adds the machinery that lets one loop start other loops safely: something that decides whether a spawn is allowed, something that counts what has been spent, something that runs many loops at once without letting them trample each other, and something that writes down everything that happened.

Key idea

Architecture is a list of ownership claims. For every piece of state in the system (the budget, the tree of agents, each agent's messages, the trace) exactly one component may change it, and everyone else asks. Most multi-agent bugs in Chapter 19 trace back to state with two writers or none.

The rest of this chapter goes from the outside in. First the guarantees the harness must give (requirements). Then a component diagram that meets them. Then one run traced through it, step by step. Then the data each component holds. Then the decisions this guide deliberately leaves open, because they are the actual learning in your project.

Requirements before boxes

Start with what the system must guarantee, not with which classes it has. A requirement that names a guarantee (“a failed child never crashes the run”) forces a component into existence. A requirement that names a component (“we need a message bus”) skips the reasoning and usually adds something you don't need yet.

A few of these deserve unpacking, because they are less obvious than they look:

R2 hard limits
“Hard” means enforced by code the model can't talk its way past. A prompt that says “don't spawn more than 5 agents” is a request, not a limit. The limit lives in the spawn service (Chapter 16).
R3 parallel
Parallelism creates the race you met in Chapter 10: two children check “is there budget left?” at the same moment and both get yes. So R3 doesn't only force an executor; it forces the budget ledger to reserve atomically.
R4 isolation
Failure must become data (a Result with status failed), not an exception that unwinds through the parent. That single choice changes the signature of every function that runs a child.
R5 explainable
“Why did agent 7 exist?” needs a parent link, the plan that proposed it, and the policy decision that allowed it. That's the registry plus structured trace events, not log lines.
R6 deterministic
The model is non-deterministic (Chapter 01), so the harness must be testable without it. A scripted fake model makes spawn trees, failures and budgets reproducible.
R7 measured
“The swarm is better” is a claim about a comparison. Without a single-agent baseline on the same tasks (Chapter 13), it can't be true or false.

This is not your architecture. Real systems merge some of these boxes (the spawn service and the registry are often one class) or split others (the executor might become a worker pool on another machine). What should survive any rearrangement are the boundaries: limits are enforced outside the agent, budget changes go through one owner, every child's outcome comes back as a value, and every decision leaves an event.

Three details in that trace are design choices, not accidents. Ask yourself whether your harness would make each the same way:

  • The denial goes back to the agent that asked, as a tool error it can work around. The alternative is to fail that agent outright. Which is better depends on whether you trust agents to recover.
  • C's spent tokens stay spent. A failed agent's spending is real money. Releasing only the unspent part of its reservation is a ledger rule you have to write down.
  • The run ends partial, not failed. That status exists only if your Result type allows it, and your aggregator decides when to use it.

The spawn path, as pseudocode

This sketch shows only the order of steps from Chapter 16, inside the spawn service. The bodies are deliberately missing: they are Stage 2 and Stage 5 of your project. The comments mark the questions each step makes you answer.

async def handle_spawn_request(parent, proposed_tasks):
    # 1. VALIDATE: is the proposal well formed and allowed by policy?
    problems = validate(proposed_tasks, parent)      # schema, duplicates, depth, fan-out
    if problems:
        tracer.emit("spawn_deny", parent, problems)
        return denial_as_tool_result(problems)        # data, not an exception

    # 2. RESERVE: one atomic step. No await between check and update.
    reservation = ledger.try_reserve(parent, cost_estimate(proposed_tasks))
    if not reservation:
        tracer.emit("spawn_deny", parent, "budget")
        return denial_as_tool_result("budget")

    # 3. CREATE + REGISTER: records exist before anything runs
    children = [registry.create(parent, t, reservation.share(t)) for t in proposed_tasks]

    # 4. SCHEDULE + RUN: the executor owns concurrency and timeouts
    results = await executor.run_all(children)          # each → Result(status=...)

    # 5. SETTLE: return unspent reservation; spent stays spent
    ledger.settle(reservation, results)

    # 6. RETURN: the parent sees values, never raw exceptions
    return summarize_for_parent(results)              # how much detail? (context passing)
Who calls this?

In Stages 2–4 your code calls the spawn path directly from a scripted plan. In Stage 5 the model calls it, through a request_spawn tool. The function above shouldn't change between those stages. If it does, the boundary is in the wrong place.

Data models: fields to consider

Before you write a class, list the fields and, for each one, the question it forces. The table below is a checklist of fields worth considering, not a schema to copy. Several fields only make sense once you've answered a design question in the next section; those questions are in the right-hand column.

EntityFields to considerThe question each one forces
Taskid, objective, parent_task_id, context, expected_output, requiredHow much of the parent's context does a child get? Is the expected output free text or a schema? Can the parent succeed if an optional task fails?
AgentRecordid, parent_id, depth, status, child_ids, budget, created_atWho is allowed to change status? Is depth stored or computed from the parent chain? Which statuses exist, and which transitions are legal (Chapter 09)?
Resultstatus (ok / failed / partial / cancelled), output, error, usage, provenanceIs a timeout a failed or a cancelled? Does usage include the children's usage? How does the parent know which child said what?
Eventrun_id, agent_id, parent_id, type, ts, seq, payloadIs ts enough to order events from concurrent agents, or do you need a sequence number? Which event types are a closed list?
Budgetlimits, reserved, spent, scope (run or agent)Do you reserve an estimate, or a hard slice? What happens to a reservation when the agent fails halfway?

Wire shapes help you think about these as data, separate from Python classes. Here is one Result as JSON, showing the fields a parent needs to make a decision without reading the child's full transcript:

Why is children highlighted? Because it is a choice. Including it lets the root explain a partial answer. Leaving it out keeps the parent's context small. That's the context-passing decision (card 4 below) showing up in your data model.

Design decisions you still own

This guide stops here on purpose. Each card below is a real fork in the road: two or three defensible options, each with a cost. There is no recommended answer. Write your choice and your reason in docs/LEARNING_NOTES.md when you reach the stage named on the card, then check it against what your traces show.

1 · Who owns the tree?

Decide at Stage 2 · Figure 20.5

  • Central registry. Easy global queries and snapshots. Costs a second source of truth that must agree with what's actually running.
  • Parent-held handles. Minimal and naturally consistent. Global questions (“how many are running?”) need a walk or the trace.
  • Both, with the registry as a read-only view. Clear, but you must decide who updates it and when.

Measure: how often you need a global question answered while the run is live.

2 · How is the budget split?

Decide at Stages 2 and 5 · Figure 20.4

  • One pool. Simplest and nothing is stranded. Fairness is not guaranteed.
  • Slices. Local, provable limits per subtree. Parents must guess how much each child needs.
  • Hybrid (slices that return their unspent part, or a pool with per-agent caps). More flexible, more rules.

Measure: stranded budget at the end of a run; how often a late child is denied.

3 · What happens when a child fails?

Decide at Stages 2, 3 and 6

  • Fail the parent (fail fast). Simple and honest; one flaky child kills a large run.
  • Return partial. The parent continues and reports what's missing. Needs a required flag or a quorum rule.
  • Retry, then degrade. Bounded retries for transient errors only. Costs tokens and time; needs idempotent tools.

Measure: fraction of runs ending partial vs failed, and whether partial answers are still correct.

4 · What context does a child get, and return?

Decide at Stages 4 and 5 · Chapters 06, 16

  • Task only. Smallest context, best isolation. Risks the child missing a constraint the parent knew.
  • Task + curated brief. The parent writes what matters. Quality depends on the parent's summary (the telephone game).
  • Full parent history. Nothing lost, but context grows with depth and isolation disappears.

Measure: child answers that violate a parent constraint; tokens per child.

5 · How are results combined?

Decide at Stages 2 and 5

  • Concatenate. Deterministic and cheap. Overflows the parent's context as fan-out grows.
  • LLM synthesis. Produces one coherent answer. Adds a model call and can drop or invent facts.
  • Structured merge (each child returns fields, code merges them). Reliable, but only works when outputs have a shape.

Measure: facts present in children but missing from the final answer.

6 · How much runs at once?

Decide at Stage 3 · Chapter 10

  • One global semaphore. Protects the provider's rate limit. Deep trees can deadlock if parents hold slots while waiting for children.
  • Per-level or per-parent limits. Avoids that deadlock. More knobs to tune.
  • Model calls limited, agents not. Limits the expensive part only. Many idle agents still hold memory and state.

Measure: wall time vs concurrency; 429 errors; any run that stops making progress.

7 · What survives a crash?

Decide at Stage 6 · Chapter 09

  • Nothing (re-run from scratch). Simplest. Pays the whole cost again.
  • Trace only. You can explain and replay, but not resume.
  • Checkpoints of each agent's state. Can resume, but every tool must be safe to repeat (idempotency).

Measure: how long and expensive your real runs are; that sets the price of losing one.

8 · When is the run over?

Decide at Stage 2 · Chapter 16

  • When the root returns. Clear. Orphaned children must be cancelled explicitly.
  • A global deadline. Bounded wall time. Needs a clean way to cancel the whole tree.
  • Quiescence (nothing running, nothing queued). Natural for message-based designs; harder to detect correctly.

Measure: agents still running after the root finished (should be zero).

Which stage introduces which component

You won't build Figure 20.2 at once, and you shouldn't. Each stage of your plan adds the component that its experiment needs and no more. The map below is one reading of your plan. Check it against your own swarm_harness_development.md; if they disagree, your plan wins, but write down why.

Two things to notice. First, Stage 1 introduces five components before there is any model: the runner, runtime, tracer, ledger and Result type can all be tested with a scripted fake. Second, the spawn path exists at Stage 2 but the model doesn't call it until Stage 5. That three-stage gap is where you prove the harness is correct before letting a non-deterministic planner drive it.

What production adds

A learning harness that runs on your laptop and a production harness that serves a company differ in a predictable list of ways. None of these belong in your first stages, but knowing them prevents choices that make them impossible later (for example, an agent ID that's only unique within one process).

Shapes to avoid
  • The god orchestrator. One class that plans, spawns, counts, runs and aggregates. It works until you need to test one of those alone.
  • Components before pain. A message bus at Stage 2 because “swarms need communication”. Figure 20.1 has no arrow into it yet.
  • The LLM enforcing its own limits. “You may spawn at most 4 children” in a prompt is a suggestion. Limits live in the spawn service.
  • Unbounded recursion through a tool. If request_spawn doesn't pass through the policy check, depth limits apply to your scripted plans but not to the model.
  • Shared mutable state with no owner. Two agents appending to the same list is a race even in single-threaded asyncio, if there's an await between the read and the write.
  • Concatenating every child's output into the parent. At fan-out 10 with 3K tokens each, the parent's next call carries 30K tokens of results before it does any thinking.

Check yourself

Answer each one out loud or on paper before you open it.

Recall Why does the spawn service check the limits, rather than the agent that wants to spawn?

The agent is driven by a model, and a model can be wrong, confused or manipulated (prompt injection). A limit the agent enforces on itself is a request. A limit enforced by code outside the agent, at the single point every spawn must pass through, is a guarantee. It also puts every allow/deny decision in one place, so it can be traced and tested.

Apply Depth limit 3, fan-out limit 4, total-agent cap 30. Which limit actually binds, and what happens to the 31st spawn request?

Depth and fan-out alone allow 1 + 4 + 16 + 64 = 85 agents, so the total cap of 30 binds first. The 31st request is denied by the spawn service, recorded as a spawn_deny event with the reason, and returned to the requesting agent as data (a tool error), so it can answer with what it has. Nothing is created, and no budget is reserved.

Apply Two children each request one spawn when exactly one agent slot is left. Both get “yes”. What went wrong?

The check and the update were separated by an await (for example, a trace write or a model call). Both coroutines read “1 left”, then both reserved. The fix is to make check-and-reserve one step with no await between them (or to guard it with a lock), so the second request sees 0. Chapter 10 covers this race in detail.

Design A parent gets back two ok results and one failed. Describe two different aggregation policies and when each is right.

Fail fast: if any required child fails, the parent fails. Right when every part is essential (for example, all three sections of a contract review). Partial with disclosure: the parent answers from the two ok results, sets status partial, and says what's missing. Right when coverage can degrade gracefully (a market survey). A third option is a quorum (ok if at least k of n succeed), common in voting designs.

Design You want a single-agent baseline for evaluation. Which components from Figure 20.2 does it still use?

The runner, one agent runtime, the model client, the tracer and trace store, and the budget ledger (so cost is measured the same way). It skips the spawn service, executor fan-out, registry and aggregator. Using the same tracer and ledger is the point: the comparison is only fair if both sides are measured by the same code.

Interview “Walk me through what happens between an agent saying ‘spawn’ and the child's first model call.”

The model returns a request_spawn tool call. The runtime passes it to the spawn service. The service validates it (schema, duplicates, depth, fan-out), then atomically reserves budget. If either step fails, it returns a denial as a tool result. Otherwise it creates and registers the child record (id, parent, depth, budget), and the executor schedules it under the concurrency limit. The child's runtime builds its initial context from the task and brief, then makes its first model call. A trace event is emitted at each step.

Interview “Your prototype works. What would it take to make it production-grade?”

Structure the answer: durability (checkpoints, idempotent tools), limits (shared rate limiting, cost alerts, per-tenant budgets), safety (sandboxed tools, least privilege, approval gates), observability (OpenTelemetry export, versioned prompts and models in every trace), quality (an eval set run in CI against a single-agent baseline), and scale (a queue and workers instead of in-process tasks). Then say which one you'd do first for your specific use case, and why.
